# 收到开发指令：先 419，再整理可开工稿

用户原话（须遵守）：**收到开发指令时，先按这个规则：`docs/开发手册和方案/419-指令编写规范与模板-Codex.md`，再整理适合开发的。**

禁止：读完指令就改业务代码；整份按模板重抄一遍主线。

权威规范只读这一份，不要把 419 全文粘进本技能或指令里：

- `docs/开发手册和方案/419-指令编写规范与模板-Codex.md`

配合：`.cursor/rules/instruction-vs-start.mdc`、AGENTS「审核指令」授权。用户说「仅审核 / 不改文件 / 暂不实施」时停在指令整理，不编码。

## 流程

1. **读 419**（至少：使用原则、证据标记、分支维度、发出前检查）。再读用户给的指令全文。
2. **最小对照**（约 2 分钟）：只打开指令点名的 1～2 个落点文件 + 必要的 `docs/02` / 现有接口权限。够判就停，禁止全库扒。
3. **按 419 判定**：靠谱 / 要改指令 / 要拍板。会改变操作、金额、权限、数据契约且无依据的标「待确认」，一次问齐并给推荐；事实错误、与代码不符、缺「当…则…」自行改指令。
4. **整理适合开发的指令**（写回原文件，或新建后再让用户用这份开工）：
   - 骨架用 419 第四节模板；无关空表删掉。
   - 已是 419 结构则**只补缺口**，不重写。
   - 必须能开工：目标谁/入口/结果；做与不做；决策表（条件→提示→写入→不变→验证）；金额不变量；接口/改表契约；事务与失败；验收勾选映射分支；止步线。
   - 未核实标「待核实」（执行方核代码，不让用户代查）；未定标「待确认」。
5. **再编码**：指令整理完成、待确认已拍板或可独立部分之后，才改 `backend/` / `frontend/src/`。实施范围以整理后的指令为准。

## 整理时查这些（419 发出前检查的落地版）

- 入口、角色、权限与**现状代码**一致（菜单 `adminOnly` / `RoleGuard` / 许可证），不一致则改指令或标待确认，禁止按草稿臆造「班组长也能进」。
- 身份 / 对象不存在 / 业务状态（如已取消）分开写，不要捆成一句「不存在或无权限」。
- 空对象、无数据、NULL 金额、未知状态、计价类型非法，各有去向，不吞、不当成功。
- 金额：原事实 vs 快照 vs 固化项分清；精度与舍入；禁止两值相加。
- 每个关键分支有验证 ID；未验证不勾通过。
- 不发明未核实的「已有能力」；后置功能不预建表/接口/隐藏按钮。

## 反例

```text
# ❌ 用户 @ 未做指令 → 立刻改 Controller
# ❌ 骨架已是 419 → 再整份重写一遍

# ✅ 读 419 + 指令 + 落点文件 → 补决策表/待确认 → 写回指令 → 再编码
```
