# 2E · 需求分析：手机摄像头扫码报工

日期：2026-09-21  
状态：方案已落地代码；自动测试通过；真机/HTTPS 待现场验收。  
开发指令：[11-补充开发指令-手机摄像头扫码报工](已做指令/11-补充开发指令-手机摄像头扫码报工.md)

## 1. 问题与现状

用户在普通手机打开「扫码报工」，看到蓝色扫描框和「等待扫描工单」，预期出现摄像头实时画面，实际一直停留在静态页面。

根据当前仓库代码核查：

- `frontend/src/views/h5/scan.vue` 的扫描框是静态样式，没有调用摄像头或识别二维码。
- 已实现 PDA/扫码枪键盘模拟输入，收到回车后跳转报工页；也支持手动输入工单号。
- 现有路由为 `/#/h5/scan` 和 `/#/h5/report?order=工单号`。
- `frontend/src/views/order/PrintLabelDialog.vue` 支持打印纯工单号及完整报工链接两种二维码。
- `frontend/package.json` 中的 `qrcode` 用于生成二维码，不能替代摄像头识别库。
- 后端按当前登录工厂查询工单；报工权限仍由现有业务规则校验。
- 未登录直接打开报工链接时，现有登录会丢掉目标地址（需在本期做最小回跳修复）。

因此，问题是手机摄像头扫码尚未开发，而非用户操作错误。当前提示没有区分手机摄像头与硬件扫码，容易让用户误以为摄像头已经启动。

## 2. 目标与范围

在现有局域网 H5 页面增加摄像头扫码，识别后进入已有工单报工页；保留 PDA 和手动输入。

- 不开发原生 App，不接微信扫码接口，不依赖公网识别服务。
- 不改变报工提交、部门权限、工厂隔离和数据库结构。
- 本次不实现工单短编号生成，只兼容现有长编号、自定义编号和未来 `A0001` 等短编号。
- 本次不增加电脑后台入口、相册识别、批量扫码、离线报工等功能。
- 不做摄像头设备列表 UI；优先后置，失败则用默认摄像头。

## 3. 推荐交互

1. 工人点击底部「扫码」。首次进入提供「打开摄像头扫码」主按钮，同时显示「手动输入工单号」及「扫码枪模式」。
2. 点击主按钮，检查访问环境并请求摄像头权限；优先使用后置摄像头，不申请麦克风权限。
3. 授权成功后，在扫描框内展示实时画面和「请对准工单二维码」。画面未启动前不显示正在扫描。
4. 识别成功后锁定本次结果，停止摄像头并解析工单号，跳转已有报工页。
5. 报工页按现有接口查询本厂工单；工人选择工序、填写数量并提交。扫描不会自动提交报工。
6. 离开页面、切换手动/PDA 模式或页面进入后台时关闭摄像头；回到前台后显示重新启动按钮。

PDA 使用明确的「扫码枪模式」：激活输入焦点、接收扫描内容和 Enter、清空输入、避免重复跳转。本设备记住上次摄像头/PDA 选择（`h5.scan.mode`）；首次默认摄像头待启动，已选 PDA 的设备再次进入时恢复 PDA 输入焦点。普通手机不自动抢焦点，避免无故弹出软键盘。

## 4. 二维码兼容规则

| 内容 | 处理 |
|---|---|
| 纯工单号，如 `GD20260914004` | 去掉首尾空白，长度 ≤ 64，按工单号进入报工页 |
| 未来短编号，如 `A0001` | 与普通工单号一样处理，不要求固定前缀或长度为 5 |
| 现有自定义工单号 | 继续兼容，不擅自转换大小写或增加不必要的格式约束 |
| 本站报工链接 | 校验来源和报工路由，从 hash 路由查询参数中提取唯一、非空的 `order` |
| 外站链接、错误路由、缺失或重复 `order` | 明确提示无效，不跳转到二维码给出的地址 |

摄像头和 PDA 共用二维码内容解析逻辑（建议 `frontend/src/utils/scanPayload.js`）。手动输入只接收工单号，避免把本来合法的自定义编号误判为网址。

默认只接受与当前页面同源的完整报工链接；协议、主机或端口不同均不默认为可信。同一系统以前打印的 HTTP、旧域名或其他端口链接也可能因此被拒绝。实施前盘点旧标签和打印设置，优先继续使用纯工单号码；如确需兼容旧来源，另行列出精确可信来源后补充指令，不能直接允许任意域名。

二维码仍只用于定位工单，不携带登录令牌，也不赋予报工权限。未登录打开本站报工链接时，登录成功后应回到该 H5 目标（仅 `/h5/*`）。

## 5. 技术方案

推荐 `qr-scanner` 配合 Vue3；依赖与 worker 全部随前端构建部署（Vite `?url` 引入 worker），不运行时访问公共 CDN。开发时核实所选版本的接口、许可与 Vite 构建兼容性，提交依赖锁文件。

摄像头图像在设备本地识别，不上传图片或视频；识别出的工单号交给已有业务接口处理。无需新增数据库表，原则上无需新增后端接口。

解析规则用纯函数 + `node --test` 覆盖；不为本功能单独引入 Vitest。

需要处理启动、识别、停止、销毁以及异步启动晚于离开页面完成的竞争情况，避免摄像头在离页后仍开启。同一码多帧识别只处理一次；二维码暂未出现在画面中属于正常扫描过程，不应反复弹错。

## 6. HTTPS 与局域网部署

网页调用摄像头需要安全上下文与用户授权。普通手机通过 `http://192.168.x.x` 访问服务器不满足这一条件；开发电脑的 localhost 可用不能证明手机可用。

保持系统局域网运行，推荐：

1. 内网服务器提供 HTTPS；证书覆盖实际访问的域名或 IP，手机信任证书链。
2. 严格离线、受管设备场景使用内部 CA 签发证书，在手机安装并信任根证书，逐台验证目标浏览器。
3. 前端与 `/api` 使用同一个 HTTPS 入口；服务器内部转发到现有后端，避免 HTTPS 页面请求 HTTP 接口。
4. 检查站点摄像头权限策略与浏览器权限。只修改网址前缀或忽略证书警告不能替代部署验收。
5. 检查打印设置中的前端基址，新增链接标签使用实际可访问的 HTTPS 地址；既有标签按第 4 节处理。

截图未显示完整访问地址，现网协议、证书和浏览器兼容性尚未确认，不能凭截图认定已经满足条件。

原部署文档需要在实施时纠正两处表述：网页内扫描纯工单号也需要摄像头 HTTPS 条件；系统相机扫描网址再打开网页，与网页自己调用摄像头是两条不同流程。另外，旧文档中的 `/#/report` 示例应与实际 H5 路由 `/#/h5/report` 对齐。

## 7. 故障体验

| 状态 | 处理 |
|---|---|
| 非安全访问地址 | 明确提示摄像头需 HTTPS，仍可手动输入或用扫码枪 |
| 未授权/拒绝授权 | 提示在浏览器设置中允许摄像头，提供重试 |
| 用户一直未处理权限弹窗 | 保持可取消状态，允许切换输入方式，避免页面锁死 |
| 无摄像头、被占用、浏览器不支持 | 显示可读原因，提供重试和手动输入 |
| 非工单二维码 | 提示扫描本系统工单二维码，允许重新扫描 |
| 工单不存在、无权限、接口失败 | 保留业务错误信息及明确返回扫码的入口，不用默认数据继续执行 |
| 切换页面/后台 | 停止视频流和识别，回到前台可重新启动 |

错误遵循项目异常规约，不空 catch、不伪装成功；诊断保留操作位置和错误类型，不展示令牌或完整敏感内容。

## 8. 实施和验收结论

先检查实际手机的 HTTPS 与摄像头环境，再完成前端扫描、二维码解析、PDA 回归和真机测试。环境暂时不具备时可以完成独立开发与本地验证，但必须将真机项标为待验收，不能宣称手机功能已交付。

验收以真实手机扫描真实打印标签为准，至少覆盖用户实际浏览器、安卓常用浏览器和 iPhone Safari（如交付包含 iPhone），并记录设备、系统、浏览器版本和证书状态。电脑模拟手机尺寸不能替代真机测试。
