# 96-开发指令-多租户MCP每厂一把Key定厂

> 交付对象：Cursor（写代码）。本文是开发指令，不是代码。
> 背景知识：先读 `docs/02-数据字典.md` 的 `sys_factory`、`docs/35-MCP上线待办清单.md`、`docs/40-扣子重搭重接MCP并发布微信网页.md`。

---

## 一、需求背景（人话，先说清楚为什么改）

**现状**：现在这套系统是「一套部署管一个厂」。每个厂独立部署一份后端，配置里写死 `Mcp:FactoryId=1`，所有 MCP 工具查的就是这个写死的厂。全系统共用一把 `Mcp:Token`（现在演示值是 `laohu-demo-2026`）挡公网乱调。

**要改成的目标**：多个厂共用一个数据库、共用一个域名（如 `https://mes.webok.net:11302`），每个厂各发一把自己的钥匙（API Key）。扣子上给每个厂各自注册一个 MCP 连接、各带各的钥匙。服务端根据请求带来的钥匙判断「这单活是哪个厂的」，只查该厂数据，绝不让 A 厂查 B 厂。

**为什么不能像现在这样**：现在全厂共用一把 Token + 配置写死厂，一旦共库，谁都能用一个 Token 串到别的厂。所以必须「每厂一把钥匙、按钥匙定厂」。

---

## 二、三条铁律（任何步骤不得违反）

1. **厂身份以「钥匙」为准**：请求里哪怕带了 `factoryid` 标签，也只是对账用的备注，**绝不**用它直接定厂。定厂只看钥匙。钥匙对不上就 401，不猜、不放行。
2. **钥匙只存哈希，不存明文**：数据库里存 BCrypt 哈希。谁拿到数据库也解不回原钥匙。
3. **所有查询强制带 factory_id**：现有各业务查询已带 `factory_id`，保持不破坏；MCP 查询工具查到的厂，必须是「当前请求钥匙」对应那个厂。

---

## 三、要做的步骤（原子步骤 + 条件判断）

### 步骤 1：建表 `sys_mcp_key`（存每厂钥匙的登记簿）

执行这段 SQL Server DDL：

```sql
CREATE TABLE sys_mcp_key (
    key_id       BIGINT IDENTITY(1,1) PRIMARY KEY,
    factory_id   BIGINT NOT NULL,          -- 所属工厂（账套），关联 sys_factory.factory_id
    key_alias    NVARCHAR(64)  NOT NULL,   -- 钥匙别名，如「五金厂-老板专用」，日志/页面只显示它
    api_key_hash NVARCHAR(255) NOT NULL,   -- 钥匙的 BCrypt 哈希，绝不存明文
    status       TINYINT NOT NULL DEFAULT 1, -- 1=有效 0=已吊销
    expire_at    DATETIME2 NULL,           -- 有效期；NULL=长期有效
    created_at   DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    remark       NVARCHAR(255) NULL
);
CREATE INDEX ix_mcp_key_factory ON sys_mcp_key(factory_id);
```

**条件判断**：
- 当 `sys_mcp_key` 表不存在 → 执行上面的 DDL 建表；
- 当表已存在 → 跳过，不重复建；
- 建完用 `SELECT COUNT(*) FROM sys_mcp_key` 验证返回 0（空表），才算建好。

### 步骤 2：PC 后台做「钥匙管理」页（生成 / 吊销 / 重发）

给管理员加一个管理入口，对每个厂发钥匙、吊销钥匙。每个动作如下：

**2a 生成钥匙（给某厂发一把）**
1. 管理员选厂（下拉选 `sys_factory` 的厂）；
2. 点「生成」→ 系统用加密随机数生成一串 32 位随机钥匙（大小写字母+数字，如 `X9kq2T7pLm3ZvRw8…`）；
3. 系统把这把钥匙做 **BCrypt 哈希**存入 `sys_mcp_key.api_key_hash`，绑定该 `factory_id`，`status=1`，`key_alias` 可填「厂名-用途」；
4. 页面**只显示一次**明文钥匙，提示「请立即复制发给客户，关闭后不再显示」；
5. 落一条操作日志（含厂名、别名、时间，**不打明文钥匙**）。

**条件判断**：
- 当管理员没选厂 → 提示「请先选择工厂」，不生成；
- 当生成成功 → 显示明文一次 + 写日志；
- 当系统异常 → 报「生成失败：具体原因」，回滚不落脏数据。

**2b 吊销钥匙**
1. 管理员找到某厂某把钥匙 → 点「吊销」；
2. 把该行 `status` 改成 `0`；
3. 立刻生效：以后带这把钥匙来调用，一律 401。

**2c 重发（客户说钥匙泄露了）**
- 先吊销旧钥匙（走 2b）→ 再走 2a 生成一把新的发给客户。旧钥匙立即失效。

**条件判断**：
- 当钥匙已在用且要吊销 → 先提示「吊销后客户立刻连不上，确认吗」，确认才执行；
- 当吊销成功 → 写日志（厂名、别名、时间）。

### 步骤 3：改造 `McpTokenMiddleware`（核心：按钥匙定厂）

现在它只比对一把 `Mcp:Token`，改成「查 `sys_mcp_key` 表定厂」。逻辑如下：

1. 取请求头 `Authorization: Bearer <钥匙>`；
2. **当**没有钥匙 → 直接 401；
3. **当**有钥匙 → 加载所有 `status=1 且未过期` 的钥匙（厂不多，可放内存缓存），对每一把用 **BCrypt.Verify(请求钥匙, 该行哈希)** 比对：
   - **当**有一把命中 → 记下该行的 `factory_id` 和 `key_alias`；
   - **当**全部不中 → 401；
4. 命中后，把 `factory_id` 和 `key_alias` 写入「当前请求上下文」（见步骤 4），供后面的 MCP 工具读取；
5. 保留现有的 `Mcp:Token` 作为**总开关兜底**：**当**请求钥匙等于 `Mcp:Token`（管理员万能钥匙）→ 用配置的 `Mcp:FactoryId` 定厂（仅限管理员排障用，演示/测试默认不开启，`Mcp:Token` 留空则此项关闭）；
6. 记录日志：`key_alias`、定的厂、请求路径、来源 IP、时间。**绝不打明文钥匙**。

**条件判断汇总**：
- 当无钥匙 → 401，日志记「未带钥匙」；
- 当钥匙查不到 / 已吊销 / 已过期 → 401，日志记「钥匙无效：{别名或哈希前缀}」；
- 当钥匙命中 → 放行并把厂写入上下文；
- 当 `Mcp:Token` 未配置 → 万能钥匙项不启用，不报错。

> 注意：`BCrypt` 只能「给明文 + 某条哈希 → 判是否匹配」，不能反查。所以采用「遍历有效钥匙逐一 Verify」的方式，厂数量少性能可接受。这个比「按厂索引」更简单，符合简洁优先。

### 步骤 4：新增「当前请求厂上下文」服务

新建一个 Scoped 服务（如 `IMcpRequestContext`），里面只放两个属性：`long CurrentFactoryId`、`string KeyAlias`。

- 步骤 3 的中间件在钥匙命中后，给这个上下文赋值；
- 各 MCP 工具通过构造函数注入它，读取「当前这个请求」是哪个厂。

**条件判断**：
- 当 MCP 工具被调用且上下文里已有 `CurrentFactoryId` → 用它；
- 当工具被调用但上下文没有 `CurrentFactoryId`（绕过了中间件直接调，异常场景）→ 抛错「MCP 缺少租户上下文，禁止查询」，绝不默认用 0 或 1 兜底。

### 步骤 5：改 7 个 MCP 工具，取厂方式从「配置」换成「上下文」

现有文件：`WorkOrderMcpTools.cs`、`ReportMcpTools.cs`、`SalaryMcpTools.cs`、`ScheduleMcpTools.cs`、`KnowledgeMcpTools.cs`、`AuthMcpTools.cs`（Auth 也改成用当前请求厂，不要再写死 `Mcp:FactoryId`）。

改法统一：把

```csharp
long factoryId = _config.GetValue<long>("Mcp:FactoryId", 1);
```

换成从 `IMcpRequestContext` 取 `CurrentFactoryId`。

**条件判断**：
- 当工具里原来读 `Mcp:FactoryId` → 全部改成读上下文；
- 当上下文没有厂 → 抛错（同步骤 4），不查询；
- 当改完 → 每个工具必须重新编译 + 走一遍自测（见「四、验证清单」），不能只改一两处。

### 步骤 6：SQL 隔离兜底（确认，不是新建）

各业务 Service 里的查询本已强制带 `factory_id`（数据字典里各表都有该字段）。**验收要求**：确认步骤 5 改完后，7 个 MCP 查询工具最终落到 SQL 时都带上了「当前请求厂」的 `factory_id`。**当**发现哪个查询漏了 `factory_id` → 补上，禁止无厂裸查。

### 步骤 7：扣子（Coze）连接配置模板（给客户/给管理员照抄）

每个厂一个 MCP 连接，区别只在 `Authorization` 的钥匙不同。模板：

```json
{
  "mcpServers": {
    "workshop-五金厂": {
      "type": "streamable-http",
      "url": "https://mes.webok.net:11302/mcp",
      "headers": {
        "Authorization": "Bearer <五金厂的钥匙>"
      },
      "disabled": false
    }
  }
}
```

- 五金厂填五金厂的钥匙，川菜馆填川菜馆的钥匙；
- **`factoryid` 键可以不写**：厂身份由钥匙决定，写 `factoryid` 也只当对账备注，服务端不靠它定厂（见铁律 1）。**当**客户坚持要写 → 写也行，但服务端必须校验「标签与钥匙定的厂一致，不一致拒绝」。

**条件判断**：
- 当 `Authorization` 缺钥匙或钥匙错了 → 连接后调用一律 401；
- 当钥匙正确 → 只查得到本厂数据。

### 步骤 8：日志与「一键关闭」（生产要求）

1. **日志完整、不脱敏**：MCP 每次调用记 `key_alias`、定的厂名、路径、来源 IP、时间、成败。异常必须带上下文（走现有 `Common/ThrowHelper.cs`），不吞异常。**唯一例外**：明文钥匙永不落日志/页面。
2. **一键关闭**：现有 `Mcp:EnableMcp`（`appsettings.json`）已是总开关。**当**设为 `false` → `/mcp` 整段不注册，所有 MCP 调用立即不可用（紧急关闭用），不影响 `/api` 正常网页。

## 四、验证清单（做完逐项打勾，全过才算完成）

1. **建表**：`sys_mcp_key` 建出来，空表。
2. **发钥匙**：后台给「五金厂」生成一把，明文只显示一次，库里存的是哈希不是明文。
3. **A 厂隔离**：扣子里配「五金厂」连接（带五金厂钥匙）→ 查工单 → 只返回五金厂的工单。
4. **B 厂隔离**：再配「川菜馆」连接（带川菜馆钥匙）→ 查工单 → 只返回川菜馆的，**绝不出现五金厂数据**。
5. **无钥匙**：直接调 `/mcp` 不带钥匙 → 401。
6. **错钥匙**：随便编一把 → 401。
7. **吊销**：吊销五金厂钥匙 → 再用它调 → 401；重发新钥匙 → 能进。
8. **串租户测试（最狠一条）**：用五金厂钥匙，强行在请求里塞 `factoryid=川菜馆` → 必须**拒绝**（因为标签与钥匙定的厂不符），或至少仍只返回五金厂数据。绝不返回川菜馆数据。
9. **过期**：配一把带 `expire_at` 且已到期的钥匙 → 401。
10. **日志**：以上每次调用在日志里有 `key_alias` + 厂名 + 路径 + 时间；日志里**搜不到明文钥匙**。
11. **一键关闭**：`Mcp:EnableMcp=false` 重启 → `/mcp` 调不通，网页 `/api` 正常。
