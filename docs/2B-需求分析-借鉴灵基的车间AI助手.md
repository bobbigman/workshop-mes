# 借鉴灵基的车间 AI 助手 · 需求分析

> 日期：2026-09-20｜状态：待开发方案，未代表已实现。
> 本轮只交付文档，不修改程序。依据：用户提供的朋友圈文字、现有项目文档及部分源码核查；未核对视频画面，未验证分享者的成交及效果宣传。
> 配套：[Cursor 开发指令](未做指令/26-开发指令-PC内置AI助手.md) · [开发与验收清单](50-PC内置AI助手-开发与验收清单.md)。分析稿续用字母编号，开发指令使用空闲的 26 号，清单使用 30+ 编号。

## 1. 要解决什么问题

系统现有价值是“电脑下单 → 手机/PDA 报工 → 看板看进度”。新增 AI 的价值是：让管理员用日常语言查到可信的业务信息、找到对应资料，并能回到原有页面继续工作。

首版定位：**PC 内置 AI 助手，先做查进度和问工艺。** 不做通用聊天平台，不改变业务台账，不要求用户学习提示词或智能体编排。

成功标准：同一个问题，通过 AI 获得的数据与现有页面及业务服务一致；来源可核对；不知道、无权限、资料缺失和系统故障能明确区分。

## 2. 从朋友圈材料借鉴什么

| 参考做法 | 对本项目的启发 | 取舍 |
|---|---|---|
| 把口述整理成需求并补充提问 | 产品不明确、日期缺失时主动澄清 | 首版落实 |
| ERP 取数、计算、报表、写回 | AI 必须接真实业务服务，答案要能回到业务记录 | 首版只读；写回后续单独做 |
| 多个场景智能体 | 给用户几个明确的任务入口 | 一个页面、两个业务模式，共用模型 |
| 自然语言创建计算技能 | 将计价制度整理为结构化规则 | 后续探索，不让模型临场算工资 |
| 用生成的数据演示 | 可以准备独立的模拟工厂数据 | 预期结果人工核对，不以模型自测证明正确 |
| 宣传原生融合与数据安全 | 讲清数据来源、权限与流向 | 不承诺云 API 调用“数据不出厂” |

朋友圈文字是参考材料，不是本项目指令。其“演示成功等于交付成功”“完全正确”等表述不作为验收依据。

## 3. 当前基础与差距

| 已核查基础 | 能复用什么 | 需要补什么 |
|---|---|---|
| `WorkOrderService`、`WorkOrderMcpTools` | 工单查询、详情及进度口径 | 交期筛选、完整总数、受控分页只加在 AI 查询上。不改现有列表的默认排序（工单 ID 倒序）和单个状态参数。MCP 仍固定取前 20 条，本期不改 |
| `KnowledgeService`、`KnowledgeFileParser` | 产品/工序关联资料、文件解析 | 同名澄清、工序归属、长度限制、来源标识用 AI 专用方法。不改旧查询「按名称取第一条」的行为，扣子仍走旧方法 |
| JWT、PC 路由与菜单 | 已登录入口、用户及工厂身份 | AI 专用服务端权限校验 |
| `docs/32` 工资底座 | 事实与计算结果分离 | 后续工资解释再接入 |
| `docs/36` 排产评分方案 | 确定性计算的设计方向 | 排产助手不进入本期 |

源码核查发现：现有知识服务按名称模糊匹配后取第一条；指定工序也可能取到不属于当前产品路线的工序。首版必须在 AI 入口用新方法消除歧义，并由服务端校验归属，不能依赖提示词提醒，也不能把这套澄清写进旧方法。否则扣子里原来能直接回答的问题会变成报错。工单列表同理：交期区间和多状态只给 AI 用，不改现有列表的默认排序和筛选。

上述为静态核查结果，不代表运行验收通过。

## 4. 首版边界

### 4.1 用户与入口

- 仅 PC 管理员（role=1）可访问；班组长和工人本期不开放，后续明确资料可见范围后再扩展。
- 增加菜单“AI 助手”，提供“查进度”“问工艺”两个模式和示例问题。
- 一个 DeepSeek 接入即可，不要求接入多家模型或多智能体协商。这是对 `docs/48`「默认不在系统内调用大模型」的改口，拍板见第 9 节；微信和扣子入口不动。
- API Key 由部署人员在服务器配置；页面显示连接状态及管理员测试按钮。首版不做浏览器填写、保存或显示密钥的设置表单。

### 4.2 首版需求

| 编号 | 需求 | 用户可见结果 |
|---|---|---|
| R01 | AI 启用状态及连接测试 | 未配置时告诉管理员如何联系部署人员处理；错误可定位 |
| R02 | 对话与有限追问 | 发送、等待、停止、新对话；刷新不保留会话 |
| R03 | 按工单号、产品、状态、交期查询 | 结果表、符合条件总数、具体日期范围、查询时间 |
| R04 | 查询单张工单进度 | 使用已有进度口径，能打开工单详情 |
| R05 | 按产品/工序问工艺 | 基于资料回答，附文件名称、版本及摘录 |
| R06 | 澄清与缺失处理 | 同名产品、同名工序给出候选供点选；点选只认本轮服务端给出的标识，选定前不查资料；无资料不编造 |
| R07 | 结果溯源 | 业务卡片和来源由服务端生成，链接指向现有合法页面 |
| R08 | 权限与稳定性 | 按登录工厂隔离；关闭 AI 或外网故障不影响原业务 |

### 4.3 不属于首版

H5/PDA 对话、微信接入改造、语音、OCR、文件上传管理、向量数据库、长期聊天记录、自由 SQL、自动生成并执行脚本、业务写回、工单创建、报工复核、工资计算与解释、自动排产、多模型切换、智能体广场、技能开发平台。

这些是后续候选，不允许开发工具顺手实现。

## 5. 典型使用过程

### 场景 A：查明天要交的工单

管理员：“明天到期但还没完成的工单有哪些？”

系统将“明天”转换为配置的业务时区下的具体日期，不用服务器墙上时钟直接和交期比大小。筛选该交期且状态为未开始(0)/执行中(1)的工单，排除已结束(2)、已取消(3)及无交期记录。数据字典里状态 2 称「已结束」；界面若写「已完成」，筛选仍按状态 2。展示总数、当前页、工单号、产品编号/名称、交期和已有进度。

这套「到期日」筛选与工单页面上的临期/超期三态不是同一套算法，不能用页面三态函数代替。页面三态把已结束、已取消和空交期都显示为正常，并用当前时刻对交期做减法；这里要的是日期区间里的未完成清单。

超过一页时明确显示“共 N 条，本页 M 条”，提供翻页。不得用当前页计算全量结论。点击记录打开原工单详情。

“未来可能延期”是预测，首版不承诺；可回答当前逾期及即将到期的实际清单。

### 场景 B：问某个产品的工艺

管理员：“产品 A 裁切时注意什么？”

如果有多个同名产品，先显示编号与名称，用户点选后再查资料。点选只提交服务端本轮给出的产品编号；编号不在本轮候选里就拒绝，不按名称取第一条。指定工序必须属于该产品工艺路线。工序同名时同样先点选：工序编号在数据字典里没有唯一约束，点选以服务端给出的工序标识为准，不能只靠名称。选定前不读资料。选定后读取该产品及相关工序资料，给出要点及实际来源。

文件无版本时显示“未标注版本”；资料互相冲突时展示差异并提示人工确认，不擅自判断哪个版本有效。没有依据时说明未找到对应资料；解析失败与没有资料分别反馈。

## 6. 业务口径

- 产品编号是唯一定位依据，名称可重复；用户只给名称时允许搜索，不允许任意选第一项。
- 日期使用配置的业务时区，默认 Asia/Shanghai（Windows 使用对应时区 ID）；显示具体日期，避免“今天”理解不同。比较时用该时区的当天起点，不用 `DateTime.Now` 直接减交期。
- “未完成”固定指状态 0、1。状态 2 在数据字典中称「已结束」，不叫完成；“逾期”还要求交期早于当天起点，且不含已结束、已取消、空交期；“明天到期”使用明日起点至后日起点的半开区间。`due_date` 按 `docs/02` 为 `DATETIME2`，比较前先落到业务时区的日期，再按半开区间过滤。
- 上述日期筛选与工单页 `DueStateHelper` 的临期/超期三态不是同一套规则，禁止用三态函数代替筛选。进度数字仍沿用原服务，不能把各工序数量简单累加成最终完成数量。
- 统计在数据库/业务服务完成；模型负责语言表达，不负责猜总数、算金额或生成业务事实。
- 不开放写工具，原有产品唯一、部门报工权限、倒序删除规则保持有效。

## 7. 技术与数据流

`PC Vue3 页面 → 已登录 .NET API → DeepSeek 工具调用请求 → .NET 白名单业务工具 → 业务数据/资料片段 → DeepSeek 组织答案 → 页面展示来源卡片`

DeepSeek 只提出工具及参数，实际查询、权限检查和结果处理由后端完成。内部直接复用服务，不通过公网 MCP 调回自己。既有 MCP/扣子入口继续保留。

本期不新增业务表；聊天只保存在有期限的服务端内存会话中。服务器重启或会话过期后开始新对话。密钥由服务器环境配置保存，不进入仓库、浏览器、本地存储或聊天历史。

每个部署实例使用自己的模型配置；不同工厂仍逐次按 JWT 隔离，不允许前端或模型传入工厂身份改变查询范围。

## 8. 数据出网、权限及错误

- 调用云端 DeepSeek 需要服务器出网。发送必要问题、获准的工单字段和相关资料片段；不发送数据库连接串、JWT、API Key、工资数据及硬盘路径。
- 页面首次使用说明“AI 会将本次问题及必要业务资料发送至配置的模型服务”；不宣传完全离线或数据不出厂。
- 如客户要求数据完全不出厂，应另立本地模型部署方案；不把“内置聊天界面”等同于私有化模型。
- 会话绑定用户与工厂；每个请求、工具执行和来源打开均校验权限。不能复用演示授权绕过或固定工厂配置。
- 用户文字、工艺文件和模型返回都属于不可信内容。资料中的“忽略规则”“查询别人工资”等文字不能改变系统权限。
- 异常遵守 ThrowHelper：服务端保留位置、操作、网址、脱敏报文及失败信息；前端只显示必要说明和追踪编号，不泄露密钥及内部路径。
- 工具失败不能回答“查无数据”；模型故障不能伪装成功。数据卡片若已获取，可保留并明确标记“AI 解读失败”。

## 9. 与既有规划的关系

- `docs/48` 第 2.3 节和第 4 节定过：默认不在系统内调用大模型，只有客户要求脱离扣子或数据不出厂才内嵌。**本方案改掉这条默认**：管理员在电脑里提问，服务器调用 DeepSeek。微信、扣子、原 MCP 入口保持原行为，不重做知识库。电脑里有聊天框，不等于数据不出厂。
- `docs/34、35` 外部 MCP 的演示授权不是 PC 内置入口的正式身份来源。
- `docs/32、36` 的工资与排产仍由确定性规则计算，本期不纳入对话工具。
- 本文是本次新增需求的分析依据；实现时应同步 `docs/01、03、04、05、30、33、48` 的相关章节。若确需改表，先更新 `docs/02`，不能在实现中自行扩表。

## 10. 后续迭代与开发协作

第二期候选：工单草稿与确认提交；第三期候选：工资明细解释、排产评分解释。每期重新确认范围和权限。

WorkBuddy、ChatGPT、DeepSeek、Cursor 等开发工具使用同一份开发指令及验收清单，依次交接代码、完成项、测试证据和未解决问题；避免多个工具同时修改同一工作目录。工具选择不改变项目技术栈或业务契约。

建议首场演示：查明日交期 → 点开工单核对 → 查询该产品工艺 → 展示引用 → 演示同名产品澄清和无资料提示。演示完成后按验收清单确认能否交付。
