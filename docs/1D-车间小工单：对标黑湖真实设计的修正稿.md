# 车间小工单：对标黑湖真实设计的修正稿

> **版本：** v1.1
> **变更：** v1.1 以黑湖官方原文（xiaogongdan.cn）逐字核对，纠正第三方站（xiaogongdan.tech）混入的脑补细节，并标注每条结论的**证据等级**。
> **定位：** 对 1C「预警、查看与复核 Use Case 分析」的对标纠偏。1C 的方向（把查看做成管理动作）对，但**对标黑湖时扒漏了、也脑补了几处**。本文以黑湖官方公开资料为准，把 1C 的偏差逐条纠正，并补齐 1C 漏掉的两条主线。
> **参考：** 1A / 1B / 1C；黑湖官方原文 `xiaogongdan.cn`（官方，可信）；`xiaogongdan.tech`（第三方 SEO 站，仅作参考、不采信细节）。
> **证据等级约定：** 🟢=官方原文实锤；🟡=官方原文有、但口径不完全一致；🔴=仅第三方站，官方无据。
> **一句话结论：** 黑湖的"查看—复核"闭环，主线是 **建单 → 派工 → 报工 → 复核 → 入库/算薪**，1C 漏了"派工"，漏了"工人一键上报异常"，且把"复核"的语义误读为卡进度。

---

## 一、黑湖的真实流程主线（1C 需要修正的骨架）

```
计划员建单 → 班组长派工 → 工人扫码/选任务报工 → 班组长复核 → 进度/工资/报表
     │              │                    │                │
     │              │              └── 进度看板【实时】更新（厂长/计划员立刻可见）
     │              │                                │
     │              └── 派工后工人手机收到任务提醒      └── 复核确认后才进【统计 + 计件工资】
     └── 工单设【交期】，系统算临期/超期预警
```

**1C 的骨架问题：** 1C 写的是"建单 → 报工"，把"派工"整段跳过了。而黑湖里**班组长最日常的两个动作是"派工"和"督促报工"**，复核只是其一。跳过派工，等于把班组长的角色砍掉一半。

## 二、逐条纠偏（1C 错在哪，黑湖真实是啥）

### 纠偏 1：漏了「派工」 🟢

| 项 | 1C | 黑湖真实（官方原文） |
|---|---|---|
| 派工环节 | ❌ 无（UC 清单里没有派工） | ✅ 班组长把工序任务派给具体工人（手机拖拽/点选）；派工后工人手机收到任务提醒；急单插单可调优先级并推通知 |
| 工人接任务 | 1C 只写"扫码报工" | 黑湖工人先"接任务"，再从任务里扫码/选工序报工 |

> 官方原文："班组长……将工单的各道工序派给具体的操作工或班组……派工完成后，工人端会收到任务通知，知道自己当天要做什么。"（`xiaogongdan.cn/article/xiaogongdan-operations-guide.html`）

**修正：** 新增用例 **UC-13 班组长派工**（派工到人、调优先级、工人收任务提醒）。

### 纠偏 2：漏了「工人一键上报异常」 🟢

| 项 | 1C | 黑湖真实（官方原文） |
|---|---|---|
| 异常来源 | 全系统被动算（超期、停滞、报工异常） | 异常主要由**工人主动一键上报**：**设备故障、物料短缺、质量异常**；自动通知机修/仓库/生产负责人 |
| 看板异常 | 系统高亮 | 工人上报后，看板**红色高亮 + 滚动播报**，同步推给班组长、生产主管 |

> 官方原文："如果遇到设备故障、物料短缺或质量异常，工人可以直接在手机上发起异常上报，拍照上传并描述问题，车间主管和管理层会实时收到提醒。"（`xiaogongdan.cn/news/xiaogongdan-mobile-login-guide.html`）
>
> ⚠️ **注意：** 官方原文只说了"**设备故障 / 物料短缺 / 质量异常**"三类；网上第三方站（xiaogongdan.tech）写的"缺料停工、设备故障、来料不良、工序报废"四类，**官方无据，不采信**。异常类型枚举以官方三类为准。

**修正：** 新增用例 **UC-14 工人上报停机/异常**。这是黑湖"让数据主动找人"的核心机制——**人主动说"为什么停"，而不是系统猜"是不是卡住了"**。

### 纠偏 3：误读「复核」语义（双轨，不是卡进度） 🟡

| 项 | 1C | 黑湖真实（官方原文） |
|---|---|---|
| 报工后进度 | "班组长复核后数据才生效"（卡进度） | **报工提交 → 进度看板实时更新**（厂长/计划员立刻看到这道工序做了多少） |
| 复核卡什么 | 1C 说卡进度、卡工资 | 复核只卡**生产统计 + 计件工资核算**（"报工—复核—入库"闭环） |

**修正：** 黑湖是**双轨**——进度实时可见，账目复核后才定。1C 把复核当成卡进度的闸门，比黑湖严了半档，会伤到"厂长实时看进度"这个核心价值。

> **逐字核对结果（官方两篇口径不一致）：**
> - 文一《从建工单到报工看板的核心流程》原文："报工后，工单进度自动更新，产量数据**用于工资核算和报表**"——**通篇没有"复核"二字**，报工直接进工资。
> - 文二《手机端使用指南》原文："班组长……逐一复核报工数据的准确性，**确认无误后数据才会正式进入生产统计和工资核算流程**"——明确有复核。
> - **判断：** 进度实时可见两篇一致（🟢 实锤）；"工资走不走复核"两篇打架。文一是概览类文章做了简化，文二是功能详解更可信，**采纳文二的"报工→复核→入库"**。故本处标 🟡（进度实锤、工资口径官方有分歧）。

### 纠偏 4：自创「工序停滞预警」——黑湖没有这种机制 🟢（反证）

| 项 | 1C | 黑湖真实 |
|---|---|---|
| 工序卡住怎么预警 | UC-06 系统猜"某工序超时没报工" | 黑湖靠**工人主动上报**缺料/设备故障/质量异常；没有"系统按无报工时长猜卡住"的机制 |

**修正：** 1C 的 UC-06「工序停滞预警」是**自己发明的**。系统靠"多久没报工"猜卡住，误报率高、猜不准；黑湖选的是"人主动说为什么停"。**建议撤销 UC-06，其场景并入 UC-14 工人上报异常**（若确需"无报工提醒"作为补充，只能当"督促报工"的软提醒，不叫"停滞预警"）。

### 纠偏 5：交期预警只做"超期"一级——黑湖是"临期 + 超期"两级 🟢

| 项 | 1C | 黑湖真实（官方原文） |
|---|---|---|
| 分级 | 只"超期"一级 | **临期 + 超期** 两级（官方实锤）；预警天数可自定义 |
| 颜色状态 | 只红色 | **正常 / 预警 / 延期** 三态用颜色区分（官方原文，非五色） |
| 列表分 Tab | 无 | 官方未详述；"未开始/执行中/临期/超期/今日完成"是第三方站写法，**官方无据** |

> 官方原文（临期+超期实锤）："老板打开手机 App，首先看到的是**临期和超期工单的数量和详情**——哪些订单快要到交期了还没完工、哪些已经超期、卡在哪道工序。"；"生产进度看板以工序流转状态为横轴，用不同颜色标识**正常、预警和延期**三种状态。"（`xiaogongdan.cn/news/xiaogongdan-mobile-login-guide.html`）
>
> ⚠️ **注意：** "灰/蓝/绿/黄/红"五色、"3 天内到期"具体天数、五大看板板块，均来自第三方站 `xiaogongdan.tech`，**官方原文没有**，故不采信。官方实锤的只有：临期+超期两级、三态颜色（正常/预警/延期）。

**修正：** UC-04 由"超期预警"升级为"**交期预警（临期 + 超期两级）**"。

## 五、新增/修正的详细用例（只写关键的几个）

### UC-13 班组长派工（新增）

- **范围：** 车间小工单
- **主要参与者：** 班组长
- **触发：** 计划员建单后，班组长打开工单派工。
- **主成功场景：**
  1. 班组长在手机端进入工单，看到工序任务列表。
  2. 选择某工序，指定执行工人（点选/拖拽）。
  3. 派工后，工人手机收到任务提醒。
  4. 急单插单：班组长调整任务优先级，系统自动向被调整工人推送通知。
- **后置条件：** 工序任务已派到人，工人端可见。
- **业务规则：** 派工到人；任务提醒实时推送（试用期走系统内，正式期可接企业微信）。

### UC-14 工人上报停机/异常（新增，黑湖核心） 🟢

- **范围：** 车间小工单
- **主要参与者：** 工人、班组长
- **触发：** 现场设备故障、物料短缺、质量异常（官方三类枚举）。
- **主成功场景：**
  1. 工人手机一键选择异常类型（**设备故障 / 物料短缺 / 质量异常**），拍照上传 + 描述问题。
  2. 系统自动通知对应负责人（物料短缺→仓库、设备→机修、质量→质检/生产主管）。
  3. 看板红色高亮 + 滚动播报，车间主管和管理层实时收到提醒。
  4. 正式期可推企业微信给班组长、生产主管。
- **后置条件：** 异常已上报并通知到人，处理可跟踪。
- **业务规则：** 上报留痕；处理结果可回填（谁处理、何时恢复）。

### UC-04 交期预警（修正：临期 + 超期两级） 🟢

- **主成功场景（改）：**
  1. 工单设「计划交期」（计划员建单时录入）。
  2. 系统按交期 + 可配置预警天数计算：临期、超期两级；看板用「正常/预警/延期」三态颜色区分。
  3. 临期/超期进入相关责任待办，正式期可聚合推送。
- **业务规则：** 预警天数可配置；临期、超期两级（官方实锤）；"3 天内到期"的具体天数官方无据，本项目落地时自行拍板。

### UC-02 班组长复核报工（修正语义）

- **核心修正：** 报工提交后**进度看板实时更新**；班组长复核确认后，数据才进入**生产统计与计件工资**。
- 复核动作本身不变：按工单、按工人核对产量、良品、不良，可退回修改。

| # | 黑湖真实有 | 本项目现状（事实） |

## 七、一句话总结

**1C 的"把查看做成管理动作"这个洞察是对的；但它对标黑湖时，漏了"派工"和"工人一键上报异常"两条主线，误读了"复核"（黑湖是卡入账、不卡进度可见），并自创了黑湖没有的"工序停滞预警"。本修正稿以黑湖公开资料为准，把这些纠正为：建单 → 派工 → 报工 → 复核（双轨）→ 交期两级预警 + 工人主动上报异常。**
