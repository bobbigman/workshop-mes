# 100-开工单-MCP多租户钥匙与认人三连（96/97/99）

> 交付对象：Cursor。开工前先读本开工单，再按序读 docs/96、docs/97、docs/99 三份指令。
> 用途：把"钥匙锁厂 + 手机号认人 + WorkBuddy 专用钥匙"三件事一次理清，按正确顺序开工，避免冲突。

---

## 一、三份是什么关系

| 指令 | 干什么 | 依赖 | 改动面 |
|---|---|---|---|
| docs/96 | 钥匙锁厂（每厂一把 Key 定厂） | 无 | 大：建表 sys_mcp_key + 改 McpTokenMiddleware + 改 7 个 MCP 工具取厂方式 |
| docs/99 | WorkBuddy 专用钥匙（简版） | 96 之后 | 小：McpTokenMiddleware 放行再加一把 WorkBuddy 钥匙 + appsettings 加一行 |
| docs/97 | 手机号直绑认人（无短信） | 96 之后 | 中：建 sys_wx_bind + 绑定/解绑/免报工具（不建验证码表） |

> 96 和 99 都改 McpTokenMiddleware.cs 这个文件，所以不能同时乱改，必须先做 96 定型、再做 99 小加。

---

## 二、开工顺序（照这个走，别跳）

```
96（钥匙锁厂，地基） → 99（WorkBuddy 专用钥匙，小加） → 97（手机号认人）
```

为什么这个顺序：
1. 96 先：它是地基。没有"钥匙定厂"，后面认人、专用钥匙都无从谈起；且它把 McpTokenMiddleware 定厂逻辑大改完，避免后续冲突。
2. 99 第二：在 96 定好的中间件上，再放行一把 WorkBuddy 专用钥匙，改动小、能独立验收。
3. 97 最后：认人依赖"厂已定好"（绑定表要带厂、查询要按厂+人），放最后最稳。

## 四、逐份要点 + 验收（简明版）

第 1 步：docs/96 钥匙锁厂
- 要点：建 sys_mcp_key（钥匙哈希，不存明文）；McpTokenMiddleware 按钥匙查表定厂；7 个 MCP 工具从"读 Mcp:FactoryId"改成"读当前请求厂上下文"。
- 验收：五金厂钥匙查→五金厂；川菜馆钥匙查→川菜馆；无钥匙/错钥匙→401；塞 factoryid 标签不符→拒。
- 完成后停一下，跑一遍 96 验证清单，全过再进 99。

第 2 步：docs/99 WorkBuddy 专用钥匙
- 要点：appsettings 的 Mcp 段加 WorkBuddyToken（随机串）；McpTokenMiddleware 放行"原 Token 或 WorkBuddy 钥匙"。
- 验收：WorkBuddy 用新钥匙发查询→真数据；随便编钥匙→401。
- 明确不做：绑厂、工资控制、审计（99 里写死，别加）。

第 3 步：docs/97 手机号直绑认人
- 要点：只建 sys_wx_bind（不建短信表）；`BindWechat(phone)` 本厂手机号直匹；免报/解绑；查询工具认人前置。
- 验收：本厂手机号→绑；外厂/不存在→拒；绑后免报；五金厂钥匙报川菜馆手机号→拒；未绑定不发任何业务数据。
- 明确不做：短信、验证码、发码工具。

---

## 五、端到端验收（三份全做完，最后跑一遍）

1. 锁厂：五金厂钥匙只查五金厂，川菜馆只查川菜馆，塞标签不符→拒；
2. 认人：微信/豆包/扣子报手机号绑一次、之后免报，未绑只提示先绑定、不发数据；
3. WorkBuddy：专用钥匙能查，随机串生效，旧演示 token 仍可用或已轮换；
4. 日志：关键调用有厂+姓名+时间；手机号明文/明文钥匙永不落日志；
5. 一键关闭：Mcp:EnableMcp=false 重启，/mcp 全关，网页 /api 正常。

---

## 六、铁律

- 顺序别跳：96 → 99 → 97，中间件文件谁改完谁交接；
- 涉及加表先备份；
- 钥匙一律随机串，不手写 workbuddy/demo；
- 上线增量包不覆盖服务器 appsettings*.json（docs/59）；
- 每份验收清单全过才算完，缺一项不算。
