## 1. 结论与目标

可以在现有 .NET 8 项目中实现，不改变技术栈，不建数据库日志表。复用 ILogger、统一异常中间件和 ThrowHelper，接入文件日志，并补齐 SQL 参数、外部接口请求/响应和请求追踪信息。

用户目标：运行报错后，服务器目录留下足以排查问题的记录；SQL 错误能看到执行语句和当时的变量值；外部接口错误能看到调用网址、报文和返回结果；超过两周的日志自动清理。

“尽量完整”指保留失败现场中必要且可安全保存的信息，不等于保存密码、访问令牌、无限大小的附件或所有成功请求。日志用于诊断，不替代业务流水、工资核算凭据或审计记录。

## 3. 首版范围与边界

首版覆盖后端请求未处理异常、SQL 命令失败、外部 HTTP 调用失败、响应解析失败、已有捕获并返回失败的代码路径，以及日志初始化之后的启动失败。现有后台任务如有异常，也使用同一出口。

业务校验失败保留 Warning；技术故障使用 Error，导致启动或运行终止的故障使用 Fatal/Critical。用户主动取消通常不算错误；超时仍需记录。不能仅依赖异常类型判断外部调用是不是技术故障。

首版不新增日志查询页面、日志数据库、公网采集平台、浏览器 JavaScript 错误上报接口。PC/H5/PDA 发到后端的失败请求均可追踪；纯浏览器错误、未到达服务器的网络错误不在后端日志覆盖范围内。断电、进程强杀或日志系统初始化前失败不能保证应用日志落盘，应结合主机/IIS日志排查。

## 4. 应记录的字段

### 4.1 公共字段

时间（带时区）、级别、事件类型、实例标识、应用版本、TraceId、请求方法和脱敏后的路径/查询参数、位置、正在执行的操作、错误摘要、异常类型、完整堆栈及内部异常链。

已登录请求增加用户 Id、部门 Id、工厂 Id；有现成业务上下文时增加工单等业务编号。身份取服务端鉴权结果，不能信任客户端传来的用户/部门字段；不可为了写日志额外查询数据库。登录前、启动和后台任务允许身份为空，并明确来源。

TraceId 在请求开始时建立，相关 SQL/HTTP 事件沿用同一值。一次外部调用增加 CallId，一次 SQL 执行增加 CommandId，重试记录尝试序号；同一请求里的多次调用不能混为一个失败。

### 4.2 SQL 错误

记录实际 DbCommand.CommandText、CommandType、超时设置、耗时、参数快照，以及 SQL Server 错误号和可用的状态、严重级别、过程、行号。参数保存名称、DbType/SqlDbType（可用时）、方向、大小、精度/小数位及脱敏后的值；区分 null、DBNull、空字符串和实际文本。

示例：SQL 为 `UPDATE prod_WorkOrder SET Status=@p0 WHERE Id=@p1`，参数为 `@p0=2 (Int32)`、`@p1=123 (Int64)`。不要拼接成“可直接执行的 SQL”，避免误转义和误执行。

EF Core 统一从命令失败拦截点采集，覆盖同步/异步及 Reader/Scalar/NonQuery；查询枚举、SaveChanges、原始 SQL 都要核查。连接打开失败可能没有 SQL，明确记录“命令尚未执行”，不能虚构语句。读取结果/实体映射失败不一定触发命令失败回调，应由上层异常记录说明阶段，不能宣称所有异常都有 SQL。

禁止通过全局 EnableSensitiveDataLogging 无差别公开参数。认证、密钥配置等敏感 SQL 的自动参数名可能只有 @p0，不能只按参数名脱敏；需结合命令涉及的敏感表/列，不能可靠识别时保守隐藏该命令参数值，并标记原因。SQL 文本内嵌的敏感字面量同样处理。二进制/表值参数保存类型、大小、行数等摘要，不无限展开。

### 4.3 外部接口错误

记录脱敏后的完整网址、请求方法、白名单请求头、请求内容类型、请求报文、状态码、响应内容类型、响应报文、耗时、CallId、业务错误码和异常链。

覆盖非 2xx、HTTP 200 但业务失败、超时、连接/DNS/TLS失败、响应读取失败和 JSON/协议解析失败。没有收到响应时记录 `responseReceived=false`，状态码为空，写明阶段与原因；已收到响应头但正文读取失败时保留状态码及读取失败信息。

普通业务 JSON 保留脱敏后的请求和返回。AI 接口沿用现有更严格策略：消息正文、知识资料和内部推理不落盘，以模型、消息角色/数量、工具数量、业务码和安全摘要替代，标记 `bodyOmittedReason`。不能借本功能取消现有隐私约束。上传文件和二进制只记摘要；响应内容不能被日志读取后导致业务再次读取失败。

## 5. 脱敏、大小与异常出口

统一脱敏覆盖 URL 查询参数、请求/响应头、JSON/表单字段、SQL 参数、异常消息和内部异常。至少涵盖 password、pwd、secret、client_secret、corpsecret、token、access_token、refresh_token、Authorization、Cookie、Set-Cookie、API Key、连接串密码及密码哈希，匹配不区分大小写。不能只脱敏结构化字段，却让异常 ToString 再次泄漏原文。

脱敏先于截断；普通请求/响应正文单项默认最多 64 KiB UTF-8，单个 SQL 参数值默认最多 4 KiB。截断必须记录标志、原长度（可确定时）、保留长度和原因；避免在截断 JSON 后再解析脱敏。无法安全解析的未知内容采用保守摘要，不靠完整原文兜底。保留异常链的类型、堆栈与脱敏后的消息。

日志写入器自身失败不能递归写同一个文件出口，也不能替换原始业务异常。运行中写入失败向独立 stderr/已配置的系统日志出口报告，做限频但保留失败状态和恢复事件；部署时确认该出口能被收集。启动时目录不可写应明确启动失败，不能让运维误以为日志正常。

## 6. 文件与两周保留口径

采用兼容 .NET 8 的稳定版 Serilog 文件输出，沿用 ILogger。输出 UTF-8 JSON Lines（每条事件一行），异常换行转义，便于搜索 TraceId。按 UTC 日期滚动，默认每卷 50 MiB，超限续卷；Warning 及以上入文件，避免业务告警与被捕获故障遗漏。正常请求正文不全量记录。

生产目录示例：`D:\MesTrials\client-a\logs\`，文件示例：`mes-error-20260920_001.log`。生产配置使用绝对路径；每个实例独立目录，位于 wwwroot 和发布替换目录之外。服务账号拥有所需读写删除权限；不提供 HTTP 下载入口。

保留口径：按 UTC 日桶保留今天及前 13 天，启动时和之后每小时清理一次。例如 UTC 2026-09-20 运行清理时，保留 09-07 至 09-20，删除 09-06 及更早的文件。这是 14 个日历日口径，不承诺逐条事件精确存满 336 小时；UTC 与中国时间相差 8 小时，运维文档必须说明。

清理按文件名中的日期，不能用“保留 14 个文件”或文件修改时间代替。只处理已校验专用目录的顶层、匹配本系统精确命名规则的日志；不递归，不跟随符号链接/重解析点，不删除当前活动文件、其他实例文件或无关文件。文件占用/权限失败要报告并继续处理其他合规文件，下轮重试。

停机期间不执行应用内清理，下次启动补清；如未来要求停机时也清理，再增加服务器计划任务。Serilog 文件数量保留限制不能提前删掉 14 日内的分卷；本方案以独立按日期清理为唯一保留策略。

## 7. 接口兼容与规约修订

保留现有 `{code,msg,data}`、业务错误码和 HTTP 状态策略，不把本任务扩成全站接口重构。增加响应头 `X-Trace-Id`，跨域时明确暴露该头。

系统技术异常的 `msg` **回传** SQL/报文等异常链 Message（密码/Token 脱敏，不含堆栈），便于电脑/手机前台直接查看排查；完整堆栈仍只写服务器错误日志；追踪号在响应头 `X-Trace-Id` 与服务器日志。业务校验继续给可理解的原有提示。密钥类字段禁止明文回传。

异常不吞；前台可见诊断上下文 + 服务端可按 TraceId 查完整链。执行时同步 docs/06、相关 .cursor/rules 与 docs/33。

## 8. 实施与验收原则

先统一日志、追踪、脱敏和清理，再接入 SQL 与现有外部调用，最后检查捕获后返回失败的遗漏路径。不要在每个 Controller 重复 try/catch。底层记录一次详细事件，上层记录请求失败摘要，通过 TraceId/CommandId/CallId 关联，避免同一异常重复输出多份完整报文。

必须以临时目录、测试数据库和可控 HTTP 测试端点验收，不破坏生产业务数据、不使用真实密钥。执行顺序、改动位置与分阶段验收勾选见文档 24；**SQL/HTTP 采集、清理不误删、并发追踪不串线均为基本交付/验收要求**；无 SQL Server 时对应项标「待验」，不得用 InMemory 冒充已验。本文保留完整方案口径，不在此重复勾选表。
