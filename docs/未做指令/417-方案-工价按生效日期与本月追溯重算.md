# 417 方案：工价按生效日期与本月追溯重算

日期：2026-10-25。状态：方案已保存，未实施。配套开发指令：418。

## 一、目标

管理员调整工序价目表后，可以明确选择新价格从哪天生效，以及是否纠正本月已有报工和工资。正常调价保留历史口径；错价有可预览、可追查的纠正通道。

首版只做PC管理员管理动作，H5/PDA等报工入口共用后端取价逻辑，不增加现场调价页面。不新增用户需要维护的“价格版本管理”“补差单”或审批模块。

## 二、确定的业务行为

**建单价格改为预估，实际工资按报工业务日期的有效工价计算，提交报工时保存完整计薪快照。** 同一张旧工单调价后继续报工，允许前后报工分别使用各自日期有效的价格；已提交记录不会被普通改价悄悄改写。

| 场景 | 首版行为 |
|---|---|
| 正常调价，今天生效 | 新提交且业务日期落入新价格有效期的报工采用新价；已有报工及工资保持原金额 |
| 本月配错价，要从月初纠正 | 选择本月1日，勾选“重算本月受影响工资”，预览并确认后纠正相关报工计薪快照及工资 |
| 有效期内已有工资草稿 | 只重算受影响明细并更新合计，不增加、删除无关工资明细 |
| 有效期内已有已确认工资单 | 预览明确列出；确认后撤回为草稿，重算后须重新确认 |
| 状态为已发放或有可靠关账限制 | 整次追溯操作阻断，不静默跳过；首版不做补发/冲减业务 |
| 只改产量、工时，或普通工资重算 | 继续使用报工已有计薪快照；不得借机改套当前价 |

“生效日期”与“提交日期”不同：补报按最终保存的业务报工日期取价；跨生效日的计时记录首版不自动分摊，按报工日期统一取价，界面写明。

## 三、管理员操作

1. 在价目表提供“调整工价”操作，显示原价格，修改金额/不良扣价，选择生效日期；日期快捷选“今天”“本月1日”。
2. “重算本月受影响工资”默认不勾选。勾选后必须填写原因，日期范围展示为“生效日到本月末”，实际仅处理已存在且落在范围内的记录。
3. 点击预览：显示受影响报工、员工、工资单数量，原金额、新金额、差额，已确认工资单撤回数量，以及逐条阻断原因。零金额差异也展示来源或版本变化，不伪造补发差额。
4. 点击确认一次提交。成功后显示本次结果及待重新确认的工资单；失败整次回滚。预览本身不保存新价、不改有效期、不撤回工资、不改报工。

例：本月100件原价1元、工资100元；从月初改为1.2元，预览为120元、增加20元。管理员确认后生效，原100元依据仍可查询。

## 四、取价与追溯依据

- 调价只改价格数值和不良扣价，不允许同时更换工序、产品范围、计价方式、计价/报工单位、换算、属性条件或收费结构。结构调整仍走资料维护流程，不混进本月调价纠正。
- 建单保存产品与工序的取价事实，包括字段ID、值、类型/单位语义；工资重新取价必须使用本条报工原有的事实，不读取后来修改的产品规格、工序要求或人员归属。
- 对已生成工资的明细沿用其原人员系数；对未生成工资的报工沿用其报工时保存的系数。旧记录缺少可靠系数或取价事实时阻断，不从工资金额倒推，也不拿人员当前系数冒充历史系数。
- 价格按既有规则匹配：本厂、工序、产品专属优先、日期有效；专属缺规格不回通用，缺价不按0价或旧预估兜底。
- 调价纠正保存原快照、改后快照、金额、原因、操作者和批次。报工当前计薪快照可经明确纠正更新，原快照须完整留存在不可改的审计记录中。普通调价不改已有报工快照。
- 内部保留不可变的价格内容版本及其生效分段，避免覆盖同一价表后无法核实历史价格。管理员无需额外管理版本页面。

## 五、范围与约束

首版本月追溯按账套业务时间（当前为Asia/Shanghai）确定本月，按报工日期筛选；不支持往月追溯。支持计件、计时、单笔固定，严格沿用现有金额、单位换算、扣款及舍入公式。计价方式不能由表名或单位文字猜测。

受影响范围按服务器实际匹配结果确定：包含新价开始覆盖原通用价的专属表，不能只查旧PriceListId。对仍被更高优先级专属表覆盖的报工不乱改。已退回报工也要检查其价格依据，避免日后重新通过复核时漏用旧价；不改变其复核状态或计入当前工资。

整次追溯遇到非法计价、缺价、快照损坏、已发放状态、跨厂、周/月工资重复引用等问题则全部阻断，不“能改几条就改几条”。涉及跨月周结工资时，只更新范围内明细，其余明细和系数原样保留。

当前系统“已发放”仅是预留状态，不能宣称已有完整发放或关账识别。首版只处理系统可识别的可撤回工资单，不新增发薪、税务或关账模块；不把“已确认”自动解释为“已发放”。

## 六、现有实现与改动点

当前413规则为建单锁价、报工和工资沿用快照；本方案实施后仅调整为“建单预估/事实基线，报工按日期锁价，明确追溯时可纠正”，不把普通工资重算改为套当前价。

- `OperationPricingService.LockedAsync`与`OperationPriceListService.PreviewAsync(workOrderId=...)`目前直接返回任务锁价，需要改造，不能只改页面日期。
- `SalaryService.RecalcDraftAsync`当前会重新读取人员最新系数，调价专用路径必须隔离，不得顺手改变系数；普通系数重算仍保留既有225规则。
- 现有`ProdReportChangeLog`只保存改数事实，不能假定已经能记录价格快照；需新增专用调价审计持久化，保留既有改数日志语义。
- 当前413没有历史价格版本表；需要内部版本和明确上线基线，不得把当前价冒充此前所有日期的真实历史价格。

## 七、验收标准

1. 旧工单在调价前后报工，分别取得正确日期价格；历史已报记录不因普通保存改价而变化。
2. 本月纠错预览与确认结果相同；100件1元改1.2元得到100→120、差额20。
3. 原始数量、时长、人员系数、工艺事实、复核状态保持不变；已确认工资撤回并停在草稿。
4. 预览无业务写入，提交幂等、并发复核完整；任一错误整次回滚，所有新旧依据可追查。
5. 计时、固定、扣价、换算、系数和舍入均有实际算例测试；跨厂和已发放状态拒绝。

## 八、对标依据与适用边界

SAP薪资追溯重算保留原结果、将差额计入当前工资；Oracle薪资提供独立追溯重算流程并保留历史结果。它们是薪资模块能力，不能声称任意MES默认自动重算整月工资。本项目取其“明确生效范围、受控重算、保留依据”的原则，并按轻量车间管理系统缩小首版范围，不照搬跨期补差或完整发薪闭环。
