> 日期：2026-10-25；状态：方案待实施。

## 一、目标与核心行为

管理员改工价时，明确选择何时生效，以及是否纠正本月已有报工与工资。首版PC管理动作，Vue3 + Element Plus；H5/PDA等现场入口共用后端算法，不新增现场调价页面。

建单价格作为预估，实际工资按报工业务日期的有效工价计算，提交报工时保存完整计薪快照。旧工单调价后继续报工，前后记录可以使用各自日期有效的价格；普通改价不改写已提交报工。

| 场景 | 方案行为 |
|---|---|
| 正常调价 | 生效日期内的新提交报工采用有效新价；已有报工和工资保持原金额 |
| 本月价格配错 | 选择本月1日或本月内生效日，勾选“重算本月受影响工资”，预览后确认 |
| 工资为草稿 | 只更新受影响明细，再汇总全单；无关明细不变 |
| 工资已确认 | 预览列明撤回数量，确认后撤回并重算，停在草稿待重新确认 |
| 工资status=2已发放预留状态 | 阻断整次追溯，不直接覆盖历史工资；首版不交付补差发薪 |
| 普通改数或普通工资重算 | 沿用报工已有计薪快照，不隐式重取当前价；225人员系数规则保持原有独立语义 |

生效日期与提交日期不同：补报按最终保存的业务报工日期取价。跨生效日计时的处理尚待拍板，推荐首版按报工日期统一取价，不自动拆小时；不能把该建议当成已确认规则。

## 二、管理员的一条完整操作流程

价目表列表/详情 → 调整工价 → 输入价格与生效日（快捷“今天”“本月1日”）→ 可选“重算本月受影响工资” → 预览差额与撤回清单 → 确认 → 查看结果和待重新确认工资单。

追溯复选框默认不选；选择追溯时必须填写原因。预览展示实际日期范围、报工/人员/工资单数量、原金额、新金额、差额和逐条阻断原因；预览不保存价格、不改日期分段、不撤回工资、不改报工。零金额差异但来源改变时也要说明。

例：本月100件，原价1元、工资100元；从月初改成1.2元，预览120元、增加20元，确认后才写入，原100元依据仍可查询。

## 三、资金与数据边界

- 只纠正工价，不连带改变数量、工时、缺陷、人员、部门、产品/工艺事实或复核状态。
- 已有工资明细沿用其原WageCoeff；未生成工资的报工须有可靠的报工系数依据。缺证据不倒推系数、不把当前人员系数冒充历史系数。是否可从现有记录取得证据属于执行方待核实事实，不让用户替开发者查数据。
- 重新匹配使用该报工原始属性值和单位语义，不读取后来修改的产品档案；专属优先、专属缺规格不回通用，缺价不按0价或旧任务预算兜底。
- 保留原快照、改后快照、原/新金额、原因、操作者和批次。普通调价不动旧快照；明确追溯才更新报工当前计薪依据，旧依据永久留在只追加审计记录中。
- 首版只纠正当前业务月份生效日起的现存报工；往月追溯、发放补差、税务、审批、版本管理页面不做，也不预建其接口或开关。
- 当前系统没有已证实的完整发放/关账管理能力，不能假装已检查“实际已发薪”。已确认不是已发放；识别到status=2或其他可靠关闭约束则阻断。
- 周结单跨月时，只改本次日期范围内的明细，其余明细与系数原样保留。无工资单不自动生成；同一报工归属多张工资单等矛盾整次阻断。

## 五、对标依据与适用边界

## 附录A：已核实基础与最小实现约束

1. 当前413为建单锁价。OperationPriceListService.PreviewAsync带workOrderId时直接返回任务旧报价；OperationPricingService.LockedAsync把它转成报工计薪依据。实施必须分开“原始工艺事实/预算”和“按报工日期取价”，不能只改界面文案。
2. ReportPriceSnapshot.Calculate按快照算金额，保留为纯计算入口；ReportService普通报工、补报、代报/分摊、开工完工及MCP等已有入口统一取价。它们是同一后端规则覆盖，不代表首版扩做多端调价界面。
3. SalaryService.RecalcDraftAsync读取当前人员系数；现有批量重算失败不停批，均不能直接作为本功能原子提交路径。RevokeAsync等含事务，需抽出能参与共同事务的核心步骤，不能让部分撤回先提交。
4. ProdReportChangeLog只记录改数，不假定已有调价快照审计。内部需持久化不可变价格内容、有效分段及调价前后依据；原418指定的三张新表只是候选实现，表数、索引和复用方式由执行方按最小正确实现核实，不锁死架构。
5. 业务日期按统一业务时区（本方案Asia/Shanghai）解释。现有存储/解析、服务端部署时区及是否已有配置待核实，不声称已有账套时区配置，不另建时区管理模块。
6. 权限、厂隔离、报工按部门授权、编号唯一、删除依赖倒序和ThrowHelper上下文不能省。不得为调价顺带删除工单/价表或改写其它账套。

候选持久化为base_operation_price_revision、operation_price_change_batch及operation_price_change_item；这是建议落点，不是已存在表或“至少新增三表”的约束。必要DDL、JSON字段和兼容规则先写入02，接口先写入33，再建EF模型和显式增量迁移。

上线基线不得清库、改历史工资或把当前价冒充所有过去日期的价。执行方核实现有版本/快照能否支持历史日期；无可靠历史价格或系数则明确阻断相关追溯/补报并列受影响范围。若会影响正常主流程，集中向用户确认上线适用范围，不能悄悄新增一刀切的历史补报禁令。

有效日期分段沿用含首尾语义；同日纠错和月初追溯不能产生重叠或结束早于开始的区间。替代/停用/恢复保留足够历史证据；未来安排冲突处理按正文待确认项执行。不要只按当前根表Status=1过滤而丢失历史合法版本。

建议沿/api/operation-price-list增加price-change/preview、price-change/commit及执行结果查询；不接受客户端factoryId/操作者或任意SQL。预览输入价表版本、生效日、拟改价格、追溯标志、原因、RequestId；返回短期确认凭据、计划指纹、范围与差额/撤回/阻断清单。确认只提交已预览请求；同RequestId同内容返回原成功结果，不同内容拒绝。具体路由/DTO由执行方对照现有惯例定稿，不另建通用工作流框架。

## 附录C：事务和金额核对清单

- 以报工业务日期筛选本月范围，覆盖待复核/通过/退回状态但不改变原状态；未通过记录不提前计入工资。重新匹配拟生效价格，不只过滤旧PriceListId；原专属价仍优先，专属缺价不回通用。
- 区分报工预估金额与工资单金额。工资纠正沿用明细原系数，报工显示金额沿用其可靠计算系数，不能用report.WageAmount替代工资旧金额；无关工资明细不变，主表从完整明细汇总。
- 普通改数若沿既有规则刷新报工预估系数，AppliedWageCoeff与显示金额须同步并留痕；普通工资系数重算仍按225处理，不反向改写报工当时的依据。
- 预览指纹覆盖完整受影响集合、原始事实/系数/快照、价格时间线、工资明细与主表状态。提交重新扫描候选集合，新增报工/工资单、改数、改价格或跨月均使旧计划失效。
- 服务端重新检查权限、授权、日期、计划指纹；沿同厂应用锁和统一行锁顺序，用一个事务完成价格生效、必要撤回、报工和工资更新、审计及幂等结果。错误整体回滚，不复用“失败不停批”。提交中断先查RequestId结果，不盲目重复。
- 计件/计时乘系数；固定每人每条有效报工一笔且不乘数量/系数；扣价不乘系数；换算和金额精度沿02及现有计算器，最后舍入。缺价、多命中、坏快照、跨厂、重复工资归属、status=2等明确阻断。
