## 二、必须先纠正的旧实现

1. `OperationPriceListService.PreviewAsync`有workOrderId时直接返回旧任务报价；不能继续把它当“按报工日期的新报价”。
2. `OperationPricingService.LockedAsync`当前工资来源为工单锁价；拆成“取得工单原始取价事实”和“按报工日期选择有效价格版本”。任务历史报价保留作基线/预估，不强行覆盖成最新价。
3. `ReportService`的普通报工、批量补报、代报/分摊、开工完工报工、预览等入口必须统一调用新服务；检查其他服务/MCP快捷入口，不留旧LockedAsync绕行。
4. `ReportPriceSnapshot.Calculate`继续是按已确认快照算钱的纯入口，不在内部查询当前价。普通修改数量/时长和普通工资重算继续沿用报工快照。
5. `SalaryService.RecalcDraftAsync`会读取最新人员系数，不能直接拿它遍历整张单来完成调价。抽出可接受“指定报工新快照＋每明细原系数”的受事务控制方法，仅更新受影响明细，再由全部现存明细汇总主表。
6. `RevokeAsync`等现有方法包含自己的事务/SaveChanges，不能简单嵌套多个已提交调用。抽出内部核心步骤，追溯提交用一个共同事务，失败不能留下“已撤回但未调价”的半成品。

## 三、唯一计算口径

- 正常提交：最终持久化ReportTime的业务日期决定价格；预览传同一日期，提交重新核实。业务时区沿现有账套配置，当前Asia/Shanghai，不混用UTC日期和服务器零点。
- 新报工根据工单建单时保存的产品/工艺事实取价；不能因产品档案后来修改自动改变工单要求。已报工追溯一律使用该条报工快照的AttributeEvidence.Attributes等原始事实。
- 补报按补报业务日期取价；不按提交当天取价。跨生效日计时记录首版按报工日期统一取价，不自动拆小时。
- 价格匹配仍为本厂/工序/产品范围/日期，专属优先，无专属才通用；专属缺规格不回通用。复用价格行、收费组、包含项、单位换算算法，缺价/多命中明确阻断。
- 计件/计时乘人员系数，单笔固定每人每条有效报工一笔且不乘系数；扣价不乘系数，沿既有最终金额舍入。保持数据字典现有金额精度，不用前端展示单价反算。
- 本次追溯冻结原数量、时长、缺陷、人员、部门、产品和工艺值、复核状态。工资明细已有WageCoeff优先作为其历史计算依据；未生成工资的报工必须有可靠报工系数快照。缺失时列为阻断，不用当前用户系数或金额除法补造。
- 旧工资明细与报工显示金额可能使用不同系数：预览必须分别核对工资明细原系数和报工预估系数，禁止仅凭report.WageAmount代替已生成工资的旧金额。此功能不改变225允许的普通人员系数重算规则。

## 四、持久化与上线基线

实施前先在02补完整SQL Server DDL（IDENTITY/NVARCHAR/DATETIME2、精度、约束、索引），在33同步API契约，再建EF模型和显式增量迁移。下表是本指令要求的最小持久化内容，不是已上线DDL。

| 对象 | 必须保存的内容 |
|---|---|
| `base_operation_price_revision`（新增） | id、factory_id、price_list_id、revision_no、effective_from/effective_to、取价有效/已替代标记、不可变完整价表内容JSON（包含表头、details、字段类型/单位语义）、内容哈希、创建人/时间；同表版本号唯一，按厂/工序/产品范围/有效期建立取价索引或等效冗余字段 |
| `operation_price_change_batch`（新增） | id、factory_id、request_id唯一幂等键、操作者/原因、价表及前后版本、业务日期范围、请求/计划指纹、成功结果JSON、受影响工资单完整前后快照、创建/提交时间；唯一(factory_id,request_id) |
| `operation_price_change_item`（新增） | id、factory_id、batch_id、report_id、可空statement_id/item_id、报工完整旧/新计薪快照及旧/新显示金额、工资明细完整旧/新快照与系数、金额差额；批内报工唯一且保持报工到工资明细映射 |
| `prod_report.price_snapshot`（扩展JSON契约） | 在现有schemaVersion=2结构上新增可空PriceRevisionId、AppliedWageCoeff及原始事实语义信息；旧结构仍能按旧金额计算，缺新字段不得凭空补入历史事实 |
| `ProcessingQuote`（扩展JSON契约） | 保留现有PriceListId/版本/产品工序/Attributes/命中行/单位换算，增加价格内容版本ID和明确PricingDate；任务预估标识只影响显示，不被工资当作最终价 |

历史版本内容与已提交审计行仅追加，不能通过普通CRUD修改或删除；现有ProdReportChangeLog只做改数日志，不往其source=1/2里塞新的不兼容枚举冒充调价审计。

有效期仍按日期、含首尾。新版本生效时在同厂应用锁和Serializable事务内校验并切分有效分段。相同日期纠错、向本月初追溯不能生成结束早于开始的区间；被替代版本内容及身份保留，取价必须排除已被替代分段。跨表同工序/产品范围不能出现两个同时生效版本。首版检测到范围内已有另一期未来调价安排时明确阻断并列明，不静默吞掉未来版本。

停用/恢复也须记录生效事件，不能因当前表头状态覆盖而抹掉历史有效版本。历史补报选择其业务日期当时有效且有证据的版本，不能只过滤当前根表Status=1后误判历史缺价。

上线不做破坏性清库：现有报工和工资保持原快照、原金额。当前价表建立上线基线版本，起点为原生效日与功能上线日中的较晚日期；不把当前价内容冒充过去所有日期的历史价格。上线前的历史补报没有可靠历史版本则阻断并提示。明确追溯纠错时可用管理员确认的新版本覆盖本月指定日期段，但不得自动推测其他日期的旧价。

旧报工若已有工资明细，可从唯一对应明细取得本次工资纠正的可靠系数；未生成工资且缺报工系数快照的旧记录首版阻断。新报工必须保存AppliedWageCoeff，后续调价能保持其原系数；普通工资重算是否刷新系数仍按225单独处理。

普通改数若按既有规则重新计算报工预估金额及人员系数，必须同步更新该报工AppliedWageCoeff并保留修改依据，不能让报工显示金额使用新系数而快照仍声称是旧系数。普通工资系数重算只更新其工资明细依据，不能顺手把报工当时的系数改成当前值。

## 五、接口与预览契约

建议沿`/api/operation-price-list`增加以下管理员接口，客户端不传factoryId/操作者身份，不接受任意SQL：

1. `POST /{id}/price-change/preview`
   - 输入：ExpectedVersion、生效日期、价格行ID及新amount/deductPrice、RepriceCurrentMonth、Reason（追溯必填）、RequestId。
   - 只允许更改价格数值/扣价；不接受改工序、产品、条件结构、收费组、计价方式、单位/换算的字段。行ID必须存在且属于当前表版本。
   - 返回：PreviewToken、ExpiresAt、PlanHash、实际范围、价表前后差异、影响记录/人员/工资单数量、原/新/差额、需撤回工资单、阻断清单；明细可分页，但确认摘要覆盖完整集合。
   - 预览无任何业务数据库写入，不能先调用原SaveAsync保存价表。Token可使用受保护短期凭据，默认5分钟，绑定厂、操作者、请求和完整计划；不把敏感快照塞进可读Token。
2. `POST /{id}/price-change/commit`
   - 输入：RequestId、PreviewToken、PlanHash。只能提交预览确认的内容，不允许附带替换价格或改变日期/范围。
   - 成功返回BatchId、各对象实际变化数量、总差额及待重新确认工资单；相同RequestId与相同请求重试返回原成功结果，不重复调价或叠加差额。同键不同内容拒绝。
3. `GET /price-change/{batchId}`
   - 本厂管理员可查前后依据、原因和执行结果；不新增“版本管理”维护页面，可在价表详情提供调价记录入口。

正常改价也走预览/确认，在RepriceCurrentMonth=false时不修改任何旧报工或工资。启用价表的价格修改不得保留一个可绕过版本/审计的旧PUT通道；原新增/草稿/复制/停用接口保持契约并在服务端统一写版本，未授权字段变更拒绝。

## 六、追溯筛选、预览与提交

1. 本月范围按提交时业务日期重新计算；生效日早于本月1日或晚于今天不能勾选本月追溯，跨月提交旧预览失效。范围是生效日起到本月末已存在的报工，不按创建时间筛。
2. 根据拟生效版本重新匹配完整候选集并比较新旧报价，不只按PriceListId过滤；特别测试新增专属价覆盖原通用价、同厂其他产品仍用通用价、原专属缺价不能回通用。
3. 覆盖待复核/已通过/已退回报工，保持原复核状态。未通过记录只纠正其未来可用计薪依据，不提前生成工资；已有工资的记录须符合现有工资与复核约束。
4. 找出所有受影响工资明细及主表，包括周结单跨月情况；仅重算范围内明细，其他明细各字段（含WageCoeff）原样保留，再从完整明细汇总TotalAmount。不得删除/重建整张单导致无关明细变化。
5. 同一报工被多张工资单引用、主表厂别不一致、明细与报工快照冲突或存在已发放status=2，整次阻断并列ID；没有明细的报工不自动生成新工资单。不存在可靠关账字段时不得假装已校验完整关账状态。
6. 预览指纹必须覆盖价表版本、价格时间线、完整受影响报工集合、原始事实/快照/系数、工资明细与主表状态。提交重新扫描候选集，不能只复核预览中的旧ID；新插入的范围内报工或新生成工资单也会让计划失效。
7. 提交取得同厂价目表事务锁，并按统一顺序锁定涉及工单/报工/工资对象；与报工提交、改数、工资生成/确认/撤回保持相同锁顺序，避免死锁或在调价与报工之间读到半条时间线。提交前再次校验权限/授权、业务日期、指纹和所有依赖。
8. 一个数据库事务内完成版本生效、必要的工资撤回、报工计薪快照及派生金额更新、受影响工资明细与主表合计更新、审计和幂等结果写入；已确认工资变草稿并清空确认信息，原确认状态完整留痕，完成后不自动确认。
9. 任一条件变化或写入失败，全部回滚。禁止复用现有“批量重算失败不停批”作为本功能提交语义；禁止先保存价表再另开事务重算。调用中断后先按RequestId查结果，再决定重试，不能自动盲目重新提交。

## 七、PC界面与其它入口

价目表列表/详情增加“调整工价”；显示原数值、生效日快捷项、默认不选的追溯复选框和原因。确认页区分“报工预估金额”和“工资单金额”，汇总差额只对同一口径求和；列出撤回工资单，阻断时不能点确认。

工单界面“锁定工价”相关文字改为“预估工价，以报工日期有效工价为准”；现场预览与最终报工使用同一价格日期和算法，不能显示旧预估却后台算新价。H5/PDA/MCP/开工完工/代报分摊不新增调价管理，但最终快照必须一致。现有普通工资重算按钮不变成隐式追溯调价按钮。
