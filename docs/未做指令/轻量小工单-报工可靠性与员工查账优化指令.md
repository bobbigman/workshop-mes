# 优化指令：普通报工可靠性与手机“我的报工”

日期：2026-09-30

## 一、目标和范围

让工人报得快、记得准、查得到。保持轻量小工单定位，不扩展成重型 MES。

按三步交付：

1. 普通报工事务完整性与重试防重复。
2. 手机报工时长“选填”标识和清楚的成功回执。
3. 手机“我的报工”只读查询。

本期不做个人工资页面、手机改数/补报/审批、复杂申诉、自动绩效、个人速度排名、设备联网和异常流转改造。不自动调整任何客户的不良扣款、工价或既有报工。

## 三、普通报工提交可靠性（先做）

### 业务行为

- 一次提交生成一个唯一请求标识。同一请求超时重试仍用原标识，不能每重试一次换一个。
- 同一厂、同一用户、同一标识、同一内容：最多生成一笔报工，返回同一笔成功回执。
- 同一标识却换了业务内容：明确拒绝，不静默返回另一笔数据。
- 成功后“继续报工”的下一批使用新标识，即使数量相同也允许正常提交。
- 成功已落库、响应丢失时，重试应返回原记录；即便原提交使工单自动结束，也不能把该重试误判成新的结束工单报工。
- 重放仍校验登录身份和账套归属，不因返回回执泄露其他人的记录。

### 实现约束

- 使用数据库持久化去重约束，不能仅依赖按钮禁用或进程内缓存；并发相同请求也只能成功写入一笔。
- 主报工记录、扩展字段、相关状态更新必须在同一业务事务中提交。任一步失败不得留下半笔有效报工；正常返回仅在事务完成后发生。
- 同工序不同请求并发时，防超额检查与写入也必须可靠，不得两笔都读到旧剩余量后突破计划上限。
- 不复用批量补报 batch_no 表达普通提交：其现有语义是一批多条，保持原有补报兼容。
- 先核对数据字典后确定最小字段/索引方案，把精确 SQL Server 增量 DDL、EF 映射、请求内容一致性判断方案补入本指令及 docs/02，再实施迁移。不得凭本稿另造整张表结构。
- 历史数据保留、去重字段可兼容旧行；明确旧客户端缺少请求标识时的兼容策略。所有本仓普通报工调用方同步接入；不得把未接入的旧端宣传为支持重试去重。
- 响应增加记录 ID、工序、良品、不良、提交时间、复核状态等回执数据，保持现有 ApiResult 包装和既有调用方兼容。
- 未知提交结果时保留输入及对应请求标识，明确提示先查“我的报工”或按原请求重试；不得直接提示“肯定没保存”。不得把跨页面、重登后的新提交伪装成原请求重试；需要恢复时按账套和账号隔离待确认请求。
- 错误按 ThrowHelper 与现有日志机制保留上下文；不吞异常，不把数据库异常误当去重成功。

## 四、报工页小改

- 标题改为“报工时长（选填）”，首版保留现有输入与校验，不增加开关、自动计时或新必填字段。
- 成功回执例：“裁切：良品 18，不良 2，已提交，待复核”。状态以服务端真实返回为准，管理员提交不能固定显示待复核。
- 保持“提交后返回”“继续报工留页清数”的原操作；回执应有足够阅读机会，并能从“我的报工”找到原记录，不增加强制确认弹窗。
- 失败保留输入；已确认成功后再清空数量。后续进度刷新失败要与报工提交失败区分，不能诱导重复报同一批。
- 不新增工人填写事项，不改权限、数量、复核与计价口径。

## 五、手机“我的报工”

### 页面范围

- 从手机工单页增加清楚的“我的报工”入口，首版不再挤一个底栏栏目。
- 默认今天；支持日期范围、工单号和分页。日期按原报工时间，沿用系统业务时区。
- 显示工单、产品、工序、良品、不良、提交时间、待复核/已通过/已退回；退回时显示原因。
- 空列表、加载失败、加载中要区分；异常不得显示成“今天没有报工”。
- 只读，无编辑、删除、代报按钮。提示“数量有误请联系管理员处理原记录，不要重复报”。
- 此页不显示工资预估，不把待复核或已退回说成已结算。

### 接口与权限

- 建议使用独立的本人查询入口（例如 GET /api/Report/mine），复用已有查询投影，避免改变原 PC 查询权限。
- factoryId、userId 必须从当前登录上下文取得；客户端传其他人的 ID 不能扩大范围。
- 检查角色守卫、账套过滤和授权档，确保能正常报工的工人可查询本人记录，不误绑工资功能档。
- 不直接开放管理员工资接口或整个报工列表作为替代方案。
- 精确参数、分页结构与返回字段开工时对齐现有 API 约定，并在本指令中补齐。

## 六、验收清单

### 必须验证的可靠性场景

- [ ] 同请求连续提交、并发提交、成功后响应丢失再重试，均只有一笔报工，回执 ID 相同。
- [ ] 同标识不同内容明确拒绝；新标识相同数量可正常记录下一批。
- [ ] 第一笔使工单结束后，以原请求重试仍可返回原成功结果。
- [ ] 在主记录保存后、附加字段或状态更新处模拟失败，没有残留半笔报工。
- [ ] 剩余 10 件时，两笔不同请求并发各报 8 件，不得累计通过 16 件。
- [ ] 普通 PC 报工、H5、批量补报原流程及旧客户端兼容策略符合本指令。

### 页面与隔离

- [ ] 时长仍非必填；计时填写、连续报工、返回路径保持正常。
- [ ] 成功提示数量及状态准确；刷新失败不显示成提交失败。
- [ ] 手机能查本人当天与历史记录，退回原因、日期筛选、分页正确。
- [ ] 更换请求参数、登录另一账号或另一账套，不能看到前一人的本人列表及待确认请求。
- [ ] 无权限部门仍不可报工；未派工但有部门权限仍可报工。
- [ ] 三种复核状态显示正确，待复核与已退回不被解释成已入工资。

可靠性与权限需有针对性的后端集成验证；文案不写镜像测试。手机/PDA 走查一次完整主流程。记录实际测试结果，不把静态阅读当运行验收。
