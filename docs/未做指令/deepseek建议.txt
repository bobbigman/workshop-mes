# 车间小工单 AI 助手 — 角色问答与实现文档

> 本文档面向 Cursor 实现。核心原则：**只描述"问什么、怎么答、怎么落地"，不含代码细节。**
> 系统边界：当前只有报工小工单（无销售、采购、库存），金蝶集成后才补充。

---

## 一、系统定位

**一句话：** 一个跑在企业微信里的 AI 助手，让老板、车间主管、财务、员工用自然语言查车间数据，回答带判断、带口径、带来源，而不是甩一个裸数字。

**入口形态：**
- **群机器人（单向推送）**：经营简报、异常预警
- **智能机器人（双向对话）**：员工/主管/老板/财务主动提问

**数据来源：**
- 现在：报工小工单（产出、计件工资、工单进度、异常）
- 集成后：金蝶（销售、采购、库存、财务）

**永远不做：** 单工单精确成本、制造费用分摊（数据基础不成立，算了没人信）

---

## 二、数据边界（所有角色必须遵守）

### 现在能答（报工系统）
- 产出数量、合格数、待检数
- 计件工资（已确认 / 待确认 / 返工扣款）
- 工单进度、产线状态
- 效率（单位时间产出、停机时间）
- 异常报工（重复、超量、待检积压）

### 集成金蝶后才能答
- 销售收入、毛利区间
- 材料成本、采购价格
- 库存金额、周转
- 现金流预测
- 客户 / 产品盈利分析

### 永远不答
- 单工单精确成本
- 制造费用分摊到工单
- 精确到分的单工单利润

**理由：** 领料、工时、分摊基准本身是估的，算了没人信。

**越界处理：** 直接说"这个算不准，不建议看"，解释原因，给替代方案。

## 三、四个角色的核心问题与回答方式

### 3.1 老板（Boss）

**角色定位：** 要方向感，不要精确到分。只回答能对账的数。

**5 个核心问题：**

| # | 问题 | 数据来源 | 能答吗 |
|---|---|---|---|
| 1 | 今天车间干了多少？ | 报工系统 | 现在 |
| 2 | 这个月人工成本多少？ | 报工系统 | 现在 |
| 3 | 哪个班组效率最高？ | 报工系统 | 现在 |
| 4 | 这个月赚了多少？ | 报工 + 金蝶 | 集成后 |
| 5 | 哪个客户最赚钱？ | 报工 + 金蝶 | 集成后 |

**回答方式：**

先结论，再数据，再归因，最后标注来源和追问入口。

示例（今天车间干了多少）：
- 结论：今天产出偏低，比昨天少 13%
- 数据：报工 1,840 件 / 合格 1,620 件 / 工资 4,280 元
- 归因：上午停机 40 分钟 + 王强请假 + 返工增加 6 件
- 来源：报工系统（已审核口径）
- 追问：要看按班组还是按产品？

**回答原则：**
1. 先结论，再数据，再归因
2. 必须标注数据来源
3. 对比昨天 / 上月，标记异常
4. 需要金蝶数据的明确说"集成后"
5. 永远不给单工单成本

**权限：** 全厂数据可见；涉及金额标注口径和来源；不自动执行写操作。

---

### 3.2 车间主管（Supervisor）

**角色定位：** 要异常和对比，不是单个数字。快速知道"谁有问题、哪个单要炸"。

**5 个核心问题：**

| # | 问题 | 数据来源 | 能答吗 |
|---|---|---|---|
| 1 | 今天我这组做了多少？ | 报工系统 | 现在 |
| 2 | 谁干得多谁干得少？ | 报工系统 | 现在 |
| 3 | 哪个工单快超期了？ | 报工系统 | 现在 |
| 4 | 今天有没有异常？ | 报工系统 | 现在 |
| 5 | 明天要怎么排？ | 报工 + 工单 | 现在（基础版） |

**回答方式：**

先汇总，再异常人/异常单，再对比，再建议。

示例（今天我这组做了多少）：
- 汇总：三组今日报工 1,840 件 / 合格 1,620 件 / 完成工单 11 个
- 异常：王强 140 件（日均 220 件，偏低）；WO-10245 待检积压 80 件
- 对比：vs 昨天 -13%，主因上午停机 40 分钟
- 建议：王强明天补产，WO-10245 优先质检
- 追问：看按人明细还是按工单？

**回答原则：**
1. 先汇总，再异常人/异常单
2. 异常必须分级（高 / 中 / 低）
3. 对比昨天 / 上周，标记偏差
4. 主动给"下一步建议"
5. 班组视角，不给个人工资明细（除非主管主动要）

**权限：** 本组数据可见；跨组查询拒绝；不自动执行排产，仅给建议。

---

### 3.3 车间员工（Worker）

**角色定位：** 要个人的数，简单、直接、能看懂。不说术语，不绕弯。

**5 个核心问题：**

| # | 问题 | 数据来源 | 能答吗 |
|---|---|---|---|
| 1 | 我今天做了多少？ | 报工系统 | 现在 |
| 2 | 我今天工资多少？ | 报工系统 | 现在 |
| 3 | 我这个月做了多少？ | 报工系统 | 现在 |
| 4 | 为什么今天少了？ | 报工系统 | 现在 |
| 5 | 我排第几？ | 报工系统 | 现在 |

**回答方式：**

先主数字，再拆分，再说口径，最后给追问入口。

示例（我今天做了多少）：
- 主数：你今天做了 260 件（报工数量）
- 拆分：合格 180 件 / 待检 80 件；A 型壳体 200 件 / B 型支架 60 件
- 说明：截至 18:30，当前班次 08:00–20:00
- 异常：比昨天少 50 件，主因上午停机 40 分钟
- 追问：要看本月累计还是组内排名？

**回答原则：**
1. 先主数字，再拆分
2. 必须说明时间口径（截至几点）
3. 工资必须拆分"已确认 / 待确认"
4. 异常主动解释原因
5. 口语化，不用财务术语

**权限：** 仅本人数据可见；看不到别人工资/产出明细；排名仅显示名次，不显示他人具体数。

---

### 3.4 财务（Finance）

**角色定位：** 要可对账、可追溯、可审计。每个数必须说清口径和来源。

**5 个核心问题：**

| # | 问题 | 数据来源 | 能答吗 |
|---|---|---|---|
| 1 | 这个月计件工资总额多少？ | 报工系统 | 现在 |
| 2 | 这些报工都审核了吗？ | 报工系统 | 现在 |
| 3 | 有没有异常报工？ | 报工系统 | 现在 |
| 4 | 这个月人工成本比上月高吗？ | 报工系统 | 现在 |
| 5 | 这个月毛利多少？ | 报工 + 金蝶 | 集成后 |

**回答方式：**

先口径，再数据（已确认/待确认/返工拆分），再对比，再异常，再建议。

示例（这个月计件工资总额多少）：
- 口径：2026 年 10 月 1–10 日，已审核口径，未计提
- 数据：已确认 84,270 元 / 待质检 12,380 元 / 返工扣款 -2,150 元 / 预估合计 96,650 元
- 对比：上月同期 78,500 元，+7.3%
- 异常：无高风险异常
- 建议：待检部分质检通过后再计提
- 追问：看个人明细还是异常清单？

**回答原则：**
1. 必须说明口径（已审核 / 含待检 / 含返工）
2. 必须给数据来源（哪个单、哪条报工）
3. 异常必须分级 + 可追溯
4. 涉及计提、结转 → 提示"需人工确认"
5. 不自动执行写操作，只给建议

**权限：** 全厂数据可见（可对账部分）；所有查询记审计日志；单价修改必须追溯"谁改的、什么时候"；涉及金额调整仅生成建议，不自动执行。

## 四、回答的通用结构

### 标准五段式
1. 结论：一句话说清
2. 数据：关键指标 + 对比
3. 归因：异常原因（如有）
4. 来源：数据来源标注
5. 追问：下一步看什么

### 员工精简三段式
1. 主数：今天做了多少 / 工资多少
2. 拆分：已确认 + 待确认
3. 追问：看本月还是看排名？

### 财务四段式
1. 口径：时间 + 状态 + 是否已计提
2. 数据：已确认 / 待确认 / 返工扣款
3. 异常：风险分级 + 来源
4. 建议：需人工确认的事项

### 禁用词
- 不说"超期了" → 说"超期 X 天 + 客户历史投诉 X 次 + 建议 P1"
- 不说"工资 3500" → 说"已确认 3500，另有 400 待审核"
- 不说"成本 36.5 元" → 说"计件工资 300 元（准确），毛利区间需集成后"

## 五、实现要点（不含代码）

### 5.1 整体架构：四层分离

**入口层（企业微信）**
- 群机器人：单向推送（经营简报、异常预警）
- 智能机器人：双向对话 + 流式回复
- 自建应用：推送配额用尽时兜底

**编排层（Agent Runtime）**
- 消息去重（企业微信会重试）
- 角色路由（从企业微信 userid 解析角色）
- 会话管理、流式回复、超时保护

**能力层**
- Skill：角色知识包（老板/主管/员工/财务），写一次，平台无关
- MCP Client：调用 MCP 工具
- MCP Server：封装车间小工单 API；集成后加金蝶 MCP Server

**治理层**
- 身份传递：企业微信 userid 穿透到车间 API
- 权限门控：不同角色只暴露不同工具
- 审计日志：所有查询留痕
- 写操作确认：涉及金额调整仅生成建议

### 5.2 角色路由与工具隔离

**核心决策：不同角色绑定独立 Agent，只暴露该角色可用的工具。**

- 员工 Agent：只能调 `query_my_output`、`query_my_wage`
- 主管 Agent：只能调 `query_team_output`、`query_anomaly`、`query_work_order`
- 老板 Agent：只能调 `query_plant_summary`、`query_trend`
- 财务 Agent：只能调 `query_wage_total`、`query_anomaly_audit`

**为什么不能只靠 Prompt 说"不要查别人数据"？** 工具在 schema 层不可见，模型想调也调不了，这是硬约束。

### 5.3 MCP 工具设计原则

**工具清单（当前）：**

| 工具 | 用途 | 适用角色 |
|---|---|---|
| query_output | 查产出（个人/班组/全厂） | 全部 |
| query_wage | 查计件工资（已确认/待确认拆分） | 员工/主管/财务/老板 |
| query_anomaly | 查异常报工 | 主管/财务 |
| query_work_order | 查工单进度 | 主管/老板 |
| query_my_ranking | 查个人排名（仅名次） | 员工 |

**设计原则：**
- 按"用户意图"设计工具，不按"API 镜像"设计
- 参数只放模型能填的（period、scope），身份从上下文注入
- 大结果分页，不截断（截断会破坏 JSON 结构）
- 只读模式启动，写工具物理不存在

**身份透传：**
- 企业微信 userid → 生成短期凭证（含 userid、role）→ MCP 调用携带 → 服务端强制按 userid 过滤数据
- 不能用一个超级管理员账号代查所有人

### 5.4 企业微信适配要点

- 消息格式是 JSON，支持 Markdown
- @人格式是 `<@userid>`，不是飞书的语法
- 主动推送有配额限制（每会话每日约 10 条）
- 流式回复：先返回 stream_id，异步产出结果

### 5.5 集成金蝶后的扩展

**不改架构，只加 MCP Server：**
- 现有：车间小工单 MCP Server
- 新增：金蝶 MCP Server（销售/采购/库存/财务）
- Skill 层只需在数据边界中把"集成后才能答"移到"现在能答"

## 六、落地路径建议

**第一阶段：群机器人单向推送（1 周内）**
- 老板群：每日 8:00 经营简报
- 主管群：异常预警（实时触发）
- 财务群：每日报工审核提醒
- 验证角色需求是否真实

**第二阶段：智能机器人 + MCP（2–4 周）**
- 接入智能机器人，支持主动提问
- 部署车间小工单 MCP Server
- 角色 Prompt 作为系统提示词

**第三阶段：按角色分流**
- 老板群 → 只响应经营概览/趋势/异常
- 主管群 → 只响应本组产出/异常/排产
- 员工单聊 → 只响应个人数据
- 财务群 → 只响应计件工资/异常报工/对账
- **不要在同一群里让机器人区分角色**

## 七、Cursor 实现清单

**Skill 层（写一次，平台无关）：**
- 老板 / 主管 / 员工 / 财务四个角色知识包
- 共享判断层（口径确认、异常分级、数据边界）
- 共享文案模板（五段式、三段式、四段式）

**Harness 层（平台相关）：**
- 企业微信消息收发（群机器人 + 智能机器人 + 兜底）
- 角色路由 + 消息去重 + 权限门控
- MCP Client（调车间 API 和金蝶 API）

**配置：**
- 角色 → 工具映射
- 企业微信 userid → 角色映射

**治理：**
- 审计日志
- 写操作确认机制
- "永远不答"清单

---

**一句话总结：** Skill 层负责"判断和文案"，Harness 层负责"消息收发、工具调用、权限门控"。四个角色共用一套底层查询工具，差异只在口径确认和文案模板。权限不靠 Prompt 自觉，靠工具隔离和身份传递硬约束。集成金蝶时只加 MCP Server，不改 Skill 和架构。
