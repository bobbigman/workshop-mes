# 413-开发指令：彻底删除旧工价表，统一工序价目表取价与工资计算

> 状态：实施中。2026-10-24。
> 用户依据：系统仍在开发阶段，没有需要保留的历史业务数据；拿掉旧工价表，连数据库后台表一起删除，避免双轨取价导致工资错误。
> 用户已要求执行，按S1～S7依次实施与验证；只操作已核实本地开发库，不部署、不修改客户库。
> 本指令实施后覆盖400/401/405/410中“普通工价继续使用、按产品工序选择模式、兼容旧工价”的当前推荐口径；旧文件保留为开发记录，实施时标注已被413替代，不再据其保留旧分支。

## 一、目标和边界

**全系统只保留“工序价目表”这一处工价配置和取价来源。** 新建/复制工单按产品、工序和属性选表并锁价；报工和工资从该任务/报工快照计算。缺表、缺价、缺关键属性、重复命中、缺锁价一律明确失败，不回退旧工价、不把缺价记成0。

不是只隐藏页面、停用旧表、改菜单名或建一个数据库视图继续兼容旧表。删除旧表、旧实体、旧CRUD、旧导入、旧匹配器及所有回退路径；普通固定单价也作为新价目表的“不限条件主价”维护。

保留现有SQL Server/.NET8/Vue3技术栈、产品编号唯一、报工部门权限和删除依赖规则。只做此次统一需要的最小改造，不新增通用薪酬引擎、审批流或模板管理。不把产品资料中的产品单价当工价。

## 三、唯一取价契约

1. 保留410表头绑定：本厂+当前工序+启用+业务日期有效；有效专属表优先，无有效专属才通用。专属表缺规格不回通用。同范围启用日期不得重叠，其他产品的专属表可并存。
2. 行不绑产品，只按产品固有属性+本单当前工序工艺属性匹配；固有属性不被工艺覆盖，其他工序/工单全局颜色不参与。
3. 全部工单工序都要有有效价目表和可靠锁价，不再提供“普通工价/属性价目表”开关，不因未配置模式或旧配置为空回退。
4. 工单创建、复制时服务端重新取价，与任务、工艺值、锁价同事务；任一道工序失败则整单不落库。预览指纹/版本变化要求重预览，禁止采用客户端成交金额。
5. 报工使用任务锁价，工资生成/重算使用报工快照；不得在报工、复核、工资页面或MCP再次按当前价格取价。调价不改已保存单据，快照是后续正确结算的必要设计，不因“没有旧历史”而删除。
6. 缺价报错带产品编号、工序、表编号/版本及缺失或冲突条件。已确认0价是显式规则，未确认/单价null与0严格区分。
7. 部门仅用于报工权限，人员系数继续保留；不把旧表的部门/人员价格优先级机制迁入新体系。禁止最具体打分/行号优先等旧匹配兜底。

## 四、计件、计时、固定价格全部落在同一体系

价目表表头增加`pricing_type TINYINT NOT NULL DEFAULT 1`：1计件、2计时、3单笔固定。一张表只允许一种计价方式。首次启用后工序与计价方式都锁定，需变更则复制新建、调整有效期，不直接改已启用表身份。

| 方式 | 维护和计算口径 |
|---|---|
| 计件 | 沿405/410：基础或最终主价唯一；已确认且适用的收费组按规则叠加；原价÷每计价单位对应报工数×良品数×人员系数，最后四舍五入到分 |
| 计时 | 同表维护元/小时，计价单位固定“小时”、换算数量固定1；首版只允许唯一命中主价，不允许附加行/收费组/包含项。按实际分钟÷60×锁定时薪×人员系数，最后舍入；工时仍经现有开工/补报校验，不由前端自由报金额 |
| 单笔固定 | 同表维护“元/笔”，换算数量固定1，首版只允许唯一命中主价，无附加组/包含项。每人每条有效报工记录按锁定固定额计一次，不乘良品数量、不乘人员系数；请求去重、复核和结算去重继续有效 |

不良扣价保持独立、非负：计件按每计价单位扣价÷换算数×不良数；计时/固定按每个报工单位的不良扣价×不良数，不乘人员系数，最后舍入。不得将时薪当每把单价或用小时换算扣款。产品报工单位仍必须与表头报工单位一致。

“固定”依据02的单笔固定额及当前计算器实际行为，**不新增月薪按月发一次的模块**；旧代码注释中的“固定月薪”误称同步纠正。不能借删表之机默默取消计时、改成按件，或把固定额重复按数量累计。

计时/固定也支持主价属性条件、专属/通用表选择和缺价报错。建单预览展示费率与公式，不在尚无实际分钟时伪造工资总额。报工计价方式必须取本单锁价，不按当前表或当前产品猜。

## 五、数据结构与接口收口

实施先同步02完整SQL Server DDL、实体和33接口，再编码：

- `base_operation_price_list`新增pricing_type与合法值约束；头/列表/详情DTO及PC界面提供计价方式；原details.schemaVersion=2条件/组/行结构沿用，按计价方式校验允许内容。不另建“计时工价表”。
- 强类型任务报价增加明确schemaVersion、PriceType及表ID/编号/版本、日期、产品和当前工序属性、原价/扣价/换算、命中依据/预览指纹。类型不能由单价单位文字推断。
- `prod_work_order_operation.processing_price`及`prod_report.price_snapshot`继续作为新体系锁价/报工快照载体；统一新结构，不做旧280/旧工价JSON兼容分支。不用负任务ID冒充旧RuleId。
- `salary_statement_item.rule_id`是旧工价来源字段，删除；增加可空`price_list_id BIGINT`记录新价目表ID，写入时新结算必须有值。原price_type、duration_minutes、unit_price、wage_coeff、amount/deduct_amount等工资事实保留；来源仍以自包含报工快照为准，不因当前表改价或停用而改金额。
- `ReportPriceSnapshot`与纯金额计算器不再依赖BasePriceRule。可以复用数值公式，但删除旧匹配/优先级算法，不能为保留旧方法签名构造伪BasePriceRule对象。
- `/api/PriceRule`及旧priceRule导入/template停止提供；旧URL不得仍可写入，404/410均可，不重定向旧请求为另一个写操作。删除mode接口、迁移状态接口及前端模式切换。
- 价目表`/preview`、创建/复制工单、报工预览、补报、工资/MCP读取统一协议。取消旧手选ProcessingChoice的baseId/values协议，工单只传工艺值和自动预览指纹；服务端选表选行。
- 旧OperationPricingService中承载新锁价的部分可重构保留，但改名/分责要清楚；旧config/bases/groups手选模型、旧API和旧数据列不保留。

## 六、明确删除和保留的数据库对象

**必须物理删除：**

1. `base_price_rule`表（含其索引、实际外键/视图等依赖，先核实再按依赖顺序处理）。
2. `base_product_operation_pricing`表（不再需要双模式开关）。
3. `base_operation.pricing_config`列（旧280手选加工价）。
4. `salary_statement_item.rule_id`列（旧工价来源），由上一节新来源字段替代。

**必须保留：**`base_operation_price_list`、产品/路线/工序/部门/人员/单位/自定义字段、`sys_user.wage_coeff`、工单/报工/开工记录、工资单/工资明细以及新快照载体；`base_product.price`是产品扩展属性，不是工价。不得扩大为清空工资、工单或基础资料。

### 删库表的执行约束

- 用户已明确“不需要历史兼容”，不得再以历史兼容为理由留下旧表或旧取价开关。该依据不等于可以连接任意库删表。
- 输出唯一目标（服务器实例+数据库名+开发环境标识）、旧表/列和依赖清单，并与本次开发目标核实一致后执行；不从默认连接串猜目标，不顺带处理客户库和其他账套。
- 若目标库中有演示/测试旧配置或引用旧快照的测试工单，列出精确记录及依赖。已明确属于本次可丢弃测试记录的，按依赖倒序处理；来源不明的保留并阻断破坏性步骤，不能整库清空或以删工资单解除依赖。用户无需为已明确的本地开发范围重复批准，但不明数据不能靠猜。
- 不自动把旧规则转成新价格（旧表按部门/人优先级与新表头模型不等价）；不迁入未确认价格、不套0价。需要演示资料时按新契约明确重建。
- 新建库的EF模型/当前DDL/Seed/EnsureCreated不再含旧对象。存量开发库通过**新的显式增量迁移/清理脚本**删除旧对象，SQL用OBJECT_ID/COL_LENGTH核对并保证重复执行安全；不篡改已运行旧迁移历史。
- **破坏性DROP不放进普通DbCompat启动路径。** 启动只检查已完成413升级，发现旧结构时明确报需要执行413升级，不自动DROP。删除当前建表/补列/Seed中的重建逻辑，重启不能把旧表/列建回来。
- DDL和前置条件在事务内处理，失败回滚、报上下文；不得禁用约束、吞异常或先DROP再发现工资路径仍引用。
- 当前只拟定文档；后续开工可实施已核实本地开发库清理。本指令不自动授权远程服务器更新、客户库DDL或部署；已上线环境仍遵守增量部署与配置保护规则。
