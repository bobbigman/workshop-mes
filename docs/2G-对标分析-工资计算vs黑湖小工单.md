# 2G · 对标分析 —— 工资计算：本系统 vs 黑湖小工单

> 触发：66 号执行暴露设计缺陷——赵江陵工资单漏计「包装」后已确认，被「仅草稿可删除、无撤回」锁死，API 无法修正。用户指出这是设计 bug，要求对标黑湖小工单的工资计算。
> 日期：2026-09-24　依据：黑湖小工单官方公开资料（xiaogongdan.cn 产品页与计件工资指南）。

---

## 1. 本系统现状与暴露的缺陷（事实）

| 项 | 本系统（车间MES）行为 |
|---|---|
| 工资生成 | `Salary/generate` 只取 `review_status=1 AND settled_flag=0` 的报工，匹配工价算 amount/deduct/total |
| 工资确认 | `Salary/{id}/confirm` 后 `status=1`，关联报工 `settled_flag=1` 永久冻结 |
| 删除限制 | `DELETE /api/Salary/{id}` 仅草稿可删；已确认单返回「仅草稿可删除」 |
| 撤回 | **无**撤回/重算接口 |

**缺陷案例（66 实测）**：赵江陵复核时包装漏通过 → 生成工资单只含 4 条（19.60）→ 确认后冻结。事后补通过包装、尝试删单重算 → 被「仅草稿可删除」拦截，**金额永久定格、无法 API 修正**。

**根因**：本系统把「工资核算」做成了**一次性不可逆动作**（确认即冻结、无撤回）。核算若漏算/错算/工价配错/复核延迟，已确认工资单无法重算 → **违反 AGENTS.md「钱要可追溯可重算」红线**。

## 2. 黑湖小工单工资计算链路（官方口径）

1. **工价库**：管理端维护工序计件单价；支持按产品、工序、班组、时间段多维配置；支持阶梯工价、困难溢价、技能系数（大工1.2/小工0.8）、班组分摊比例。
2. **扫码报工**：工人扫工单二维码，录良品+报废数，系统自动记报工人、工序、产量、时间。
3. **工价版本**：**工价变更时按报工时间自动适用对应版本**——变更前的报工仍按原价计，不被覆盖、不重算。
4. **质量扣减**：不良品自动扣减计件数量/金额（与报工关联）。
5. **防超报**：累计良品达计划量自动锁死工序，杜绝虚报。
6. **工资报表**：报工数据自动汇成工资报表，**可按日/周/月、工人/班组/产品/工序任意时间点生成与导出**；工人手机实时查累计产量与预估工资。
7. **定位**：生产协同工具，工资是「统计/报表」口径，非专业发薪闭环（社保个税仍需专业薪资系统）。

## 3. 逐维对比

| 维度 | 黑湖小工单 | 本系统（车间MES） | 谁优 |
|---|---|---|---|
| 工资形态 | 可重算的**派生报表**，随时重生成 | 一次性**确认即冻结**的工资单 | 黑湖 |
| 事后纠错 | 报表重算即可，漏算/错算可修正 | 已确认即冻死，无撤回，API 不可修 | 黑湖 |
| 工价版本 | 按报工时间适用版本，历史不被覆盖 | 有 EffectiveFrom/Priority 配置，但确认后工价变更对已结算无效且不可重算 | 黑湖 |
| 防错兜底 | 源头防超报+留痕可追溯 | 复核流程 + 确认冻结兜底 | 各有 |
| 复核把关 | 公开资料未见「班组长复核」作工资强前置 | 有完整报工复核（通过/驳回） | 本系统 |
| 发薪闭环 | 仅统计报表，不涉发薪 | 有工资单确认（结算意识） | 本系统 |
| 报工留痕 | 带时间戳+操作人，可追溯 | 报工落快照含当时单价（32号设计），可追溯 | 相当 |
| 工人透明 | 手机实时查产量/预估工资 | 待确认（本系统是否开放工人查工资未验证） | 黑湖 |

---

## 4. 结论

**黑湖把工资当作「基于报工的可重算结果」，纠错成本低；本系统把工资当作「确认即不可逆的结算单据」，把纠错路径堵死了。** 本系统的复核与确认是增强（防虚报、有结算意识），但「确认即冻结 + 仅草稿可删 + 无撤回」的三连设计，牺牲了可重算性，正是赵江陵事件的根因。

黑湖的防错主要靠**源头**（防超报、报工留痕、工价版本），不靠「事后冻死」兜底——这一点本系统应借鉴：防错前置，纠错留门。

---

## 5. 修复建议（对齐黑湖，最小改动）

按「正确性优先、钱可追溯可重算」红线，建议解除不可逆：

1. **新增撤回/重算能力**：`POST /api/Salary/{id}/revoke`（撤回已确认工资单，回滚关联报工 `settled_flag=0`、状态回草稿），或放开已确认单删除（带审计留痕）。撤回后可重新 `generate`。
2. **保留复核**（本系统优势）：工资仍只算 `review_status=1`；驳回不计钱逻辑不动。
3. **工价版本坐实**：确认报工按报工当刻工价快照（已有基础）匹配，工价变更不影响历史报工口径；撤回重算时仍用快照，保证可复算。
4. **防错前置不动摇**：防超报、留痕保留，不依赖「冻结」兜底。

> 落地方式：按分工，多隆先落「优化指令」给 Cursor 实现 `revoke` 接口与测试；本文为对标依据。
