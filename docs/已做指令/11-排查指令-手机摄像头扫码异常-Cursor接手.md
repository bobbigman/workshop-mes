交接日期：2026-09-22。状态：**Cursor 已接手并定位根因 + 完成修复（0922-10），待真机验收。**

### Cursor 接手结论（2026-09-22，最终）

**根因（已由真机日志锁定，非猜测）**

- 0922-9 真机「复制日志」完整时间线证明：`getUserMedia` 成功 → `video.play()` 成功（日志出现「视频已开始播放」）→ 在 `QrScanner.start()`（二维码识别引擎启动）**这一下页面被重建**（导航类型 `back_forward`），随后出现「上次摄像头请求未完成」。
- 即：摄像头、权限、HTTPS、视频播放全部正常，崩溃点只发生在 `qr-scanner@1.4.2` 启动识别引擎时。
- `qr-scanner` 的识别引擎通过 `new Worker(URL.createObjectURL(new Blob([…纯 JS 解码器…])))` 创建；百度浏览器内核对这套 Blob-URL Worker 支持不稳，页面直接闪退。
- 独立页 `camera-check.html` 完全正常，正是因为它**根本不加载 `qr-scanner`**。

**最终修复（`scan.vue` 0922-10）：改用 jsQR 主线程纯 JS 解码，彻底移除 Worker**

1. 依赖由 `qr-scanner` 换成 `jsqr@1.4.0`（MIT，纯 JS、主线程，无 Worker/WASM/Blob/OffscreenCanvas）。
2. 启动链路：`getUserMedia` → `video.srcObject` → `video.play()` → 进入 scanning 并启动 `setInterval`（120ms）识别循环，`drawImage` + `getImageData` + `jsQR()` 解码，命中即停流跳转报工页。
3. 保留并保留此前正确的生命周期/会话/后台/迟到授权处理；诊断记录改为 `localStorage`（崩溃/重载不丢），含「复制日志」按钮与 UA/可见性采集。
4. 构建产物不再含 `qr-scanner-worker.min-*.js`（Worker 已彻底移除）。

自动化：`node --test --test-isolation=none src/utils/scanPayload.test.mjs src/views/h5/scan.test.mjs` → **27 通过**；`npm run build` 通过；5175 已提供含 0922-10 的最新构建（jsQR 已打包、无 Worker）。

## 4. 当前代码做过哪些改动

主文件：`frontend/src/views/h5/scan.vue`。请完整阅读，不要只读本摘要。

1. 页面直接请求 getUserMedia，保留原始错误，再把已获得的视频交给 QrScanner；当前请求为 `video: true, audio: false`。
2. 启动超时 15 秒，权限、设备缺失、占用等错误提示常驻页面。
3. 为取消、重试、离页和迟到的授权添加会话标记与流释放处理。
4. 每轮启动通过 `videoKey` 更换 video 节点，以避免旧 QrScanner 延迟清理影响新流。**当前在请求权限前递增 key，这是独立页不存在的差异，未做真实浏览器验证。**
5. video 在进入 scanning 状态前使用 `opacity: 0`，带 autoplay、muted、playsinline；QrScanner.start() 完成后才显示。独立页视频可见，直接调用 video.play()。
6. 等待授权且没有 scanner 时，visibilitychange 不取消请求；授权返回若仍在后台则关闭流。pagehide 会使会话失效、释放流。
7. 移除无效的 QrScanner.WORKER_PATH 与多余 worker URL 引入；Vite 打包库内动态导入的本地 worker。
8. 诊断通过站点查询参数开启，兼容 0922-3/4/6/7；显示当前版本 0922-7。记录保存在 `sessionStorage['h5.scan.diagnostics']`，最多 20 条，包含 pending 标记。
9. `recordCameraStep('点击打开…')` 是 startCamera 的第一条语句，早于重入检查、权限检查及 getUserMedia。最新反馈连此行都没有，必须先定位事件接收/状态/页面实例或记录呈现，不能继续只改摄像头参数。
10. 诊断区域定高，启动按钮现在位于预览框上方；尚未得到真机按钮点击成功的验证。

## 7. Cursor 应如何接手

1. **先复核而非追加补丁。** 保存当前修改的可回退副本，审查扫码模板、事件绑定、响应式状态、视频节点更换及生命周期处理。区分原问题和排查过程中新增的复杂性。
2. **优先查最新“点击无记录”。** 使用真实浏览器/移动视口检查按钮实际命中元素、disabled、遮挡、触摸/点击派发、事件绑定与页面实例是否仍存活；确认日志写入是否异常或新实例替换旧记录。不要只继续增加模拟函数测试。
3. **对齐成功基线。** 独立页已验证 getUserMedia + video.play 成功；逐项比较扫码页的 DOM、Vue 更新、视频可见性、生命周期、开发客户端和扫码库初始化时序。一次验证一个关键差异，避免再同时改变多项。
4. **获取真实证据。** 如需手机协助，明确说明要区分的两个结论、一次测试应提供什么。优先让记录自动持久化/可导出，避免要求用户抢拍一闪而过的提示。任何新增采集仅限必要的技术信息，不记录账号、令牌、业务数据或视频。
5. **不要过早定根因。** 目前未证实的猜测包括：权限弹窗触发后台、后置约束兼容、Vite HMR 刷新、浏览器崩溃、按钮位置/遮挡。前面数次“修复”没有得到最终真机验收。
6. **根因确认后做最小修复。** 清理不再需要的诊断逻辑及阶段性 workaround，恢复清晰的页面结构与生命周期。若默认设备为前置，需要处理真实工单扫码可用性；不要为恢复后置优先再次引入未经验证的问题。
7. **验证并诚实交付。** 自动化、构建与手机验收分别记录。未获用户手机扫码成功证据时，不得写“已解决”。同步修订前面不准确或过时的说明。
