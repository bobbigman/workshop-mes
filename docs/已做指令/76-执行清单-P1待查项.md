## 第一部分 · P1 新建工单 500（删单后必现，需修复，根因已锁定）

### 现象（已实测，含稳定复现）
`POST /WorkOrder` 在**当天删除过工单后**稳定返回 `code=500，msg=操作失败，请稍后重试；若多次出现请联系管理员`。本次系统自测反复建/删后，新建已 **100% 失败**（`workorder_test.mjs` 实测）。并非"偶发"，而是**只要当天删过工单，下次新建即撞号**。

### 根因（已读源码 + 日志铁证锁定）
文件：`backend/Services/WorkOrderService.cs`，方法 `NextOrderNoAsync`（659–672 行）：

```csharp
var date = DateTime.Now.ToString("yyyyMMdd");
var prefix = "GD" + date;
var count = await _db.WorkOrders.CountAsync(o => o.FactoryId == factoryId && o.OrderNo.StartsWith(prefix));
return prefix + (count + 1).ToString("D3");
```

**问题**：自动单号 = `prefix + (当天单号数量 Count + 1)`，用**数量推断序号**。当天只要删除过工单（删除是真删，`Count` 随之变小），再新建时生成的序号就会与**仍存在的存量单号重复** → 撞唯一索引。

日志铁证（`backend/logs/mes-error-20260927.log`）：
```
SqlException: 不能在具有唯一索引 "IX_prod_work_order_factory_id_order_no" 的对象 "dbo.prod_work_order" 中插入重复键。重复键值为 (1, GD20260927008)
```
→ 撞唯一索引抛 `DbUpdateException` → 被外层吞成 `code=500 操作失败`。

### 修复建议（Cursor 选其一，优先 A）
- **A（推荐）**：单号序号改用「当天 `Max` 序号」而非 `Count`：取 `OrderNo` 以 `prefix` 开头、形如 `GD20260927003` 中尾号的最大值 `+1`；或查询当天尾号集合取最大，避免删除导致序号回退。注意 `Count` 是 `int`，超 999 也会溢出。
- **B**：生成后查重，若重复则序号 `+1` 重试（循环最多 N 次仍冲突再抛）。
- 自定义单号（`dto.OrderNo` 非空）已有「工单号不可重复」校验（664–665 行），不受影响。

### 验收清单（Cursor 修完逐项自证）
1. 当天**先删一个工单**，再连续新建 3 个，均 `code=0`，单号**不撞号、不与存量重复**。
2. 新建单号连续（如 `GD20260927xxx` 无跳号/无重复）。
3. 复现步骤回归：反复「新建→删除→新建」10 次无 500。
4. 原自定义单号去重校验不回归。
5. **复现现场已保留**：当前测试库 F001 新建工单必现 500（因当天已大量建/删），修好单号生成后此现象即消失。

## 第二部分 · 软删语义（澄清，无需修复）

### 初版结论（有误）
测试表初版把 7 个基础模块 + 工单的删除判为「疑似软删」（列表已移除、GET 单个仍 HTTP 200）。

### 核实结论（已坐实）
删除为**真删**，无软删设计：
- 工单：`WorkOrderService.DeleteAsync`（636–647 行）级联 `RemoveRange`（Reports / WorkOrderOperations / CustomFieldValues）+ `Remove(WorkOrder)` + `SaveChanges`。
- 删除后 `GET /WorkOrder/27` 实测返回：`HTTP 200 + code=1，msg=工单不存在，data=null`。

### 误判成因（登记，避免再犯）
自测脚本只按 **HTTP 状态**（`chk.status === 200`）判断"单个仍可查"，未看业务 **code**。本系统业务错误用 `HTTP 200 + code=1` 表示（统一 `ThrowHelper.Biz`），因此"工单不存在"被误读为"仍可查"。

### 处置
- **无需修复**。删除逻辑正确。
- 提示前端：所有接口判断请以业务 `code`（0=成功）为准，勿依赖 HTTP 状态码。
- 自测脚本 `tests/selfcheck/crud_selfcheck.mjs` 的"删除后验证"判据应改为"`GET 单个 code=1`（不存在）且列表无残留 = 通过"，防止再次误判（多隆后续可顺手改，本次已勘误到 docs/74）。
