# 129-优化指令：企微消息推送「事件触发 + PC 规则配置」（对标方向）

> 状态：**代码已实现，自动验证完成（30 项）；现场联调待验**（2026-10-02）。用户本轮“完成代码”授权实施；分钟级投递、沿用 `LicenseFeature.WechatDueAlert`，未执行客户部署或真实企微发送。
> 目标：报工或工单状态变化后自动提醒指定企微接收人；配置简单、业务提交不等待企微网络请求、失败可查。
> 依据：`docs/01`、`docs/02`、`docs/06`，以及 `docs/已做指令/20-优化指令-企业微信预警.md`、`docs/已做指令/75-优化指令-企业微信交期预警自动定时推送.md`。

## 1. 首版范围与取舍

| 项 | 建议方案 |
|---|---|
| 事件 | 报工提交成功、工单开始、工单结束；不单独增加“不良品上报”事件，避免一次报工重复通知 |
| 条件 | 报工：每次都提醒，或本次报工不良率严格大于阈值；开始/结束：无附加条件 |
| 配置端 | PC 现有「微信预警」入口增加「消息规则」区域，Vue3 + Element Plus；不做 H5 配置页 |
| 接收人 | 直接填写企微 UserId，多人用 `|` 分隔；规则留空沿用本厂默认接收人；不建 MES 用户映射 |
| 模板 | 提供默认文案 + 有限占位符；不做脚本、SQL 条件、公式引擎或拖拽编辑器 |
| 投递 | 建议 SQL Server 持久待发记录 + Windows 计划任务短周期投递；不引入 BackgroundService、外部队列或新调度框架 |
| 时效 | 业务提交时生成待发记录；建议任务每分钟执行，正常网络及无积压时分钟级送达。首版不承诺秒级即时 |
| 保留能力 | 原交期预警、测试推送、手动推送及 `cron-push` 契约保留；交期扫描不是事件补发机制 |

**核心纠偏**：直接 `await SendWecomTextAsync` 会等待网络与重试；不等待的 `Task.Run`/`async void` 会受请求作用域释放、进程回收影响。原稿同时要求“不阻塞、不引入后台任务、即时可靠投递”，无法直接落地。本稿推荐持久待发 + 现有部署方式的计划任务；若必须秒级送达，应先另定执行器方案。

企微是可选外部通道，默认关闭；MES 主流程仍在局域网独立运行。实施需服务器能访问企微 API、客户已配置自建应用及有效接收人，不要求把 MES 暴露到公网。

## 2. 实施前现状与落点（审稿依据）

- `backend/Services/WechatAlertService.cs`：`SendWecomTextAsync` 为私有方法，发送使用设置中的 `ToUser`。抽取共用发送能力时支持接收人参数，禁止为了某条规则修改或临时保存全厂设置。
- 当前网络/技术失败最多尝试 **3 次（含首次）**，企微业务错误直接抛出，不重试；不是“所有失败重试 3 次”。
- `SendAsync` 先查去重/日限额，发送成功后才写 `sys_wechat_alert_log`。现状不能当作并发抢占或可靠待发记录使用；禁用直接跳过，配置不完整/超限会抛错。
- `docs/02`：成功日志唯一键为 `(factory_id, alert_key, send_date)`，`alert_key` 长度 128；可将规则与事件身份编码入键，无需单为去重新增 `rule_id` 列。
- 业务落点是 `ReportService` 与 `WorkOrderService`，不能只在 Controller 挂钩，否则其它调用入口会漏掉。报工内有 `RecalcStatusAsync` 自动更新工单状态，批量补报也有独立事务；开工时逐一核实新增报工、批量补报、人工状态变更及自动状态变化的事务边界。
- 管理接口现有授权特性为 `LicenseFeature.WechatDueAlert`；本稿沿用该档，不开新档；仍须遵守原有正式期/试用期限制。规则管理仅管理员、本厂隔离，接收提醒不赋予报工权限。

## 3. 事件与条件契约

| 事件 | 触发条件 | 事件身份 |
|---|---|---|
| `report_created` | 新增报工记录已取得 ID、明细写入完成，在事务提交前落待发；批量补报按实际新增记录生成 | 报工记录 ID |
| `order_started` | 事务前状态 0 → 最终状态 1；包含报工自动变化 | 持久化的本次状态变更 ID |
| `order_completed` | 事务前状态 0/1 → 最终状态 2；包含人工结束及自动完成 | 持久化的本次状态变更 ID |

- 状态取 `docs/02` 的 0未开始、1执行中、2已结束、3已取消。比较同一业务事务开始前与提交前的最终状态，不监听每次属性赋值或 `SaveChanges`。0 → 2 只发结束，2 → 1 撤回不发开始，重算中短暂写入 1 再回到 2 不发事件；撤回后再次 1 → 2 属于新结束事件。
- 同值保存、失败回滚、幂等请求未新增记录，不生成事件。一次报工可同时产生报工事件及状态事件；各自匹配对应规则。多人报工按实际新增记录分别匹配规则，数量使用该条记录，不按整个请求合计，首版不合并通知。
- 报工修改、删除、撤回、审核本身不发“报工成功”提醒；若这些操作确实满足上述事务前后转换，按同一状态转换规则处理，不新增其它事件类型。
- 不良率 = 本次 `DefectQty / (GoodQty + DefectQty) × 100%`（数据库字段为 `defect_qty`，不存在 `BadQty`），不是工单累计不良率；分母为 0 时阈值规则不命中，全部提醒规则仍可命中。按 decimal 原值比较，显示保留两位小数；10% 阈值下恰好 10% 不命中。
- 阈值只能在 0～100 之间；其它事件不允许保存阈值。规则名称必填，事件类型固定枚举，不接受自由表达式。
- 可用占位符：`{工单号}`、`{产品编号}`、`{产品名称}`、`{事件时间}`；报工事件额外支持 `{工序}`、`{良品数}`、`{不良数}`、`{不良率}`。保存时拒绝未知或不适用于该事件的占位符。
- 无启用规则、条件不命中、全厂通道关闭或不具备授权：不生成待发记录，业务正常；启用规则时校验通道配置与最终接收人，禁止 `@all`。

## 4. 持久化、去重与失败处理（建议契约）

已同步 `docs/02`、实体映射、`DbCompat` 与独立增量脚本。另加 `sys_wechat_send_attempt` 作为所有发送共用的额度/尝试账本，记录人工核实与重试历史；没有额度账本，仅依赖成功日志无法计入未知和部分成功请求。采用项目现有 EnsureCreated + DbCompat 升级方式，未引入第二套迁移机制。

- 新增 `sys_wechat_alert_rule`：本厂、规则名称、事件类型、条件类型、阈值、接收人覆盖值、模板、启停、更新时间。采用固定列，禁止含糊的自由 `condition` 字段；字段类型、长度、默认值与 CHECK 约束在 `docs/02` 定义。
- 新增 `sys_wechat_alert_delivery`：本厂、规则 ID、事件类型/身份、发生时间、工单/报工引用、接收人和消息快照、待发/处理中/成功/待重试/失败/结果未知/部分成功/取消状态、累计尝试次数、下次执行时间、领取租约、脱敏错误及完成时间。唯一约束 `(factory_id, rule_id, event_type, event_id)`；状态事件 ID 在业务事务内生成并固化至对应待发记录，同次转换命中多规则共用该 ID，投递与手动重试读取原值；不为首版另建通用事件中心。工单状态转换须串行或使用并发校验，防止两个请求把同一转换各记一次。工单/报工引用仅供定位，不允许通知记录阻断原业务删除；实体删除后保留快照。规则首版只停用，不提供物理删除。
- 命中的待发记录与业务写入使用同一事务：提交后才可被领取；回滚时一同回滚。待发落库失败必须带上下文抛错并回滚，不能宣称报工成功却丢失提醒；“不等待企微”不等于“数据库失败也成功”。
- 去重粒度为**规则 + 业务事件**，不是“工单 + 日期”：同一事件重复处理仅一条待发；同一工单的两笔不同报工可以分别提醒。成功日志键建议 `event:{ruleId}:{eventType}:{eventId}`，限制在 128 字符内；日后重试不能因跨日生成新投递。
- 投递任务使用数据库原子领取与租约，防止重叠任务同时发送；进程退出后租约过期可恢复。领取条件是租约为空或已过期，领取后持有有效租约才处理；请求超时须短于租约，必要时续租，过期持有者不得继续写终态。发送成功后的状态与成功日志一同提交；只插成功日志无法避免发送前竞争。租约过期时：未进入发送阶段可重新领取；已进入发送阶段则转结果未知。企微已接受但本地提交失败同样转结果未知，禁止自动重发。
- 事件推送与交期推送共享工厂 `daily_limit`；统一发送入口对所有发送入口使用同一按厂互斥机制并原子预占额度，旧入口也要遵守同一并发约束。达到上限保留待发至次日，不写成发送成功。额度按客户部署时区自然日统计，一次消息发送请求占一份额度（多人仍一份）；明确未接受可释放预占，成功、部分成功及结果未知保留占用，不能只数成功日志。后续重发也须预占。测试推送沿用原来不计额度的行为，并在页面说明。
- 任务发送前重新检查授权、全厂开关及规则启用状态：暂时关闭通道保留待发，规则停用则取消该规则未发送项；恢复后不重算旧事件。编辑规则只作用于后续事件，已有待发保留接收人与内容快照。
- 事件投递每次领取只执行一次消息发送，累计最多 3 次（含首次），可安全重试的明确失败间隔 1、5 分钟；不叠加现有内部 3 次重试。获取 Token 失败且尚未调用消息发送可重试；消息请求发出后的超时、断连、响应无法解析及其他不能证明未接受的情况进入结果未知。配置/接收人明确错误直接失败；其它企微返回码只有经官方契约确认可安全重试才自动重试，禁止笼统把技术异常都重发。
- 网络超时可能出现“企微已收到但本地未知”，数据库租约也不能保证外部严格一次。此类结果标为“发送结果未知”，暂停自动重发，由管理员核实后处理；明确失败可手动重试并沿用同一待发记录。
- 成功指企微 API 确认接受，不代表用户已读；需检查接收人部分失败，不能仅凭 `errcode=0` 宣称全部接收人成功。部分失败不得整批重发成功接收人。
- 异常遵守 `ThrowHelper` 与脱敏日志规范：请求网址、报文、返回、factory/rule/event 上下文可追查，Secret/Token 不出现在页面或日志；计划任务按厂隔离失败并返回明确汇总；批次基础设施失败返回明确失败，逐条错误落库可查，不用全成功响应掩盖失败。

## 5. PC 与接口交付

- 「微信预警」内提供规则列表、新建、编辑、启停；表单随事件切换条件，提供默认模板、占位符说明及消息预览，明确不良率口径与分钟级时效。
- 提供简洁发送记录：事件、规则、时间、接收人、状态、失败原因；失败项可重试；结果未知项提供「确认已发送」与「确认未发送后重试」，记录操作者、时间、核实说明，前者不伪造企微成功日志。部分成功项只允许对失败接收人重试，保留成功/失败接收人及各次结果。重复点击重试不得重复排队。不做独立监控大屏。
- 建议接口：`GET/POST /api/WechatAlert/rules`、`PUT /api/WechatAlert/rules/{id}`、`GET /api/WechatAlert/deliveries`、`POST /api/WechatAlert/deliveries/{id}/retry`；统一返回 `ApiResult`，权限、长度及工厂归属在服务端校验，factoryId 从 JWT 取得。
- 新增 `POST /api/WechatAlert/dispatch-events` 供 Windows 计划任务调用；沿用 `X-Cron-Token` 校验，空/错拒绝，有限批次领取并返回成功/失败/待重试/跳过统计。不要把交期扫描改成高频执行。
- 复用现有企微发送与配置能力，补 DI、脚本及部署说明；试用厂清理同步清理规则和待发记录。更新只交增量包，不覆盖服务器 `appsettings*.json` / `start.bat`。

## 8. 实施步骤（仅供后续获授权开工时使用）

按序执行，每步有可判定的前置与收尾；第 3～5 节是契约，步骤不得另改口径。

1. **数据契约**：当获授权实施 → 先同步 `docs/01` 的事件业务口径、`docs/02` 的规则/待发 DDL，再对齐实体与增量升级脚本；已有定义则核对后复用。收尾：字段、状态、唯一约束及租约/领取索引一致；不覆盖已有客户配置。
2. **业务事务**：当业务写入及明细已保存、ID 已取得但事务尚未提交 → 比较事务前后状态、匹配规则并落待发，再一并提交；不满足条件不落待发。收尾：回滚零待发、多人报工口径一致、0 → 2/2 → 1/重复重算符合第 3 节。
3. **投递**：当到期且可原子领取 → 持有效租约、重查开关/授权/规则、预占额度后发送；当限额用尽或通道暂关/授权暂不可用 → 保留待发等待恢复；当规则停用 → 取消。明确失败、部分成功、未知结果按第 4 节处理。收尾：重叠任务、跨日、进程退出与成功后落库失败均不盲目重发。
4. **PC 与接口**：按第 5 节交付规则、预览、发送记录和受控处理；不做 H5 配置。收尾：管理员/本厂校验覆盖查询、修改、重试、核实；CronToken 空/错拒绝，任务不向调用者泄露 Secret/Token。
5. **验收与交付**：当以上完成 → 按第 6 节逐项验收；任一不过返回对应步骤修正。收尾：权威文档、升级脚本、计划任务说明一致，记录真实验证结果后再移动至「已做指令」。


## 9. 实现与验证记录（2026-10-02）

- 数据：规则、待发、尝试账本三表，固定列/CHECK/唯一键/领取索引；`docs/02` 与 `backend/scripts/129-wechat-events.sql` 同步。独立脚本和启动升级同源，可重复执行；旧成功日志迁入额度，不重复计数。
- 业务：ReportService 的新增/多人/批量/修改事务，WorkOrderService 人工状态/修改计划后重算，ReviewService 退回后重算；工单行锁内重载状态、提交前生成事件。幂等补报优先重放回执，结束工单的同批重试不再误报错误。接收提醒不替代部门报工权限。
