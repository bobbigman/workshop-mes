> 执行人：Cursor。所有命令在 Windows + PowerShell 下执行；后端为 .NET 8（`WorkshopMes.exe` / `dotnet run`）。

## 一、现象（用户侧看到的）

电脑端进入「生产管理 → 报工复核」页（URL：`https://localhost:5173/#/review`），**每次**都弹出红色"业务失败"提示；下方列表正常显示"暂无数据"（待复核本来一条没有，空列表不是问题）。用户已**重启后端，问题依旧**。

## 二、已确证的事实（现场抓包结果，勿推翻）

1. **"业务失败"是前端兜底文案，不是后端返回的真实原因。**
   来源：`frontend/src/api/http.js` 两处：
   - 第 12 行：`const text = tip || '业务失败'`
   - 第 39 行：`const tip = body.msg || '业务失败'`
   即：**只要某个接口返回 `code≠0` 且 `msg` 为空/缺失，前端就统一显示"业务失败"**，把真因盖住。

2. **报工复核页 `frontend/src/views/review/index.vue` 的 `onMounted` 同时调用两个接口：**
   - `GET /api/Review/pending`（列表）
   - `GET /api/Review/order-options`（工单下拉）

3. **实测两个接口返回（浏览器会话内 XHR 抓包，已带登录态）：**
   - `GET /api/Review/pending?orderNo=&userName=&reviewStatus=0&page=1&pageSize=50`
     → HTTP 200，`Content-Type: application/json`，body=`{"code":0,"msg":"ok","data":{"list":[],"total":0}}`（**正常**）
   - `GET /api/Review/order-options`
     → HTTP 200，`Content-Type: text/html`，body=**前端 `index.html`**（**异常！接口被当作静态页/兜底页返回**）

4. **绕开前端直连后端 8080（不带 token）再次验证：**
   - `http://127.0.0.1:8080/api/Review/pending` → HTTP **401**（路由命中，被 `[Authorize]` 拦，属正常）
   - `http://127.0.0.1:8080/api/Review/order-options` → HTTP **200 + text/html**（**路由未命中，被 `MapFallbackToFile("index.html")` 兜底返回**）

   结论：**后端没有注册/匹配 `/api/Review/order-options` 这条 action 路由**。pending 能命中，order-options 不能，两者同一控制器 `ReviewController`。

5. **后端路由结构（`backend/Program.cs` L258-262）：**
   ```
   app.UseStaticFiles();
   app.MapControllers();
   ...
   app.MapFallbackToFile("index.html");
   ```
   标准写法。`MapControllers` 应在 `MapFallbackToFile` 之前优先匹配到 controller action；命中不了 action 才落到 fallback。

6. **源码里有该接口：** `backend/Controllers/ReviewController.cs` 含
   `[HttpGet("order-options")] public Task<ApiResult<List<ReviewOrderOptionDto>>> OrderOptions()`，
   且 `backend/Services/ReviewService.cs` 的 `OrderOptionsAsync` 已实现（只查待复核工单下拉）。
   `ReviewController.cs` 修改时间 **2026-10-01 08:16**。

7. **后端进程证据：** 8080 端口监听进程 `WorkshopMes.exe`（PID 5300），启动时间 **2026-10-01 07:41:55**，
   早于控制器 08:16 的修改时间。曾怀疑是旧进程未加载新代码；但**用户已重启后端，问题仍在**，
   故"未重启"不再成立，需按下面推测继续查。

## 三、推测的故障点（按可能性从高到低，逐条验证）

> **核心矛盾**：同一控制器、同样 `[Authorize]`，`pending` 命中、`order-options` 不命中（返回 HTML）。
> 这说明该 action 确实没进后端路由表。

- **推测①（最可能）：运行中的后端程序里根本没有 `order-options` 这条路由。**
  子因：
  - ①a 运行的是**旧编译产物/旧发布包**，不含 08:16 新增的 action（用户"重启"可能启动的是旧 exe / 旧 dll，而非重新编译的最新代码）。
  - ①b 前端 5173 代理目标是 `127.0.0.1:8080`，但用户重启的可能是**另一个实例/端口**（如 8081 的 B 档），8080 上仍是旧进程。
  - ①c 编译**没生效**：改了 `.cs` 但没重新 `dotnet build` / `dotnet run`，跑的还是旧 dll。
  验证方法：查当前监听 8080 的进程对应的工作目录/可执行文件，比对其中 dll（如 `ahu.MicrosoftMes.Services.dll`）与 `bin/Release` 或源码编译产物的时间戳；或直接看该进程加载的程序集是否含 `OrderOptions`。

- **推测②：路由模板/命名导致 action 未被映射。**
  子因：
  - ②a `[HttpGet("order-options")]` 中的连字符 `-` 在路由里本应合法，但需确认没有其它同路径 action 冲突、或大小写/模板拼写不一致（前端请求 `order-options`，控制器模板也是 `order-options`，已核，基本排除）。
  - ②b `ReviewController` 因某种原因（如 DI 依赖、DTO 序列化问题）在**该 action 上抛了路由期异常**被跳过——但 pending 正常，此可能性低，仍需用路由调试确认。
  验证方法：开启 Swagger（若 `EnableSwagger=true`）查看 `/swagger/v1/swagger.json` 中 `/api/Review` 下到底有哪些路径；或用 `dotnet` 路由端点列表核对。

- **推测③：请求被静态文件/中间件抢先截走。**
  子因：`UseStaticFiles()` 在 `MapControllers()` 之前，若 `wwwroot` 下存在 `api/Review/order-options` 同名静态路径（基本不可能），会被抢先。可能性极低，作排除项。
  验证方法：`Get-ChildItem -Recurse` 检查 `backend/wwwroot` 下有无 `api/Review` 目录。

- **推测④：实例隔离/工厂守卫中间件**（`InstanceFactoryGuardMiddleware`、`McpGateMiddleware`、`RoleGuardMiddleware`）
  对 `order-options` 特殊处理拦截。可能性低，但确认一下 `RoleGuardMiddleware` 未把该 GET 路径错误放行成 HTML。

## 四、执行步骤（原子 + 条件判断）

### 步骤 1：锁定 8080 后端进程的真实程序与编译时间
- 当：需要确认运行中的后端是否含最新代码
- 做：

  - `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` 拿 ExecutablePath/CommandLine（若为空，用 `Get-Process -Id <pid> | Select Path` 或管理员权限再试）；
  - 记录该 exe 所在目录、启动时间、目录内 `ahu.MicrosoftMes.Services.dll` 等程序集的 **LastWriteTime**。
- 当：程序集时间 ≥ 2026-10-01 08:16 且确实含最新代码 → 跳到步骤 2；
- 当：程序集时间早于 08:16，或目录/端口与前端代理目标不符 → **判定为旧产物，重新编译并重启**（见步骤 5），做完直接到验收。

### 步骤 2：核对前端代理目标与后端实际监听
- 当：需要确认 5173 到底转发到哪个后端
- 做：
  - 读 `frontend/vite.config.js`：默认 `target: http://127.0.0.1:8080`（B 档才是 8081）；
  - 确认 8080 进程 = 步骤 1 找到的进程。
- 当：前端代理指向 8080 而 8080 不是新代码 → 回到步骤 1 处理；

### 步骤 3：核对后端路由表是否含 `order-options`
- 当：需要确认后端有没有这条 action 路由
- 做：
  - 若 `EnableSwagger=true`：访问 `/swagger/v1/swagger.json`，检索 `/api/Review/order-options`；
  - 否则：直接 `GET http://127.0.0.1:8080/api/Review/order-options`（不带 token），看返回是 401 还是 200 HTML。
- 当：swagger 或 401 显示路由存在 → 后端路由正常，问题转向前端/代理，跳到步骤 4；
- 当：返回 200 HTML（路由不存在）→ **确认是后端没这条 action**，重点查编译产物/运行版本（步骤 1），或查控制器路由注册。

### 步骤 4：核对前端 http.js 兜底逻辑（本次一并加固）
- 当：后端路由修复后，仍想根治"业务失败"无信息量的体验

  - 确认新进程启动时间 > 编译完成时间。
- 当：编译报错 → 修到编译通过为止，不要带着错误启动；
- 当：用户部署的是发布包目录（如 `publish/`）→ 需按 `docs/59-执行指令-部署更新铁律-appsettings不覆盖.md` 走增量更新，**只覆盖程序文件，绝不覆盖服务器 `appsettings*.json` / `start.bat`**。
