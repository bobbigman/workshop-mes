# 优化指令：批量补报前道工序（管理员一键补齐未报满工序）

> 状态：已实现  
> 依据：`docs/2A 班组长手动批量报工完整方案（deepseek网页版）.txt`（已纠偏）；PRD §4.12 报工；`docs/14 防超额报工`；现实现 `ReportService` / `ReportController` / `frontend/src/views/report/index.vue`  
> 目标：流水线小厂常在末道认真报数、前道漏报导致看板进度假低。让管理员一次把「尚未报满的工序」按同一良品数补齐，并在提交时把「谁做的」分配掉，落地伙伴要的「末道认 1000、前面也算 1000、谁做的自己分」  
> 原则：**只做人工点一下的补报，永不做自动倒冲**。瘦身版：仅管理员、仅 PC、不建分摊/冲销/日志表、不加设备追踪、不加后台开关矩阵。

---

## 0. 与 DeepSeek 原方案的关系（为什么瘦身）

| 原方案项 | 本项目现状 | 本期处理 |
|---|---|---|
| 班组长 / 车间主管角色 | `sys_user.role` 只有 1 管理员 / 2 生产人员，班组长属 docs/16 第二期 | **仅 role=1**，不扩角色 |
| 计件分摊明细表 + 冲销 + 工资挂起 | 工资报表为简单版，无分摊概念 | **不做表**；谁做的在提交时拆人写进 `prod_report.user_id` |
| `report_type/batch_id/operator_id/device_type/device_id` | 报表/看板只按 `SUM(good_qty)` 聚合 | 只加一个可空 `batch_no` 做幂等/追溯 |
| 批量操作日志表 | 审计可由报工行 + `batch_no` 得出 | 不建日志表 |
| 返工工单 / 已结案 / 质检开关 / 行业开关 | 数据字典无这些概念 | 删；状态按现有 0/1/2/3 校验 |
| 冲销（反向报工记录） | 项目约定「只改数不删」 | 不做冲销；改错走 `PUT /Report/{id}` |
| PDA 独立端 / 扫工序码 | H5 + PDA 键盘枪，扫的是工单号 | 不做独立 PDA |

**保留正确点：** 纯人工触发、一次填一个数量给多道工序各生成正规报工行、事务提交、数量 ≤ 各待报工序剩余的最小值、不良默认 0 事后补。

## 1. 功能定位

- **名称：** 批量补报前道工序（界面文案「一键补报未完工序」）。
- **入口：** PC 报工页（`/#/report`）工具栏一个按钮，**仅管理员可见**。
- **做什么：** 输入工单号 → 展示未报满工序 → 填一个统一良品数 N（可选按工序拆人）→ 一次提交为每道未报满工序生成正规 `prod_report` 行。
- **不做什么：** 不做末道自动倒冲、不做班组长角色、不做分摊/冲销/审计日志子系统。

## 2. 自主拍板（实现前定死）

| 项 | 决定 | 理由 |
|---|---|---|
| 角色 | 仅 `role=1`；`role=2` 无入口、无接口权限 | 与现 PC 代报一致；不引班组长 |
| 终端 | 首版仅 PC；H5 有现场需求再开 | 控制范围 |
| 待报工序来源 | 有任务行用 `prod_work_order_operation`；无任务行兜底产品路线 `routing_steps`，plan 兜底工单 `qty` | 与 `LoadTasksAsync`、`SubmitAsync` 口径一致 |
| 剩余可报 | `planQty - SUM(good_qty)`（按 operationId）；仅处理「剩余 > 0」的工序 | 与 docs/14 一致，不良不占上限 |
| 数量校验 | `N > 0` 且 `N ≤ min(各待报工序剩余可报)` | 防超额硬规则 |
| 「谁做的」 | 提交时拆人：每道待报工序至少一条报工；未指定则 `user_id = 当前管理员`；指定则按人拆数量，每人 `goodQty > 0`，每道工序合计 = N | 替代分摊表，产量直接落到人 |
| 部门权限 | 批量走管理员豁免（`role=1` 不校验部门） | 与现 PC 报工一致 |
| 字段 | `prod_report` 仅加可空 `batch_no NVARCHAR(32)`（同一次操作同一号） | 幂等 + 追溯，成本最低 |
| 幂等 | 同 `order_id + batch_no` 已存在则直接返回成功，不重复插入 | 防弱网重试重复生成 |
| 并发 | 事务内重查剩余 + 对工单行加 `UPDLOCK` | 防两人同时补报超数 |
| 不良 | 批量行 `defect_qty = 0`；事后走现有 `PUT` 补；**不**自动减良品、**不**做「良品+不良≤计划」 | 完全遵循 docs/14 |
| 自动倒冲 | **永不做**，必须点按钮留痕 | 避免无痕难追责 |

## 4. 后端改动

### 4.1 DTO（`backend/Services/ReportService.cs` 内新增）

```csharp
public class BatchReportDto
{
    public long OrderId { get; set; }
    public int GoodQty { get; set; }                       // 本次统一补报良品数
    public string? BatchNo { get; set; }                   // 幂等批次号（前端生成，可选）
    public List<BatchReportOperationDto>? Allocations { get; set; }  // 可选：谁做的拆分
}

public class BatchReportOperationDto
{
    public long OperationId { get; set; }
    public List<BatchReportUserDto> Users { get; set; } = new();
}

public class BatchReportUserDto
{
    public long UserId { get; set; }
    public int GoodQty { get; set; }
}

public class BatchReportResultDto
{
    public int OperationCount { get; set; }   // 补了几道工序
    public int ReportCount { get; set; }      // 生成了几条报工
}
```

### 4.2 服务方法 `BatchReportAsync`

接口 `IReportService` 加：

```csharp
Task<ApiResult<BatchReportResultDto>> BatchReportAsync(BatchReportDto dto, long currentUserId);
```

实现要点（顺序校验，异常全走 `ThrowHelper.Biz` 带上下文）：

1. 取当前用户，`role != 1` → 拒绝「无批量补报权限」。
2. 取工单 `order`，不存在 → 拒绝；`status ∈ {2,3}` → 拒绝「已结束/已取消不可补报」。
3. `GoodQty <= 0` → 拒绝「补报良品数必须大于 0」。
4. 幂等：若 `BatchNo` 非空且同 `order` 已存在该 `batch_no` → 直接返回成功（`OperationCount=0, ReportCount=0`），不再插入。
5. 收集待报工序：
   - 有任务行：`WorkOrderOperations.Where(t => t.WorkOrderId == order.Id)`。
   - 无任务行：走产品路线 `RoutingSteps`（按 `seq`），plan 兜底 `order.Qty`。
   - 对每道工序算 `alreadyGood = SUM(prod_report.good_qty)`，`remain = planQty - alreadyGood`；只留 `remain > 0`。
   - 无待报工序 → 拒绝「所有工序已报满」。
6. `GoodQty > min(remain)` → 拒绝「本次数量超过工序 X 剩余可报 Y」（带具体工序名/剩余）。
7. 拆分校验：`Allocations` 若提供：
   - 每个 `OperationId` 必须是待报工序之一；其 `Users` 每人 `GoodQty > 0`，且每道工序 `SUM(Users.GoodQty) == GoodQty`。
   - 未在 `Allocations` 出现的待报工序，默认生成一条 `user_id = 当前管理员`。
8. 事务内：
   - `BeginTransactionAsync`；对工单行加 `UPDLOCK`（`SELECT ... FROM prod_work_order WITH (UPDLOCK) WHERE id = @p0`，用 `FromSqlRaw`）。
   - 锁内**重查**各待报工序 `remain`，再校验一次 `GoodQty ≤ min(remain)`（防并发）。
   - 为每道待报工序的每个分配人 `INSERT ProdReport`（`FactoryId = order.FactoryId`，`OrderId`，`OperationId`，`UserId`，`GoodQty = 分配数`，`DefectQty = 0`，`DefectId = null`，`DurationMinutes = 0`，`BatchNo`，`ReportTime = DateTime.Now`）。
   - `SaveChangesAsync`；调用 `RecalcStatusAsync(order)`；`CommitAsync`。
9. 返回 `BatchReportResultDto { OperationCount, ReportCount }`。

> 关键：待报工序来源、plan 兜底、`SUM(good_qty)` 口径必须与 `SubmitAsync` / `LoadTasksAsync` 完全一致，不要另写一套。

### 4.3 控制器 `ReportController`

```csharp
[HttpPost("batch")]
public Task<ApiResult<BatchReportResultDto>> Batch([FromBody] BatchReportDto dto) =>
    _reportService.BatchReportAsync(dto, JwtHelper.GetUserId(User));
```

> 注意 `[HttpPost("batch")]` 需与 `[HttpPost]`（`Submit`）区分，ASP.NET 按模板匹配，无冲突。

## 5. 前端改动（`frontend/src/views/report/index.vue` + `api/prod.js`）

### 5.1 API（`frontend/src/api/prod.js`）

```js
export const batchReport = (data) => http.post('/Report/batch', data)
```

### 5.2 报工页（PC）

- 工具栏加按钮【一键补报未完工序】，仅管理员可见（与现有 `+ 报工` 并列）。
- 新弹窗 `batchDlg`：
  1. 输入工单号 → `getOrderByNo` 加载（复用现有 `getOrderByNo`，返回 `tasks` 已含 `planQty/doneQty/defectQty`）。
  2. 展示**待报工序列表**：`tasks.filter(t => t.planQty - t.doneQty > 0)`，列：序号、工序名、计划、已报良品、剩余可报。
  3. 统一良品数 `batchQty`（`el-input-number`，默认值 = `min(剩余)`，`:max = min(剩余)`）。
  4. 「谁做的」分配（核心，首版必做）：
     - 每道待报工序一行，默认一条「当前管理员」占全部 `batchQty`。
     - 可展开为该工序增行拆人：下拉选人（`getUserList` from `@/api/sys`）+ 每人数量；**每道工序合计必须 = `batchQty`**，前端实时校验并提示。
     - 生成 `allocations: [{ operationId, users: [{ userId, goodQty }] }]`；未改动则该项不传（后端默认挂管理员）。
  5. 提交 → `batchReport({ orderId, goodQty, batchNo, allocations })`；`batchNo` 前端生成（如 `crypto.randomUUID()`）。
  6. 成功提示「已为 X 道工序生成 Y 条报工」，关闭弹窗并 `load()` 刷新列表。

## 6. 明确不做（本期）

| 项 | 原因 |
|---|---|
| 自动倒冲（末道一报自动完成前道） | 无痕、难追责；必须人工点按钮留痕 |
| 班组长 / 车间主管角色 | docs/16 第二期，现在扩会拖垮交付 |
| 计件分摊明细表 + 冲销 + 工资挂起 | 半套薪资系统，超范围 |
| 批量操作日志表、设备类型/ID 追踪 | 报工行 + `batch_no` 已够追溯 |
| 后台开关矩阵（行业开关/补不良期限/单次最大数量） | 配置项堆叠，交付成本高 |
| H5 / PDA 独立端、扫工序码 | 首版仅 PC；PDA 即浏览器扫工单号 |
| 「改不良自动减良品」「良品+不良≤计划」 | 与 docs/14 冲突 |
