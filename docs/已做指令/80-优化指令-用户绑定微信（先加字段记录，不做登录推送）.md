## 2. 背景与现状

老沈要求"用户能绑定微信"。经核对源码，`SysUser` **没有**微信字段（`SysWechatAlertSetting` 是企业微信交期预警设置，与"用户绑微信号"是两回事）。

**边界（已拍板）**：本轮**只做最小闭环**——给用户加一个「微信号」字段，PC 用户页能填/改/显，能按微信号查。**不做**微信扫码登录、**不做**给工人微信推消息（那要对接微信开放平台/公众号/企业微信的 OAuth 与消息接口，是另一量级，另排）。边界外本轮不做、不承诺。

---

## 3. 任务清单（原子步骤，每步带条件判断）

### 步骤 6-1 · 确认数据字段 ✅

检查 `backend/Models/SysModels.cs` 的 `SysUser` 与 `docs/02-数据字典.md` 的 `sys_user` DDL。

- **当**已有微信相关字段（如 `WechatId`/`OpenId`）→ 直接沿用，跳到步骤 6-2。
- **当**没有 → 在 `SysUser` 加**可空** `WechatId`（NVARCHAR(64)），`AppDbContext` 映射 `wechat_id`，`docs/02-数据字典.md` 同步补列；**已有库**在 `DbCompat.cs` 幂等 `ALTER TABLE … ADD wechat_id`（本项目无 EF Migrations，EnsureCreated 不改已有表）。不改既有字段、不动既有数据。  
  → 判定：原先无字段；已加实体/映射/字典/DbCompat。

### 步骤 6-2 · 后端读写 ✅

检查 `UserService.cs` / `UserController.cs` 的创建/更新 DTO 与查询返回。

- **当** DTO 已含 `WechatId` → 确认创建/更新/查询三处都读写该字段，缺哪补哪。
- **当**未含 → 在 Create/Update DTO 加可空 `WechatId`；创建/更新时保存，查询（列表/单个）返回带上。字段为空即存空，**不强制填、不做格式硬校验**。  
  → 判定：原先未含；Create/Update/List 已读写；空白规范化为 null。

### 步骤 6-3 · PC 用户页 ✅

检查 `frontend/src/views/user/index.vue`。

- **当**已有「微信号」输入框/列 → 核对可用、对齐后端字段名。
- **当**没有 → 新增/编辑表单加「微信号」输入框（可空），列表加一列展示；保存后能查回。报错提示走人话。  
  → 判定：原先没有；表单+列表列已加（`wechatId`）。

### 步骤 6-4 · 按微信号查询（可选） ✅

- **当**需要"按微信号找用户"→ 用户列表加「微信号」搜索过滤。  
  → 按 §2「能按微信号查」做了：Keyword 覆盖微信号，占位「姓名/账号/微信号」。
- **当**暂不需要 → 本步跳过，在汇报里注明"未做按微信号筛选"。

### 步骤 6-5 · 校验与容错 ✅

- 微信号**可为空**，空值正常保存、正常登录，不拦截。
- 保存/查询失败：人话提示 + 服务端日志留上下文（位置+做什么失败），**不吞错**；不把堆栈/SQL 原样回浏览器。

## 4. 红线（违反即返工）

- **不破坏三条业务硬规则**；不改既有用户账号/密码登录逻辑。
- **不做**微信扫码登录、**不做**微信消息推送（边界外，本轮明确不做）。
- 微信号**不强制填**；不改既有用户数据、不批量回填。
- 失败原因可读、带上下文（位置+做什么失败），不吞错；敏感上下文只写服务器日志。
- 若改 DDL/字典，同步 `docs/02-数据字典.md`；不引入外部依赖。
- 每项验收必须**实测**再勾，禁止凭印象打勾。

## 5. 完工定义（Definition of Done）

1. `sys_user` 有微信字段（新增或复用），字典已同步。
2. PC 用户页能填/改/显「微信号」，空也能保存、不影响登录。
3. （如做步骤 6-4）按微信号能查到用户。
4. 未接微信 OAuth 登录/消息推送（边界外，未做属正常）。
5. 前端 `npm run build`、后端编译通过；向用户交付说明改动文件与验收结果。
