# 205-优化指令：未审核报工可手机撤回改 + 修改留痕（对标黑湖）

> 状态：已做（2026-10-02）
> 一句话目标：给报工加"**未审核可撤回改 + 修改留痕**"：工人在手机端可撤回/修改自己**待复核**（review_status=0）的报工；已通过/已结算的仍走管理员退回。修改保留痕迹，堵乱改口子。
> 依据/拍板：2026-10-02 多隆老同学与黑帽大人对标黑湖（"未审核可编辑/删除/撤回，已审核需管理员驳回，保留修改痕迹"）后拍板；放 `docs/未做指令/205`。

## 取舍（定死）
| 项 | 定案 |
|---|---|
| 做/不做 | 做**未审核（待复核）手机可撤回改** + **修改留痕**；已通过/已结算**保持现状**（管理员退回） |
| 复用还是另写 | 复用 `prod_report.review_status`（0待复核/1已通过/2已退回）判断；复用电脑端改数逻辑（`04-报工与复核·报错数量怎么改`） |
| 谁可改 | 待复核：**报工人本人**手机可撤改（管理员仍可）；班组长/管理员照旧 |
| PC / H5 | 撤改入口在 **H5（Vant）** 报工记录；电脑端（Element Plus）同步支持本人撤改 |
| 留痕 | 新增报工修改记录（谁改、何时、原值→新值），可追溯 |

## 已核实现状（勿重复做）
- 已有：`prod_report.review_status`（0待复核/1已通过/2已退回）；`settled_flag`（0未结算/1已结算冻结）。（知识库 4.3/5）
- 已有：电脑端管理员改数流程：已通过先退回→修改→重复核；已结算不能改（`04-报工与复核`）。
- 已有：手机端无历史改数页。
- 缺口：待复核报工**本人手机不能撤改**；**无修改留痕记录**。

## 改动点
- 数据模型（**改 docs/02**）：
  - 新增**报工修改日志**表（report_id、修改人、原良品/不良/原因/时长、新值、修改时间、来源）——用于留痕。
- 后端：
  - 撤回/修改接口：当 `review_status=0`（待复核）且 `settled_flag=0` → 允许本人/管理员改良品、不良、原因、时长；修改后仍 `review_status=0`。
  - 当 `review_status≠0`（已通过/已退回）或 `settled_flag=1` → 拒绝直接改；已通过先走退回流程（现状），已退回改后回待复核。
  - 每次修改写一条**修改日志**（留痕），不覆盖历史值。
  - 权限：生产人员仅能改**自己**的待复核报工；管理员/班组长按现状（班组长限本组）。
- 前端 H5（Vant）：
  - 报工记录（本人、待复核）加【撤回/修改】入口 → 改数量提交 → 提示"已更新，待复核"。
  - 非待复核/他人记录不显示撤改入口。
- 前端 PC（Element Plus）：本人待复核报工同步支持撤改；可查看该条修改日志。
- 文档：改 `docs/02`（修改日志表）；同步 `SupportDocs/04` 或 `08` 说明。

## 不做 / 边界
- **不做**已结算报工的手机撤改（仍冻结，需管理员特殊处理）。
- **不做**"撤销报工删除记录"（保留记录+留痕，只改数量，避免追溯断链）。
- **不做**短信/推送通知（企微预警默认关）。
- 修改日志表结构由 Cursor 对照数据字典定，不臆造。
