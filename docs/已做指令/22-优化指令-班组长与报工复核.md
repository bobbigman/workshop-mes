## 1. 功能定位

| 项 | 内容 |
|---|---|
| 名称 | 班组长 + 报工复核（双轨） |
| 入口 | PC「报工复核」页；用户管理可选角色「班组长」 |
| 做什么 | 工人/班组长报工 → 待复核；进度/防超额立刻算；班组长或管理员通过/退回；生产报表只汇总已通过 |
| 不做什么 | 派工、异常上报、工序停滞预警、反确认已通过以外的复杂状态机、自动推企业微信「待复核」（H5 复核见 docs/104） |

**双轨一句话：**

```
报工提交 ──► 进度看板 / 防超额 / 工单状态（含待复核+已通过）
         └─► 复核通过 ──► 生产报表入账（及日后工资）
         └─► 复核退回 ──► 不占进度；工人改数后回到待复核
```

## 2. 自主拍板（实现前定死）

| 项 | 决定 | 理由 |
|---|---|---|
| 角色值 | `1` 管理员 / `2` 生产人员 / `3` 班组长 | 最小改动；不引入角色表 |
| 班组长能登录 | **可登录 PC**（与 PRD 旧「仅管理员上电脑」冲突，以本指令为准，收尾改 PRD） | 复核是管理动作，首版 PC |
| 班组长权限 | 可：报工（同工人规则）、复核本组、只读工单/看板/生产报表、改自己的待复核/已退回报工。不可：基础数据 CRUD、删工单、批量补报、用户/部门管理、工价/工资 | 介于 1 与 2 之间 |
| 「本组」范围 | 班组长部门集合 ∩ 报工人部门集合 **非空** 则可复核该条；`department_id` 快照优先，空则用报工人当前部门关联 | 无班组表时用现有部门 |
| 管理员 | 可复核**全厂**任意报工；批量补报仍仅 role=1，且补报行直接 `review_status=1` | 管理补录视为已入账 |
| 提交时初始状态 | `role=1` 提交（含 batch）→ `1已通过`（reviewed_by=本人, reviewed_at=now）；`role=2/3` 提交 → `0待复核` | 少打扰管理员自测/代报 |
| 字段 | `review_status` TINYINT、`reviewed_by`、`reviewed_at`、`reject_reason` | 见 docs/02 |
| 历史行 | DbCompat 加列 `DEFAULT 1`（已通过） | 避免上线后报表清空 |
| **进度轨**（下列全部） | 只统计 `review_status IN (0,1)`，**排除 2** | 退回后不再虚增进度 |
| 进度轨清单（必须改全） | `ReportService` 防超额 SUM、`RecalcStatusAsync`；`WorkOrderService` 所有 GoodQty 汇总/任务进度；看板 `BoardAsync` 的 DoneQty 与顶部 TotalGood/TotalDefect | 漏改即双轨失败 |
| **入账轨** | `ReportStatService.ProductionAsync` **仅** `review_status=1` | 生产报表=入账 |
| 报工列表 Query | 返回 `reviewStatus` 等字段；默认看全部，可筛状态 | 便于核对 |
| 修改规则 | `settled_flag=1` 仍禁改（为 21 预留）。除此之外：`1已通过` → 禁止改数（要改先退回）；`0/2` → 报工人本人或管理员可改；工人改后若原为 2则变 0，若原为 0保持 0；清除 reviewed_* / reject_reason | 闭环 |
| 退回 | 必填 `reject_reason`（1～256 字）；status→2；进度立即不含该条 | 对齐 UC-02 |
| 通过 | status→1；写 reviewed_by/at；清空 reject_reason | |
| 批量通过 | 支持 ids 列表；跳过非待复核；班组长只能批本组 | 小厂效率 |
| 终端 | **PC + H5 复核**（H5 见 docs/104）；班组长手机/平板可审 | 交付节奏：先 PC 后 H5，104 已补齐 |
| RoleGuard | role=2：现有白名单 + **允许 `PUT /api/Report/{id}`**（改自己的待复核/退回）。role=3：role=2 白名单 + 复核 API + `GET` 生产报表/看板/报工列表 | 工人退回后才能改数 |
| 与 docs/21 | **先 22 后 21**；21 生成工资单必须 `review_status=1 AND settled_flag=0` | 依赖正确 |
| 不做反审核 | 已通过若要改：管理员/班组长「退回」即可（已通过→2），再改数。不做单独「反确认」按钮 | 状态机保持 3 态 |

## 3. 数据（DDL，SQL Server）

> 权威在 `docs/02`。DbCompat 幂等摘要：

```sql
-- 角色注释无需改列类型；业务代码识别 role=3 即可

IF COL_LENGTH('prod_report', 'review_status') IS NULL
BEGIN
  ALTER TABLE prod_report ADD review_status TINYINT NOT NULL
    CONSTRAINT DF_prod_report_review DEFAULT 1;  -- 历史默认已通过
  -- 新插入由应用写 0 或 1；DEFAULT 1 仅保护未显式赋值的旧路径
END
IF COL_LENGTH('prod_report', 'reviewed_by') IS NULL
  ALTER TABLE prod_report ADD reviewed_by BIGINT NULL;
IF COL_LENGTH('prod_report', 'reviewed_at') IS NULL
  ALTER TABLE prod_report ADD reviewed_at DATETIME2 NULL;
IF COL_LENGTH('prod_report', 'reject_reason') IS NULL
  ALTER TABLE prod_report ADD reject_reason NVARCHAR(256) NULL;

IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = 'ix_report_review')
  CREATE INDEX ix_report_review ON prod_report(factory_id, review_status, report_time);
```

**注意：** 加列后，应用层 `SubmitAsync` 必须**显式**赋 `ReviewStatus`，不能依赖 DEFAULT（否则工人报工也会变成已通过）。

实体 `ProdReport` 增加对应属性；`AppDbContext` 映射列名。

工资相关列（`product_id` 等）若 21 未做可暂不建；**本期只加复核四字段**。若 02 里工资列已写但库未建，**不要在本期 DbCompat 里顺手建工资表**（避免抢 21）。

## 4. 后端改动

### 4.1 提交 / 批量 / 修改（`ReportService`）

- `SubmitAsync`：按 §2 设 `review_status`；防超额 SUM 加 `&& (r.ReviewStatus == 0 || r.ReviewStatus == 1)`。
- `BatchReportAsync`：每行 `ReviewStatus=1`，`ReviewedBy=admin`，`ReviewedAt=now`。
- `UpdateAsync`：按 §2 冻结/退回后可改；改完重置复核字段。
- `RecalcStatusAsync`：GoodQty 汇总排除 `review_status=2`。
- `QueryAsync`：DTO 增加复核字段；查询可选 `reviewStatus`。

### 4.2 复核 API（新建 `ReviewController` + `ReviewService`，或挂在 Report 下）

推荐路由（RESTful，前缀 `/api`）：

| 方法 | 路由 | 说明 |
|---|---|---|
| GET | `/api/Review/pending?orderNo&userName&page&pageSize` | 待复核列表；班组长过滤本组；管理员全厂 |
| POST | `/api/Review/{id}/approve` | 单条通过；仅 status=0 |
| POST | `/api/Review/{id}/reject` | body `{ reason }`；仅 status=0 或允许从 1 退回 |
| POST | `/api/Review/batch-approve` | body `{ ids: number[] }` |

权限：role∈{1,3}；班组长校验本组。

退回已通过：允许（便于纠错）；若 `settled_flag=1` → 拒绝「已结算不可退回」。

### 4.3 聚合回改清单（逐项勾选）

| 位置 | 改法 |
|---|---|
| `ReportService` 防超额两处 SUM | 排除 status=2 |
| `ReportService.RecalcStatusAsync` | 排除 status=2 |
| `WorkOrderService` 任务进度 / LoadTasks / Recalc | 排除 status=2 |
| `ReportStatService.BoardAsync` DoneQty、TotalGood、TotalDefect | 排除 status=2（进度轨） |
| `ReportStatService.ProductionAsync` | **仅 status=1**（入账轨） |

### 4.4 RoleGuard / JWT / 用户

- `RoleGuardMiddleware`：实现 §2 白名单；role=3 单独分支（不是「非 1 就当工人」）。
- 凡 `user.Role != 1` 当管理员豁免的地方，复核权限要写成 `role==1 \|\| role==3`，报工部门校验对 role=3 **仍要校验**（班组长报工不豁免部门，除非同时是管理员）。
- `UserService` / 导入：允许 Role=3；非法 role 拒绝。
- `SeedData`：`wangban` → role=3。

### 4.5 前端可见角色

登录返回的 `role` 已有；前端根据 role 显示菜单：  
- 1：全菜单  
- 3：工单（只读或现有列表）、报工、报工复核、生产报表、看板；隐藏基础数据/用户/部门等  
- 2：仍走 H5 为主；若误开 PC，仅极简或提示去手机端（保持现状即可）
