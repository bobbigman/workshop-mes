## 1. 为什么要做（业务背景，一句话）

现在工资单上的"应发合计"只有计件工资那一块（截图上 331.4 / 352.5 / 376），离工人实际到手差了一整截：底薪、餐补、社保个税、罚款借支都没地方填。所以老板觉得"不真实"。

本次只加这一截，**不加公式、不让用户写表达式、不挂工单自定义字段**（那是后面的事，见 `docs/32` §4.2 留的 Excel 外挂口子）。

---

## 2. 加哪 5 列（字段就这 5 个，别多别少）

挂在 `salary_statement` 表上（**不是**挂在 `salary_statement_item` 明细行上——这 5 项是"人/月"维度的，不是"每条报工"维度的）：

| 列名（数据库） | 中文名（界面） | 类型 | 默认 | 说明 |
|---|---|---|---|---|
| `base_salary` | 底薪 | decimal(12,2) | 0 | 月底薪，不管干多少活都有的那笔 |
| `meal_allowance` | 餐补 | decimal(12,2) | 0 | 固定餐补 |
| `other_allowance` | 其他补贴 | decimal(12,2) | 0 | 交通补/高温补等杂项补贴 |
| `social_tax` | 社保个税 | decimal(12,2) | 0 | 公司代扣的社保+个税合计（**填正数**，系统会减） |
| `other_deduction` | 其他扣款 | decimal(12,2) | 0 | 罚款/借支/迟到扣款等（**填正数**，系统会减） |

> 精度与现有 `total_amount` / `amount` 对齐为 **DECIMAL(12,2)**（原稿写 18,2，与 `docs/02` 工资口径不一致，已改）。

**应发合计公式（钉死，别让用户改）：**

```
应发合计 = 计件合计（现有 salary_statement_item 的 Amount - DeductAmount 求和）
         + base_salary + meal_allowance + other_allowance
         - social_tax - other_deduction
```

- **计件合计**只读展示，不落库单独列（详情/导出时现算）。
- **应发合计**仍写回 `salary_statement.total_amount`（列表、确认后冻结口径都读这一列）。
- PUT 保存手工列后，**必须按公式重算并写回 `total_amount`**。

界面上把"计件合计"这一项也单独显示出来，让老板一眼看到：计件是多少、加了多少补贴、扣了多少、最后到手多少。

## 3. 业务操作流程（人话版）

1. 管理员进"工资报表"页，点【生成工资单】——跟现在一样，系统按周期把已复核报工算成计件合计，那 5 列默认 0，应发合计 = 计件合计。
2. 工资单状态是"草稿"时，管理员点【明细】进去，能看到 5 个输入框，把底薪、餐补、扣款这些手填进去，点【保存】；保存后列表上的应发合计同步变。
3. 填完核对无误，点【确认】——确认后这 5 列跟计件合计一样冻结，不能改。
4. **已确认要改手工项**：本版只能拦报错。`docs/67`（工资单撤回作废）**仍是未做指令**——67 语义是「作废整单 → 解冻报工 → 重新 generate」，不是「撤回到草稿保留手工列」。67 落地后：撤回作废 → 重新生成（手工列归 0）→ 再填 → 再确认。
5. 导出 CSV：每行一个人，列里要包含这 5 列 + 计件合计 + 最终应发。

**硬规则：**
- 只有草稿状态能改这 5 列；已确认状态调保存接口必须报错：`已确认工资单不能修改`（文案统一，不引用尚未落地的撤回按钮）。
- 这 5 列只录正数（或 0），不允许录负数——负数意味着"补回来"，逻辑上乱，第一版不做。后端要校验，前端也要拦。
- 生成工资单时这 5 列默认 0，不强制必填（老板可能这个月只发计件，没底薪）。
- 老的历史工资单（本次上线前已生成的）这 5 列就是 0，不用回填；应发合计与上线前一致。

## 4. 一键关闭开关（生产环境救命用）

在 `appsettings.json` 加一个开关（**示例键，增量包不覆盖服务器 appsettings**）：

```json
"Salary": {
  "AllowManualComponents": true
}
```

- `true`（默认，代码 `GetValue` 缺省也当 true）：前端显示这 5 列与保存按钮；API 接受保存。
- `false`：前端工资明细页**隐藏**这 5 列和"保存"按钮；后端保存接口直接拒绝（报错`该功能已关闭`）；查询接口这 5 列仍返回（值是多少就是多少）；**应发合计仍按公式算**（列在表里就在）。
- **前端如何得知开关**：`GET /api/Salary/{id}` 详情 DTO 增加 `allowManualComponents: bool`（读配置），不另开配置页/接口。
- 部署铁律（`docs/59`）：服务器 `appsettings*.json` 不覆盖；开关默认值写在代码里 = true，服务器要关就在服务器自己的 appsettings 里改。

## 6. API 改动

1. **改现有** `GET /api/Salary/{id}`：`SalaryDetailDto` 加 5 个手工字段 + `pieceworkAmount`（计件合计）+ `allowManualComponents`。
2. **新增** `PUT /api/Salary/{id}/components`：body 就是这 5 个 decimal。
   - 校验：单必须存在、属于本工厂、状态=草稿、开关开启、5 个字段都 >= 0。
   - 校验失败走 `ThrowHelper.Biz` / `BizUser`（业务提示语清晰）。
   - 成功：写 5 列 → 按公式重算 `total_amount` → 返回最新详情或 `{ totalAmount, pieceworkAmount }`。
   - 日志：成功/失败都写，带工资单 ID、改前改后、操作人 userId。
3. **导出 CSV**：每行加列——底薪、餐补、其他补贴、社保个税、其他扣款、计件合计、应发合计（顺序可读即可）；计件合计由明细现算。

**不要**新做一个"工资条模板"配置页。
