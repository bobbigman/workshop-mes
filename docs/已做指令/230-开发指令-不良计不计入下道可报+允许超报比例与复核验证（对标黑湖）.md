# 230-开发指令：不良品计不计入下道可报 + 允许超报比例与复核验证（对标黑湖）

> 状态：已做（2026-10-13）。代码已落地，后端已成功生成。验收勾选未打，现场未联调。
> 性质：正式生产（改报工/复核行为，新增配置持久化，涉及钱，需走重）
> 目标：让【管理员】在 PC 配置两个开关——「上道不良品计不计入下道可报」「每工序允许超报比例%」，使报工与复核按配置执行，与黑湖「报工数配比 + 超报审批」对齐。
> 依据/拍板：老沈 2026-10-13 两条意见（①不良品未控制到下道可报，加计入/不计入选项；②加允许超报比例，复核验证超报工序）；黑帽大人 2026-10-13 拍板：对标黑湖写死两个口径——「计入」=上道良品+上道不良（放大，排除扣减防双扣）、默认超报比例 0% + 不良不计入（与现状/黑湖一致）；超报比例结果非整数**向上取整**（ceil，件数不取半件，问卷选 A）；豆包扒黑湖官方（报工数配比=1+损耗率；超报拦截+标红+非管理员审批无法录入）。

## 〇、需求分析（为什么这样写，下次查这里）

### 背景
老沈提两条：①不良品没控制到下道可报数量（现在是没计入的）；②每道工序要有个"允许超报比例"选项，复核时验证超报工序。

### 黑湖怎么做（已扒官方，2026-10-13）
- **不良品**：黑湖默认**不计入**下道可报——规则「本道报工良品数 ≤ 上道良品数」（xiaogongdan.net/46 表单校验规则②，启用）。上道只移交良品，后道可报上限锁为上道良品数（官方"前道移交480良品→后道锁480"）。黑湖是**规则引擎式**：每条规则可开/关、字段可组合，要"计入/不计入"靠配不同规则。
- **超报比例**：黑湖报工上限 = **计划数 × 报工数配比**，配比 = 1+损耗率（官方例：10万件损耗10% → 配比1.1 → 可报11万）。配比内正常报不拦。
- **超报审批**：超过上限强行多报 → **系统拦截+标红报警，非管理员审批无法录入**（官方 FAQ）。即超报不是无限放行，是要管理员/复核批。

### 咱现状（源码已核，2026-10-13）
**两把独立尺子，别混成一个开关：**
- **尺子① 超本工序计划数（防超额）**：`SubmitAsync`/`UpdateAsync`/`BatchReportAsync` 里 `累计良品 + 本次 > planQty → 拦`。**死上限=计划100%，无损耗率可配、无超报审批**（docs/14 当时砍掉"损耗率可配置"）。
- **尺子② 后道超前道良品（上游校验）**：`EvaluateUpstreamAsync`（ReportService.cs 1401-1428）：limit = 上道**已复核通过良品**合计，occupied = 本道良品；超限 soft(默认，确认可超)/hard+清单硬拦，配置 `sys_report_upstream_setting`（docs/150）。**DefectQty 完全不参与**——即"不良没计入"。
- **复核页**：`ReviewService.FillQtyCheckAsync`（156-251）：首道 limit=工单计划数，非首道 limit=上道已复核良品；`QtyAbnormal = occupied > limit`；前端已有「数量异常」标签 + 「确认放行」弹窗（PC `review/index.vue`、H5 `h5/review.vue`）。
- **一键补报**：`BatchReportAsync`（docs/17，仅管理员/PC）同样走防超额与上游校验。

### 设计结论（写成指令的原因）
1. 老沈① = 给**尺子②**的 limit 加"上道不良计不计入"选项；黑湖默认不计入，咱默认也不计入，做开关对齐黑湖"规则可配"。
2. 老沈② = 给**尺子①**加"允许超报比例%"（=黑湖报工数配比），并在**复核页验证超报**（=黑湖超报审批：标异常+确认放行）。
3. 两个开关语义不同（一个管"超本道计划"，一个管"超上道良品"），**必须分开配置、分开实现**，防止执行方混成一个开关。

## 三、行为与口径（分叉写成显式条件）

### 尺子①：允许超报比例（`overrun_ratio`，%）
- 基数与报工现码一致：工序计划数（任务行 `plan_qty`），没有任务行才用工单数量。工单可以单独改工序计划，不能用工单数量顶替。
- 允许件数 = `ceil(基数 × (1 + overrun_ratio/100))`，**向上取整**，件数不取半件；`ratio=0` 时结果=基数（整数），与现在「超 1 个即拦」一致。
- 比例存整数 0–999（5 表示 5%）。负数或大于 999，保存时拒绝。
- 当 `overrun_ratio=0`（默认）→ 报工校验维持现状：`累计良品+本次 > 基数 → 拦`，超 1 个即拦。
- 当 `overrun_ratio>0` → `累计良品+本次 > 允许件数 → 拦`，提示「超出允许超报比例」；允许件数以内正常报工。累计口径不变：待复核+已通过，不含已退回。
- 批量补报剩余可报 = 允许件数 − 已报良品。`SubmitAsync` / `UpdateAsync` / `BatchReportAsync` 用同一上限。
- 复核：本道累计良品（待复核+已通过）> 允许件数 → 并入现有 `QtyAbnormal`，页面仍显示「数量异常」，确认放行沿用现弹窗。
- 首道复核上限改为上述允许件数（按工序计划，不按「工单数量×比例」）。非首道的上道上限仍走尺子②。任一把尺子超了就标「数量异常」，两条互不替代。
- 报工超比例是硬拦，soft 确认跳不过尺子①。复核页上能看到已超比例的待复核，是因为报完之后把比例改小，或把工序计划改小。验收按这条路径造数。

### 尺子②：上道不良计不计入（`count_defect`）
- 当 `count_defect=0`（默认）→ limit = 上道已复核通过**良品**合计（现状，黑湖同款）。
- 当 `count_defect=1` → limit = 上道已复核通过**良品 + 不良**合计（把上道报工总量当可流转量）。
- 落点：`EvaluateUpstreamAsync`（报工拦截/软确认）与 `FillQtyCheckAsync`（复核页 UpstreamLimit/QtyAbnormal）**两处同步改同一口径**，禁止一处改一处不改。
- 两把尺子独立判定：超尺子② 走现有 soft 确认（1002）/hard 拦截；超尺子① 走新比例拦截——**互不绕过**（soft 确认只能跳过尺子②，不能跳过尺子①；比例只放宽尺子①，不影响尺子②）。

## 四、止步线

- 后置项：不做黑湖"按工序/产品单独配比"；不做超报不计工资；不做智能预警/行为画像（docs/14 已砍）；不做超报自动倒冲/返工工单；不重建报工事务。
- 后置项不预建接口、开关、表、隐藏按钮、框架或测试。

## 五、验收（可观察，默认 3～5 条）

- [ ] ratio=0（默认）：计划100已报99，再报1通过；再报2被拦。工序计划与工单数量相同时，复核页超计划标数量异常。工序计划 80、工单数量 100 时，报工和复核都按 80，不按工单 100。
- [ ] ratio=5%：计划100，累计报105不拦；首道复核不标（非首道若同时超上道上限，尺子②仍标数量异常）。报106被拦，提示「超出允许超报比例」。
- [ ] count_defect=0：上道已复核 100良+10不良，下道可报上限=100；count_defect=1：上限=110；复核页 UpstreamLimit 同步变化（两处口径一致）。
- [ ] 复核验证超报：报工后把比例改小（或把工序计划改小），超比例工序在复核页标「数量异常」，可确认放行；比例内且未超上道则不标；hard 上游校验仍生效（两把尺子互不绕过）。
- [ ] 配置持久化+权限：仅管理员可改、立即生效；`docs/开发手册和方案/02-数据字典.md` 已同步新表；后端构建通过 + PC 配置页/H5 报工/复核页各走一遍。
