## 一、目标（说人话）

让报工**报得快、记得准、查得到、分得清**，且不加重工人负担。四件事合一条线：
1. **可靠性（地基）**：普通报工不能记重、不能记半笔——网络抖动、手抖多点一下，钱和数量都要对得上。
2. **多人分摊**：一群人共干一道工序（喷涂线/装配线），一人报总数、勾参与人，系统按人头自动平分，各人各记各账。
3. **代报工**：不会用手机/车间不让带手机的老工人，由主管替报，记到工人名下、进工人工资。
4. **手机"我的报工"只读页**：工人能查自己哪天报了啥、什么状态。

## 二、本期不做（边界，硬约束）

- 不做：手机工资中心、手机改数/补报/审批、自动绩效、个人效率排名、厕所/停工计时、设备联网、异常流转大改。
- 不做"各自填数量再合计"的手动精确分摊（本轮多人按黑湖自动平分）；代报各人数量可不同（那是代报，不是分摊）。
- 不改：客户不良扣款、工价、既有报工数据；不重做工资算法、复核、结算冻结、部门权限口径。
- 不强制开启派工/AI/企微推送；派工不成为报工前置条件。

## 五、模块 A：普通报工可靠性（地基，先做）

### A1 请求去重
- **当**：客户端无请求标识字段 → 普通报工增加"本次提交唯一标识"（前端生成；**同一批重试沿用同一标识，不得每重试换一个**）。
- 后端持久化去重：同一厂+同一用户+同一标识+同一内容，最多落一笔，返回同一笔回执；同一标识内容变了 → 明确拒绝。
- 去重必须落数据库（并发也不得写两笔），不能只靠按钮禁用或内存缓存；不复用批量补报 batch_no 语义。

### A2 事务完整
- **当**：主记录、扩展字段、状态更新非同一事务 → 改成**同一数据库事务**，任一步失败整体回滚，不留下半笔有效报工。
- **当**：报工使工单自动结束 → 以原请求重试仍返回原成功结果，不得误判成新报工。
- **当**：并发多笔各自超量 → 防超额检查与写入同事务，不得读到旧剩余量后合计突破计划上限。

### A3 结果回执与日志
- **当**：响应丢失但已落库 → 重试返回原记录（含记录 ID）。
- 成功回执带：记录 ID、工序、良品、不良、提交时间、复核状态；保持 ApiResult 包装与既有调用方兼容。
- 提交结果未知 → 保留输入与请求标识，提示"先查我的报工或按原请求重试"，不得说"肯定没保存"。
- 日志按 ThrowHelper/现有机制保留上下文（位置+做什么失败），异常必抛不吞，不把数据库异常当去重成功，关键业务字段不脱敏。

### A4 身份/账套
- 重放/重试仍校验登录身份与账套归属；回执不得泄露他人记录。

### A5 手机"我的报工"只读页
- **当**：手机工单页无本人报工入口 → 增加入口（首版放工单页，不挤底栏）。
- 默认今天；支持日期、工单号、分页；显示工单、产品、工序、良品、不良、提交时间、状态（待复核/已通过/已退回），退回显原因。
- 空/加载失败/加载中要区分，不把异常显示成"今天没有报工"；只读，无编辑/删除；不显示工资预估，不把待复核/已退回说成已结算。
- 接口建议独立本人查询（如 GET /api/Report/mine），factoryId/userId 取自登录上下文；不开放管理员工资接口或整个报工列表。

## 六、模块 B：多人分摊报工（黑湖式自动平分）

### B1 业务行为
- 工人报工勾选"多人共同报工"，勾参与人（**含自己**），填良品/不良总数 → 系统按参与人数**自动平分**；**余数归报工人**，各人合计=总数，一笔不丢、可追溯（3 人报 20 → 8/6/6，合计 20）。
- 参与人**只允许该工序报工权限部门内人员**；报工人本身必须已过部门权限校验；非权限人员勾了也拒绝，不静默剔除。
- 一次提交在同一事务内为每参与人生成独立记录；各条进各人工人工资/复核/进度。
- 进度/报表按**数量合计、不按条数**；多人分摊不改变原总数、不重复计数。
- 复核各自独立；退回一人不影响其余。
- 可选不强制：工人主动勾选才启用；单人报工原流程不变。

### B2 入参与实现
- **当**：需参与人入参 → `ReportDto` 增加可选 `List<long>? ParticipantUserIds`（空 = 单人原逻辑）。
- **当**：`ParticipantUserIds` 与 `Assignees` 同时非空 → 拒绝。
- **当**：非空 → 计算每人平分量（良品/不良同规则），逐人生成记录，同一事务提交；写 `share_batch_no`，`operator_user_id`=提交人。
- 去重标识、防超额、回执按**模块 A** 执行；防超额按总数一次校验，不得把分摊后的总量当 N 份各自超额。
- 分摊用 `share_batch_no` 追溯；不复用/不破坏补报 BatchNo/Allocations 语义；旧客户端无参与人字段按单人处理。
- **本期只做 H5**；PC 多人分摊后置。

## 七、模块 C：代报工（主管替工人报工）

### C1 业务行为
- 管理员/班组长在报工页进"代报工"模式，**为实际干活的工人代报**。
- 报工人=**被代报工人**（UserId=工人），不是操作的管理员；工资、进度、复核都归工人。
- 可一次代报多人、**各人数量不同**（A 120、B 80），逐行填，不要求统一数/平分。
- 权限硬规则：被代报人**必须在该工序报权部门**，否则拒绝；代报人：管理员不受限；**班组长按 docs/22「本组」**（班组长部门 ∩ 被代报人部门非空），否则拒绝。
- 复核态看**操作人角色**（非被代报人）：管理员 → 已通过；班组长 → 待复核。
- 同一事务生成多条记录，不留半笔；**记录操作人**（`operator_user_id`）可追溯，业务归属按被代报工人。
- 进度按数量合计、不按条数；复核各自独立。

### C2 入参与实现
- **当**：需代报入参 → `ReportDto` 增加 `List<ReportAssigneeDto>? Assignees`（空 = 现有单人逻辑）；每项 UserId、GoodQty、DefectQty、DefectId、时长。
- **当**：`Assignees` 与 `ParticipantUserIds` 同时非空 → 拒绝「分摊与代报不能同时提交」。
- **当**：Assignees 非空 → 逐被代报人生成记录，同一事务提交；任一不在报权部门 → 拒绝整次，不静默剔除；班组长再校验本组。
- 复用补报拆分（一键补报→按工序拆分到人）的落库/界面思路，只放开场景（正常报工可代报、各人数量不同、不限未报满），**不新建一套报工体系**。
- **本期只做 PC**；手机代报后置。

## 九、验收清单（逐项打勾）

### A 可靠性
- [ ] 同请求连续/并发/响应丢失重试，只有一笔报工，回执 ID 相同
- [ ] 同标识不同内容拒绝；新标识同数量可正常记下一批
- [ ] 第一笔使工单结束后，原请求重试返回原成功结果
- [ ] 主记录保存后、扩展字段/状态处模拟失败，无残留半笔
- [ ] 剩余 10，两笔不同请求并发各报 8，不得合计通过 16
- [ ] 单人 PC 报工、H5、批量补报、一键补报原流程无回归
- [ ] 手机"我的报工"当天/历史、退回原因、日期筛选、分页正确；换账号/账套看不到他人记录

### B 多人分摊
- [ ] 良品/不良按人数平分、余数归报工人，各人合计=总数，一笔不丢
- [ ] 各参与人独立记录、UserId 正确、进各人工人工资
- [ ] 进度/报表按数量合计不按条数，分摊后完成数/进度不变
- [ ] 非报权部门的人不能被选为参与人；选了也拒绝
- [ ] 分摊同事务，失败无"部分人报了部分人没报"半笔；重试不重复分摊
- [ ] 防超额一次校验，不被当 N 份各自超额

### C 代报工
- [ ] 代报后记到被代报工人名下、进工人工资；各人数量可不同
- [ ] 被代报人不在报权部门 → 拒绝，不静默剔除
- [ ] 管理员可代报；班组长受部门限制
- [ ] 代报有操作人记录，可追溯
- [ ] 代报同事务，失败无半笔；重试不重复
- [ ] 复核各自独立，退回一人不影响其余

可靠性与权限需后端集成验证（非文案镜像测试）；手机/PDA 与 PC 各走查一次完整主流程；记录实际测试结果，**不把静态阅读当运行验收**。
