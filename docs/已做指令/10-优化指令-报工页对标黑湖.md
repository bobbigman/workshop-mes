# 优化指令：报工页对标黑湖（进度摘要 / 继续报工 / 报工时长）

> 状态：已实现  
> 依据：黑湖截图（工单详情报工页：计划数/良品数/不良品数、生产人员、报工时长、继续报工+提交）+ `文字带时间.txt` + 现实现  
> 范围：移动报工端为主；PC 报工查询同步展示时长  
> 原则：对标黑湖核心体验，轻量落地；**不做**生产人员扫工牌、领料备注、工艺路线下拉（与现设计冲突或超范围）

## 2. 自主拍板（实现前定死，避免返工）

| 项 | 决定 | 理由 |
|----|------|------|
| P0 摘要口径 | **按当前选中工序**汇总，不是工单合计 | 对齐黑湖「选中洗菜后显示该工序计划/良品/不良」 |
| P0 计划数来源 | 取 `prod_work_order_operation.plan_qty`；无任务行时兜底用工单 `qty` | 与现有工序任务一致 |
| P0 良品/不良 | `SUM(prod_report.good_qty)` / `SUM(defect_qty)`，按 `order_id + operation_id` | 含历史所有报工；提交后刷新可见 |
| P0 是否改表 | **不改表** | 详情接口已有 tasks，补 `defectQty` 即可 |
| P1「继续报工」 | 提交成功 → Toast → **清空本次录入** → **刷新详情摘要** → **留在本页** | 对齐黑湖连报 |
| P1「提交」 | 提交成功 → Toast → **回扫码页** `/h5/scan` | 对齐「报完走人」 |
| P1 校验 | 两按钮共用同一套校验（工序必选、有不良必选原因、良品/不良 ≥0） | 不重复造轮子 |
| P2 存储 | `prod_report.duration_minutes INT NOT NULL DEFAULT 0`（总分钟） | 一条字段够算工资；UI 拆成小时+分钟 |
| P2 是否必填 | **非必填**，默认 0 | 黑湖可填 0；不拦现场快报 |
| P2 上限 | 单次 `0 ≤ duration_minutes ≤ 24*60`（1440） | 防误填；超限抛业务异常 |
| P2 修改报工 | `PUT /Report/{id}` 同步可改时长 | 与改良品数同一纠错路径 |
| 不做项 | 生产人员切换、领料备注、工艺路线下拉、删除报工 | 见 §1 |

## 3. P0 · 报工页进度摘要

### 3.1 后端

`WorkOrderDetailDto.Tasks`（`WorkOrderTaskDto`）现有：

- `operationId / operationName / seq / planQty / doneQty`（doneQty = 良品合计）

**补字段**：

```
defectQty   int   // 该工序已报不良品合计
```

`LoadTasksAsync` / 旧数据兜底路径：对 `prod_report` 按工序同时 `Sum(GoodQty)`、`Sum(DefectQty)`。

`GET /api/WorkOrder/by-no`、`GET /api/WorkOrder/{id}` 自动带上，**不新增接口**。

### 3.2 前端（`frontend/src/views/h5/report.vue`）

页面结构改为对标黑湖三层：

1. **标题区**：工单号（大字）+ 产品名  
2. **摘要卡**（随当前 `operationId` 变化）：  
   - 计划数 = 当前工序 `planQty`  
   - 良品数 = 当前工序 `doneQty`  
   - 不良品数 = 当前工序 `defectQty`  
   - 未选工序时：三项显示「—」或隐藏摘要数字  
3. **表单区**：工序、良品、不良、不良原因、（P2）时长  

交互：

- 切换工序 → 立即刷新摘要数字 + 重新拉不良品项下拉  
- 提交/继续报工成功后 → 重新 `getOrderByNo`，摘要更新

- [ ] 报 2 良品后点「继续报工」：摘要良品数 +2，无需离开页面  
- [ ] 换工序：摘要切到新工序数字  
- [ ] 未选工序：不误显示别的工序合计

## 4. P1 · 「继续报工」+「提交」

### 4.1 后端

**无改动**（仍走现有 `POST /api/Report`）。

### 4.2 前端

底部双按钮（移动端并排，样式可简）：

| 按钮 | 行为 |
|------|------|
| 继续报工 | `submit` → 成功提示 → 清空 `goodQty/defectQty/defectId/时长`（**保留当前工序**）→ `reloadDetail()` → 停留本页 |

共用 `doSubmit()`：校验失败两按钮都不放行；提交中 `submitting` 防双点。

## 5. P2 · 报工时长

### 5.1 数据模型

`docs/02-数据字典.md` / 实体 / DbContext / `DbCompat` 同步：

```sql
-- prod_report 新增列
duration_minutes INT NOT NULL DEFAULT 0   -- 报工时长（分钟）；0=未填
```

兼容已有库（`DbCompat.EnsureAsync`）：

```sql
IF COL_LENGTH('prod_report', 'duration_minutes') IS NULL
  ALTER TABLE prod_report ADD duration_minutes INT NOT NULL CONSTRAINT DF_prod_report_duration DEFAULT 0;
```

### 5.2 API

| 接口 | 变更 |
|------|------|
| `POST /api/Report` Body | 增加 `durationMinutes`（可选，默认 0） |
| `PUT /api/Report/{id}` Body | 同上，可改 |
| `GET /api/Report` 列表 | `ReportListDto` 增加 `durationMinutes`；前端可格式化为「X小时Y分钟」 |

校验（`ThrowHelper.Biz`）：

- `durationMinutes < 0` → 拒绝  
- `durationMinutes > 1440` → 拒绝「单次报工时长不能超过 24 小时」  

完成状态回算逻辑**不依赖**时长（仍按工序计划数判完成）。

### 5.3 前端

**移动报工页**：

- 表单项「报工时长」：小时（0–24）+ 分钟（0–59）两个数字框  
- 提交前换算：`durationMinutes = hours * 60 + minutes`  
- 回填修改时（若 PC 改报工）：分钟拆回小时/分钟  

**PC 报工查询**：

- 列表增加列「时长」，展示如 `1小时30分钟`；0 显示 `—` 或 `0分钟`  
- 修改弹窗增加时长编辑（与良品/不良一并保存）  

### 5.4 验收（P2）

- [ ] 填 1 小时 30 分钟，库中 `duration_minutes = 90`  
- [ ] 不填时长可正常提交（存 0）  
- [ ] 填超过 24 小时被拦并提示  
- [ ] PC 报工列表能看到时长；修改后保存生效  
- [ ] 旧报工记录无此列时兼容为 0（DbCompat 后默认 0）
