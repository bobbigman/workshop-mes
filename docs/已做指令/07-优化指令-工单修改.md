# 优化指令：工单修改

> 状态：已并入 `docs/09-优化指令-对标黑湖全功能.md`，以 09 为准  
> 对标：黑湖小工单（轻量、高性价比）  
> 编制说明：完成态一律禁止改；无报工时数量可改至任意 ≥1

---

## 1. 目标

对齐黑湖：创建后可改工单。首期解决数量输错 + 自定义字段（桌号/辣度）改错；不追求黑湖全量能力。

## 2. 拍板结论（设计原则）

| 点 | 决定 | 理由 |
|----|------|------|
| 已完成工单 | **一律禁止改** | 规则一条最好讲；完成=结案。拆成「只改桌号」性价比低。错了用删除重建。 |
| 无报工改数量 | **允许改到任意 ≥1** | 正是「数量输错」场景；还没报工，无对账风险。 |

黑湖侧「未开始 / 执行中」可编辑；「已结束」教学几乎不碰——按**未结案可改、结案锁定**做最简闭环。

## 3. 字段策略

| 字段 | 策略 |
|------|------|
| 工单号 `orderNo` | 不可改（扫码锚点） |
| 产品 `productId` | 首期不可改（换产品=换路线，复杂且少见） |
| 数量 `qty` | 可改 |
| 自定义字段 `ext` | 可改（按提交的 key 更新/插入，未提交的保留） |
| 状态 `status` | 不可手工改；保存后按报工回算 |

## 4. 业务规则（实现必须遵守）

1. 工单须存在且属于当前工厂，否则抛业务异常。
2. **仅管理员（role=1）**可改；生产人员拒绝。
3. **`status == 完成(2)` → 整单禁止改**（数量与自定义字段都不行），提示「工单已完成，不可修改」。
4. `status` 为待生产(0) 或生产中(1) 时允许改。
5. 数量：`qty >= 1`；若有报工，还须  
   `qty >= SUM(该工单 good_qty)`，否则提示「数量不能小于已报良品数 N」。
6. **无报工**：只要 `qty >= 1` 即可改大改小。
7. 保存后回算状态：
   - 无报工 → 保持原 status（不因改数量强行变更）
   - 有报工且 `SUM(good) >= qty` → 置完成(2)
   - 有报工且 `SUM(good) < qty` → 置生产中(1)
8. 自定义单选值须落在选项内，否则抛业务异常。
9. 不改历史报工记录。

## 5. 接口 / 前端（实现要点）

- `PUT /api/WorkOrder/{id}`，Body：`{ qty, ext }`
- 列表加「编辑」；弹窗：工单号/产品只读，数量与自定义字段可编辑；`GET` 详情回填。
- 完成态：隐藏或禁用「编辑」，即使绕过前端，后端仍拦截。

## 6. 本期不做

- 改工单号、换产品、手工改状态
- 工序级计划数、撤回/反完成
- 完成后仍改自定义字段

## 7. 文档同步（实现时必做）

- 更新 `docs/01-PRD需求规格说明书.md` §4.9（补编辑规则）
- 表结构不变（仍用现有 `prod_work_order` / `sys_custom_field_value`）

## 8. 验收要点

1. 待生产：数量从 10→2 成功；桌号可改。
2. 已报良品 3：改 2 失败，改 5 成功。
3. 已完成：编辑失败。
4. 工单号不变；生产人员不可编辑。

## 9. 规约

- 异常用 `ThrowHelper.Biz`，不吞异常，带「位置 + 在做什么失败」
- 工厂隔离；命名空间 `ahu.MicrosoftMes`
- SQL Server；统一返回 `{ code, msg, data }`
