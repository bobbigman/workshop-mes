# 优化指令：全量「修改」能力（基础资料 + 单据）

> 状态：已并入 `docs/09-优化指令-对标黑湖全功能.md`，以 09 为准  
> 对标：黑湖小工单（轻量、高性价比）  
> 关联：`docs/07-优化指令-工单修改.md`（工单细则以 07 为准）  
> 编制原则：能改展示信息就改；身份锚点慎改；有下游引用时「改」比「删」宽；不做反审核/复杂版本链

## 0. 现状盘点（实现前必读）

| 对象 | 后端 Update | 前端编辑 | 列表能否回填编辑 | 缺口 |
|------|:-----------:|:--------:|:----------------:|------|
| 用户 | ✅ | ❌ | 基本够（密码另议） | 接 UI；改密可选 |
| 部门 | ✅ | ❌ | ❌ 缺 `memberIds` | Get 详情或列表补 Ids + UI |
| 单位 | ❌ | ❌ | 仅名称 | 补 PUT + UI |
| 不良品项 | ❌ | ❌ | 仅名称 | 补 PUT + UI |
| 工序 | ✅ | ❌ | ❌ 缺 `deptIds`/`defectIds` | Get 详情 + UI |
| 工艺路线 | ✅ | ❌ | ❌ 缺 `steps` | Get 详情 + UI |
| 产品 | ✅ | ❌ | ❌ 缺 `unitId`/`routingId` | Get 详情或列表补 Id + UI |
| 自定义字段 | ❌ | ❌ | 有 options | 补 PUT（限范围）+ UI |
| **工单** | ❌ | ❌ | 有 Get 详情 | 见 **docs/07** |
| 报工记录 | — | — | — | **本期不做修改**（提交即事实） |

结论：不是「全部没后端」，而是**大半后端已写好，前端全缺编辑**；单位/不良/自定义字段/工单需补 API。

## 1. 统一设计原则（自行拍板）

1. **权限**：仅管理员（role=1）可改基础资料与工单；生产人员只报工。  
2. **工厂隔离**：所有读写带 `factoryId`。  
3. **改 vs 删**：删除继续走 `DeleteGuard`（有引用就拦）；**修改默认放行**（名称、权限部门、路线工序顺序等），避免「改个错别字还要先删工单」。  
4. **身份锚点**：  
   - 工单号：不可改（扫码）  
   - 产品编号：可改，但须工厂内唯一（排除自身）  
   - 工序/路线/部门编码：可改，不做历史版本  
5. **不做**：报工记录修改、反完成、审批流、字段类型变更迁移。  
6. **前端模式**：列表操作列「编辑」→ 复用创建弹窗 → 保存走 PUT；创建/编辑共用表单，用 `editingId` 区分。  
7. **异常**：`ThrowHelper.Biz`，不吞异常。

## 2. 分对象指令

### 2.1 用户

| 项 | 说明 |
|----|------|
| API | 已有 `PUT /api/User/{id}` |
| 可改 | 账号、手机、姓名、角色；密码**留空=不改**，有值则校验复杂度后更新 |
| 不可改 | Id；不在此接口改部门归属（部门页维护成员） |
| 前端 | 编辑回填；密码 placeholder「不填则保持原密码」 |
| 验收 | 改姓名成功；空密码保存后仍能用旧密码登录 |

### 2.2 部门

| 项 | 说明 |
|----|------|
| API | 已有 `PUT /api/Department/{id}` |
| 可改 | 编码、名称、成员列表（全量替换 `memberIds`） |
| 缺口 | 补 `GET /api/Department/{id}`，返回 `{ id, code, name, memberIds }` |
| 前端 | 编辑时勾选成员 |
| 验收 | 热菜组成员增删后，工序列表报工权限展示与报工校验一致 |

### 2.3 单位

| 项 | 说明 |
|----|------|
| API | **新增** `PUT /api/Unit/{id}`，Body：`{ name }` |
| 可改 | 名称（被产品引用仍可改名，只影响展示） |
| 校验 | 同工厂名称建议唯一（空名拒绝）；不存在/跨工厂拒绝 |
| 前端 | 列表加编辑 |
| 验收 | 「只」改成「个」，产品列表单位名跟着变 |

### 2.4 不良品项

| 项 | 说明 |
|----|------|
| API | **新增** `PUT /api/DefectItem/{id}`，Body：`{ name }` |
| 可改 | 名称（已被工序引用仍可改名） |
| 前端 | 列表加编辑 |
| 验收 | 「粘锅」改名后，工序不良下拉与报工原因显示新名；**历史报工**若存的是 defectId，展示跟新名（当前模型即如此） |

### 2.5 工序

| 项 | 说明 |
|----|------|
| API | 已有 `PUT /api/Operation/{id}` |
| 可改 | 编号、名称、报工权限部门、不良品项（关联表先删后插，与现实现一致） |
| 缺口 | 补 `GET /api/Operation/{id}` → `{ id, code, name, deptIds, defectIds }` |
| 约束 | 有报工记录**仍允许改**（改权限影响「之后」报工，符合轻量现场纠错）；删除仍按 DeleteGuard |
| 前端 | 编辑回填多选 |
| 验收 | 去掉某部门权限后，该部门生产人员再报工被拒；管理员仍可报 |

### 2.6 工艺路线

| 项 | 说明 |
|----|------|
| API | 已有 `PUT /api/Routing/{id}` |
| 可改 | 编号、名称、工序明细（有序 steps，先删后插） |
| 缺口 | 补 `GET /api/Routing/{id}` → `{ id, code, name, steps:[{ operationId, seq }] }` |
| 约束 | 已被产品引用**仍允许改**（影响该产品后续工单可选工序）；至少 1 道工序 |
| 风险（接受） | 进行中工单按产品当前路线取工序，改路线会改变可报工序——轻量系统可接受；不做路线版本号 |
| 前端 | 编辑回填步骤行 |
| 验收 | 路线插入/调序后，新开/已有工单详情工序列表与路线一致 |

### 2.7 产品

| 项 | 说明 |
|----|------|
| API | 已有 `PUT /api/Product/{id}` |
| 可改 | 编号、名称、单位、工艺路线、供应商、单价 |
| 硬规则 | 编号工厂内唯一（排除自身）；编号空拒绝 |
| 缺口 | 补 `GET /api/Product/{id}` 或列表 DTO 增加 `unitId`/`routingId`（推荐 Get，干净） |
| 约束 | 已有工单**仍允许改**名称/单位/路线；不级联改历史工单快照（工单只存 productId） |
| 前端 | 编辑回填 |
| 验收 | 改路线后，该产品下工单报工可选工序随新路线变化 |

### 2.8 自定义字段

| 项 | 说明 |
|----|------|
| API | **新增** `PUT /api/CustomField/{id}` |
| 可改 | `fieldName`；若 `fieldType==single`，可重提 `options`（先删旧选项再插） |
| 不可改 | `target`、`fieldType`（避免已有值类型错乱） |
| 删除 | 本期可不做；若做：有 `sys_custom_field_value` 则禁止删 |
| 前端 | 列表加编辑；类型只读展示 |
| 验收 | 桌号选项增加「四号桌」后，开工会单下拉可见 |

### 2.9 工单

见 **`docs/07-优化指令-工单修改.md`**（完成态禁止改；数量 ≥ 已报良品；无报工可改至 ≥1；产品/工单号不可改）。

前端另补：`updateOrder` API 封装 + 列表「编辑」。

### 2.10 明确不做

| 对象 | 原因 |
|------|------|
| 报工记录修改 | 现场事实；错了用管理干预或下期「作废重报」，本期不做 |
| 工厂档案 | 种子级，非日常 |
| 导入结果回滚 | 超范围 |

## 3. 实现优先级（性价比排序）

| 优先级 | 内容 | 说明 |
|:------:|------|------|
| **P0** | 用户 / 部门 / 工序 / 路线 / 产品：接前端编辑 + 补 Get 详情 | 后端已有 PUT，收益最大 |
| **P1** | 单位 / 不良品项：补 PUT + 前端 | 字段极简 |
| **P2** | 工单修改（docs/07） | 单据纠错刚需 |
| **P3** | 自定义字段 PUT + 前端 | 改选项频率较低 |

建议同一迭代做完 P0+P1（基础资料编辑闭环），再 P2，最后 P3。

---

## 4. 前端统一交互规约

1. 操作列：`编辑`（primary link）+ `删除`（danger）。  
2. 弹窗标题：创建 / 编辑 切换。  
3. `onSave`：`editingId ? updateXxx(id, form) : createXxx(form)`。  
4. 完成态工单：不显示编辑或点开即提示（以后端为准）。  
5. API：`base.js` / `sys.js` / `prod.js` 已有 update 的补调用；缺的补函数。
