## 8. 日志改造建议（可选，推荐：让管理员能定位、用户看不到 Id）

现状：`Common/ExceptionMiddleware.cs` 已统一记录 `BusinessException`（`LogWarning` 带 TraceId/UserId/FactoryId/Path/Msg）。但 Msg 去掉 Id 后，具体对象（哪条报工、哪道工序、哪个批次）无法从用户消息定位。

**推荐方案 A（最小侵入、全站受益）**：
- 给 `BusinessException` 增加一个结构化日志上下文字段（如 `IDictionary<string, object?>? Log`）；`ThrowHelper` 增加重载 `BizUser(what, (key,value)…)` / `Biz(where, what, (key,value)…)`，抛错时把 `reportId`、`operationId`、`userId`、`batchId` 等放进 Log。
- `ExceptionMiddleware` 在 `LogWarning` 时把 `ex.Log` 一并输出（Serilog structured properties，如 `LogWarning("业务异常 TraceId={TraceId} … Msg={Msg} ReportId={ReportId} OperationId={OperationId}", …)`）。
- 效果：Message 保持人话无 Id（用户端），日志保留全部定位 Id（排查端），与 `ThrowHelper` 注释既有意图「完整敏感上下文由服务器日志采集」一致。
- 波及：`BusinessException` 加字段（向后兼容，不改现有构造）、`ThrowHelper` 加重载（可选参数，不改现有调用点语义）、`ExceptionMiddleware` 读取字段。

**备选方案 C（暂不改框架，先落地文案）**：
- 去掉的定位信息靠中间件已有 TraceId + Message 里保留的业务编号（工单号/产品编号/工序名）定位；
- 无法映射业务编号的（报工 Id、批次 Id），配合前端 `http.js` 的追踪号 `{id}` 与后端 TraceId 关联请求日志排查。
- 优点：零框架改动；缺点：单靠 TraceId 定位略绕。
