# 优化指令：防超额报工（对标黑湖「硬上限」）

> 状态：已实现  
> 依据：`docs/黑湖防超额报工.md`；PRD §4.12 报工；现实现 `ReportService.SubmitAsync`  
> 目标：把「防超额」从事后追责前移到**事中拦截**——报工提交时校验「累计良品数 ≤ 该工序计划数」，超了直接拦下  
> 原则：先做**性价比最高的一层（硬上限）**，其余多层防线（智能预警 / 良率平衡 / 行为画像）明确后置或不做

---

## 0. 差距分析（黑湖 5 层防线 vs 本项目现状）

| # | 黑湖防线 | 本项目现状 | 本期 |
|---|---------|-----------|------|
| 1 | 硬上限（计划量 × 损耗率，达上限锁死） | ❌ 无任何数量上限校验，`goodQty` 想报多少报多少 | **P0 做**（死上限=计划数 100%） |
| 2 | 智能预警（单次 vs 历史均值） | ❌ 无 | **不做**（依赖报工历史，数据量不足阈值会瞎跳） |
| 3 | 工序顺序校验（前道完成才报后道） | ⚠️ 有 `seq` 但报工不校验前道 | **不做硬拦截**（现为下拉选工序，强顺序会卡返工/补录） |
| 4 | 良率平衡（产出+报废 > 投入） | ❌ 无，且**数据字典缺「投入数量」字段** | **做不了**（等领料/发料模块再补） |
| 5 | 行为画像（产能曲线 / 深夜突击） | ❌ 无 | **不做**（小车间过度设计） |

**结论**：本期只做 **第 1 层「硬上限」**，一条主线（后端拦截 + 前端剩余可报提示）。

---

## 1. 自主拍板（实现前定死，避免返工）

| 项 | 决定 | 理由 |
|----|------|------|
| 上限口径 | **累计良品数 + 本次良品数 ≤ 该工序计划数**（100%，不放损耗率） | 拦截绝大多数无意识超报；有真实超产需求再开放损耗率配置 |
| 计划数来源 | 有任务行取 `prod_work_order_operation.plan_qty`；无任务行兜底 `prod_work_order.qty` | 与 `RecalcStatusAsync`、`docs/10` 口径一致，别搞两套 |
| 是否约束不良品 | **不约束**。上限只算「良品」，不良品单独累计 | 不良品占计划数会把逻辑算错 |
| 是否改表 | **不改表** | 计划数、已报良品都是现有字段/可聚合得到 |
| 修改报工是否同样校验 | **是**。`PUT /Report/{id}` 改良品数时同样拦（排除本条记录） | 否则超了之后改数就能绕过 |
| 拦截方式 | `ThrowHelper.Biz` 抛业务异常，带「计划/已报/本次」三要素 | 遵循规则：异常不吞、带上下文 |
| 前端 | H5 摘要加「剩余可报」，报满禁用提交；PC 报工弹窗同步提示 | 后端是底线，前端只是体验，**不能只信前端** |
| 报满语义 | 剩余=0 时禁止再报，提示「该工序已报满」 | 达到计划数即完成（`RecalcStatusAsync` 已按此判完成） |

---

## 2. 数据

**不改表**，无 DDL。

- 计划数：`prod_work_order_operation.plan_qty`（无任务行用 `prod_work_order.qty`）
- 已报良品：`SUM(prod_report.good_qty)`，按 `order_id + operation_id`
- 已报不良：`SUM(prod_report.defect_qty)`（仅展示，不参与上限判断）

## 3. 后端改动

### 3.1 `ReportService.SubmitAsync` —— 新增硬上限校验

位置：现有「部门权限校验」之后、「`_db.Reports.Add(...)`」之前。

```csharp
// 防超额：累计良品 + 本次良品 不得超过该工序计划数
var task = await _db.WorkOrderOperations
    .FirstOrDefaultAsync(t => t.WorkOrderId == order.Id && t.OperationId == dto.OperationId);
var planQty = task?.PlanQty ?? order.Qty;   // 无任务行兜底工单级 qty

var alreadyGood = await _db.Reports
    .Where(r => r.OrderId == order.Id && r.OperationId == dto.OperationId)
    .SumAsync(r => (int?)r.GoodQty) ?? 0;

if (alreadyGood + dto.GoodQty > planQty)
    throw ThrowHelper.Biz(nameof(SubmitAsync),
        $"超出计划数：该工序计划 {planQty}，已报良品 {alreadyGood}，本次 {dto.GoodQty}");
```

### 3.2 `ReportService.UpdateAsync` —— 改报工同样校验

现有 `UpdateAsync` 在末尾才查工单（`order`），需**提前**到改数前；并排除本条记录：

```csharp
// 防超额（改报工同样校验，排除本条）
var order = await _db.WorkOrders.FirstOrDefaultAsync(o => o.Id == report.OrderId)
    ?? throw ThrowHelper.Biz(nameof(UpdateAsync), "报工关联工单不存在");
var task = await _db.WorkOrderOperations
    .FirstOrDefaultAsync(t => t.WorkOrderId == report.OrderId && t.OperationId == report.OperationId);
var planQty = task?.PlanQty ?? order.Qty;
var othersGood = await _db.Reports
    .Where(r => r.OrderId == report.OrderId && r.OperationId == report.OperationId && r.Id != report.Id)
    .SumAsync(r => (int?)r.GoodQty) ?? 0;
if (othersGood + dto.GoodQty > planQty)
    throw ThrowHelper.Biz(nameof(UpdateAsync),
        $"超出计划数：该工序计划 {planQty}，其它记录已报良品 {othersGood}，本次 {dto.GoodQty}");
```

> 注：现有 `UpdateAsync` 末尾那段 `var order = ...` 与上面合并，避免重复查询。

### 3.3 无需改动的接口

- `GET /api/WorkOrder/by-no`、`GET /api/WorkOrder/{id}`：`WorkOrderTaskDto` 已有 `planQty / doneQty / defectQty`，前端可自算「剩余可报」，**不新增字段**。
- `POST/PUT /api/Report`：Body 不变。

## 4. 前端改动

### 4.1 H5 报工页（`frontend/src/views/h5/report.vue`）

- 摘要卡由 3 项扩成 **4 项**，新增「剩余可报」= `max(0, planQty - doneQty)`。
- 新增 `locked` 计算属性：已选工序且剩余 ≤ 0 时为 `true`。
- `locked` 时：禁用「继续报工」「提交」按钮；良品输入框 `:max="remain"`。
- 提示：剩余 ≤ 0 时摘要下方或输入框旁显示「该工序已报满」。

关键片段：

```js
const summary = computed(() => {
  if (!detail.value || !form.value.operationId) return { plan: '—', done: '—', defect: '—', remain: '—' }
  const t = (detail.value.tasks || []).find(x => String(x.operationId) === String(form.value.operationId))
  if (!t) return { plan: '—', done: '—', defect: '—', remain: '—' }
  return { plan: t.planQty, done: t.doneQty, defect: t.defectQty, remain: Math.max(0, t.planQty - t.doneQty) }
})
const remainNum = computed(() => {
  const r = summary.value.remain
  return (typeof r === 'number') ? r : 0
})
const locked = computed(() => !!form.value.operationId && remainNum.value <= 0)
```

### 4.2 PC 报工页（`frontend/src/views/report/index.vue`）

- 新增报工弹窗的「工序进度」摘要里补一项「剩余可报」。
- 报满时前端 `ElMessage` 提示 + 禁用提交（后端仍兜底拦截）。

## 5. 明确不做（本期）

| 项 | 原因 |
|----|------|
| 损耗率可配置（如 103%） | 先做死上限，有真实超产需求再加配置 |
| 智能预警（单次 vs 历史均值） | 依赖报工历史，数据不足阈值失真 |
| 工序顺序硬拦截 | 现为下拉选工序，强顺序会卡返工/跳序补录 |
| 良率平衡（投入 vs 产出+报废） | 数据字典缺「投入数量」字段，无法算 |
| 行为画像 / 刷单风控 | 小车间收益低，过度设计 |
| 报工删除 / 作废 | 与黑湖一致：只改数不删 |
