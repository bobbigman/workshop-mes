## 行为与口径（分叉写成显式条件）

- 当只说“帮我报工”或字段缺失 → 只追问缺项；当单号/工序不明确、语音数字存在歧义 → 请用户澄清，不自行猜测。问“怎么报工”才走操作说明。
- 当缺可信身份或未有效绑定 → 禁止写入，提示完成有效绑定；昵称、模型提供的 userid、单独报手机号及工厂共享钥匙均不作为已验证员工身份。既有无验证码手机号绑定机制不能不经核实就宣称满足写入身份要求；若平台无法提供可靠身份链路，记录阻点，不启用写入，不扩大为重做整套账号系统。
- 当身份及字段完整 → 复用现有校验后返回预览（员工、工单、工序、良品数、待确认状态），不产生报工流水。写入不得使用查询演示模式的免绑定放行。
- 当本人明确确认当前预览 → 核对当前工厂、渠道/会话身份与有效员工绑定均与预览一致，再重新执行报工校验、提交。其他员工或会话拿到同一 token 也不能确认。
- 当修改报数或取消 → 原预览失效；修改后重新预览。新预览替换同一身份会话的旧待确认内容，后端拒绝旧 token；过期、重启丢失或无当前预览时要求重新预览。不得把先前的“确认”自动用于新内容。
- 当重复确认或并发重试 → 同一确认凭证最多生成一条流水；执行方核实并补齐现有锁与数据库幂等链路。提交失败不得留下部分业务写入；结果未知时按原凭证核实/重试，不自动新建预览再次入账。
- 当部门无权限、超额、前道限制不通过 → 回显真实原因、不入库；有不良或多人/多工序等复杂报工 → 引导现有表单。只有工具明确成功才能回复“报工成功”，失败按 `ThrowHelper` 规范保留上下文并脱敏。
