## 取舍（已定）

| 项 | 方案 |
|---|---|
| 开工打卡是否绑考勤 | **不绑**。考勤管"人来没来"，开工打卡管"人在这道工序干了几小时"，两码事 |
| 计件岗要不要开工 | **不显示开工按钮**。计件工资=良品数×单价，不依赖时长；H5报工页只对 price_type=2（计时）显示【开工】按钮，计件岗扫码直接填数量提交（对标黑湖：计件岗扫一次码两步完事） |
| 计时岗H5普通自报 | **强制开工**。无 session 直接报工 → 后端 400"请先开工" |
| 计时岗PC管理员补报 | **例外放行**。表单填开始/结束时间，后端算分钟数；也创建 session（已结束状态），留痕操作人 |
| 开工记录存哪 | **独立表 `prod_work_session`**。开工 INSERT，报工 UPDATE。H5自报和PC补报都走这张表 |
| PC补报表单填什么 | **只填开始/结束时间**，不填分钟数。后端算 `(end-start).TotalMinutes`，向上取整到整分钟 |
| 时长优先级 | 普通报工：未手改传null，服务端自动算；手改传分钟数。管理员补填起止时间时由服务端算分钟数。计时报工最终时长必须 > 0 |
| 跨工单自动收尾 | **做**（本方案加的容错，黑湖原生未明确）。扫下一张工单开工时，旧 session 自动收尾 status=2，不自动生成报工；PC端有"待补报开工记录"入口人工补 |
| 同厂同人唯一进行中session | **保留唯一索引**（本方案加的防烂账，黑湖原生未明确）。代价：工人同时看两台机要切着扫；好处：防忘收尾导致时长翻倍 |
| 多人分摊工时怎么算 | **逐人记自己的工时，不平分**。数量按原规则分摊，工时按每人自己的 session/补填时间算 |
| 时薪挂哪一层 | **挂产品+工序，不挂用户资料**。对标黑湖：工价维度无"员工"字段；人级价差走 `base_price_rule.user_id` 覆盖（已有能力） |
| 计时岗挂时薪方式 | 建虚拟产品+虚拟工序（如"机修辅助/机修工时"），price_type=2，时薪30元。不新建人员时薪表 |
| 临时工打8折 | **已有能力（docs/225），本次不动**。`sys_user.wage_coeff` 已跑通 |
| `PriceRuleMatcher.Calculate` | **不改**。后端计时分支已跑通，本次只喂数据 |

### 缺口（本次要做）

#### 1. 新表 `prod_work_session`（开工/补报记录）
```sql
CREATE TABLE prod_work_session (
  id              BIGINT IDENTITY(1,1) PRIMARY KEY,
  factory_id      BIGINT NOT NULL,
  work_order_id   BIGINT NOT NULL,
  operation_id    BIGINT NOT NULL,
  user_id         BIGINT NOT NULL,               -- 实际干活人
  start_time      DATETIME2 NOT NULL,            -- 开工时间（H5=服务端now；PC补报=表单填）
  end_time        DATETIME2 NULL,                -- 结束时间；NULL=进行中
  duration_minutes INT NOT NULL DEFAULT 0,        -- 该次session时长（分钟）；报工/补报时固化
  status          TINYINT NOT NULL DEFAULT 0,    -- 0进行中 1已报工 2已收尾未报工 3已取消
  source          TINYINT NOT NULL DEFAULT 0,    -- 0=H5自报 1=PC管理员补报 2=跨工单收尾
  operator_user_id BIGINT NULL,                  -- 实际操作人（PC补报时=管理员；H5自报=NULL）
  report_id       BIGINT NULL,                   -- 关联报工ID；status=1时回填
  created_at      DATETIME2 DEFAULT SYSDATETIME(),
  ended_at        DATETIME2 NULL
);
-- 并发兜底：同厂同人同时最多一条进行中记录
CREATE UNIQUE INDEX ux_session_running
  ON prod_work_session(factory_id, user_id) WHERE status = 0;
CREATE INDEX ix_session_order ON prod_work_session(work_order_id);
CREATE INDEX ix_session_pending ON prod_work_session(factory_id, status) WHERE status = 2;
```

#### 2. H5报工页改造
- 进页面调 `GET /api/work-session/current?workOrderId=xxx&operationId=xxx`（**后端从JWT取登录人，不接受传 userId**）查进行中 session
- **核对工单+工序**：返回的 session 必须与当前工单、工序一致，才显示【作业中…】+实时秒表；不一致（工人在别的工单开工着）→ 仍显示【开工】按钮，点了才触发既定的跨工单收尾
- 无 session 且 price_type=2 → 显示【开工】大按钮；【提交报工】按钮前端置灰提示，但**真正拦截在后端**
- 点【开工】→ `POST /api/work-session/start`（工单+工序）：
  - 事务内：①若该工人已有 status=0 session 且同工单同工序 → 返回原 session（幂等）；②若已有 status=0 session 但不同工单/工序 → 旧 session UPDATE end_time=now, status=2；③INSERT 新 session status=0
- 点【提交报工】→ 报工DTO：
  - `durationMinutes` 改为**可空 int**；未手改传 null
  - `sessionId` 带上当前进行中的 session
  - **后端校验 session 与本次人员、工单、工序完全一致**，不一致拒绝
  - **先校验开工资格，再算时长**（不能因手填时长绕过校验）：
    - 该报工命中的工价规则 price_type=2（计时）→ 必须有有效 status=0 session，或符合管理员补填例外（管理员在表单补填了起止时间）；不满足 → 400"请先开工"，不论前端传了多少时长
    - 该报工命中 price_type=1（计件）或 3（固定）→ 不校验开工
  - 时长取值（开工资格通过后）：
    - 前端显式传了 durationMinutes → 以前端值为准
    - 未传 durationMinutes 且有有效 session → 服务端算 `(now - session.start_time)`，向上取整；<1分钟按1分钟
    - 未传 durationMinutes 且管理员补填了 startTime/endTime → `Ceiling((endTime-startTime).TotalMinutes)`；校验 endTime>startTime 且 endTime≤now；新建 session(status=1, source=1, operator=管理员)，**不执行"WHERE status=0"的条件更新**（是新建不是更新已有session）
    - 未传 durationMinutes 且无 session 且计件/固定岗 → durationMinutes=0
  - **未匹配工价（price_type=0）的报工**：不强制开工；显式时长保留；有session自动算；两者都没有记0；范围0–1440；工资沿用原有"未匹配工价"提示，不猜计价方式
  - **时长范围校验**：计件/固定岗允许 0–1440 分钟；计时岗必须 1–1440 分钟（≤0 直接 400"计时报工时长必须大于0分钟"）；超过1440 → 400"单次报工时长不能超过24小时"
  - **报工事务内闭环**（仅已有session走下述UPDATE；管理员补填走INSERT；计件/固定/未匹配且无session只写报工）：INSERT 报工记录 → **带条件** UPDATE session SET status=1, end_time=now, duration_minutes=算好的值, report_id=新报工ID WHERE id=sessionId AND status=0 AND report_id IS NULL；**受影响行数必须=1，否则整笔回滚**（防两个并发请求同时读到同一条进行中记录分别生成报工）
  - 已关联 report_id 的 session 禁止再用于新报工；同一次请求重试（client_request_id）返回原结果，不重复计薪

#### 3. PC补报改造（docs/17 现状：仅管理员、良品数>0、时长固定0）
- 表单加：开始时间、结束时间（datetime-local），**不填分钟数**
- 提交前校验：end_time > start_time 且 end_time ≤ 当前时间；单次时长 ≤ 1440分钟（24小时）
- **归期口径**：计时补报的 `report_time = end_time`（业务报工时间=实际结束时间），session.created_at 仍记实际录入时刻（prod_report不新增created_at）；工资按 report_time 归月份、按当时工价匹配。跨结算周期（如9月30日开工、10月2日完工）**不自动拆分**，表单提示管理员分段填两条
- 提交时事务内：
  1. 算 `durationMinutes = Ceiling((end-start).TotalMinutes)`
  2. INSERT 报工记录（计时岗允许良品数=0；report_time 用 end_time，不用 now()）
  3. INSERT session：status=1, source=1, operator_user_id=当前管理员, report_id=新报工ID, start_time/end_time/duration_minutes 固化
- 计件岗补报：现有逻辑不变（良品数>0，duration_minutes=0，不建 session）

#### 4. "待补报开工记录"入口（PC端）
- PC报工页加 Tab/列表：查询 `prod_work_session WHERE factory_id=当前厂 AND status=2`
- 列表列：人员、工单编号、产品、工序、开工时间、收尾时间、时长（自动算）
- 点某条 → 弹出补报表单，自动带出人员/工单/工序/起止时间，管理员补填良品数（计时岗可0）→ 提交
- 补报成功：session UPDATE **WHERE id=sessionId AND status=2 AND report_id IS NULL**，受影响行数必须=1；置 status=1, report_id=新报工ID, duration_minutes 固化；否则回滚报错"该记录已被补报"
- 已 status=1/3 的记录不出现在待补报列表（防重复补报）

#### 5. 多人分摊报工改造
- 现有"平均分摊"：数量按人数均分；**工时不平分**
- **参与人接口结构**（每位参与人随报工请求提交）：
  ```
  participants: [
    {
      userId: long,
      sessionId: long?        // 有开工记录时传；无则null
      durationMinutes: int?   // 手填时长；未手填传null
      startTime: datetime?    // 管理员补填开始时间；有session则null
      endTime: datetime?      // 管理员补填结束时间；有session则null
    }
  ]
  ```
- 计时岗多人分摊时：
  - 每个参与人**先按其个人命中的工价规则判断是否强制开工**（混合计价时不按整批一刀切）
  - 命中 price_type=2 的参与人：有 status=0 session → 报工事务内 UPDATE status=1；无 session 但管理员在表单补填了 startTime/endTime → INSERT 报工+INSERT session(status=1, source=1, operator=管理员)
  - **任一人校验失败（缺开工且未补填、时间范围非法、权限不对）→ 整批回滚**，返回具体失败人名和原因
- 每条报工记录独立核对：factory_id、user_id、work_order_id、operation_id、部门权限（沿用现有报工权限校验）

#### 6. 工资单明细加快照字段
- `salary_statement_item` 加两列：
  - `price_type TINYINT NOT NULL DEFAULT 0`（**0=未记录/未匹配工价 1=计件 2=计时 3=固定**）
  - `duration_minutes INT NOT NULL DEFAULT 0`
- **历史数据**：price_type=0，duration_minutes=0；界面：
  - price_type=0 → 单价列不显示单位、不归入计件合计也不归入计时合计
  - price_type=1 → 显示"X元/件"，归入计件合计
  - price_type=2 → 显示"X元/时"，明细时长列显示"X.Xh"，归入"计时合计（元）"
  - price_type=3 → 显示"固定X元"
- **新生成明细**：成功匹配工价规则必须写真实 price_type（1/2/3）；**仅在未匹配工价时允许写0**，并在工资单标注"未匹配工价"
- 工资单生成、草稿重算都要同步更新 price_type 和 duration_minutes 快照，不改变原有未匹配工价的结算规则

## 行为与口径（分叉写成显式条件）

- **当**工人H5扫码进工单页 **且** 有同工单同工序的 status=0 session → 显示【作业中…】+秒表
- **当**工人H5扫码 **且** 进行中 session 属于别的工单/工序 → 显示【开工】按钮，点了才触发跨工单收尾
- **当**工人H5扫码 **且** 无 session **且** price_type=2 → 显示【开工】，后端拦截无 session 的报工
- **当**工人点【开工】**且** 同人同工单同工序已有 status=0 → 返回原 session（幂等，不重复建）
- **当**工人点【开工】**且** 已有其他工单/工序的 status=0 session → 旧 session UPDATE end_time=now, status=2；新 session INSERT status=0（事务内）
- **当**工人报工 **且** 命中计时工价 **且** 无有效 session 且无管理员补填 → 400"请先开工"，**即使前端传了 durationMinutes 也不采纳**
- **当**工人报工 **且** 开工资格通过 **且** 显式传了 durationMinutes → 以前端值为准
- **当**工人报工 **且** 开工资格通过 **且** 未传 durationMinutes **且** 有 session → 服务端算时长，向上取整；<1分钟按1分钟
- **当**计件/固定岗报工 **且** 无 session 且未传时长 → durationMinutes=0，正常提交
- **当**计件/固定岗报工 **且** 显式传 durationMinutes → 接受 0–1440 分钟
- **当**管理员补填 startTime/endTime 且未传 durationMinutes → 用 `Ceiling(endTime-startTime)` 算时长，新建 session(status=1, source=1)，不执行"WHERE status=0"条件更新
- **当**报工命中未匹配工价（price_type=0）→ 不强制开工；显式时长保留；有session自动算；都没有记0；范围0–1440；不猜计价方式
- **当**计时岗报工最终 durationMinutes ≤ 0 → 400"计时报工时长必须大于0分钟"
- **当**报工时长 > 1440分钟 → 400"单次报工时长不能超过24小时"
- **当**报工提交成功 → 事务内 UPDATE session status=1, end_time, duration_minutes, report_id；已关联 report_id 的 session 禁止再报工
- **当**PC管理员补报计时岗 **且** 良品数=0 → 允许；表单填开始/结束时间，校验 end>start 且 end≤now；同时写 session（status=1, source=1）
- **当**PC管理员补报计件岗 → 现有逻辑不变，不建 session
- **当**多人分摊报工 **且** 涉及计时人员 → 每人独立取自己 status=0 的 session；缺记录的人由管理员**在同一张多人表单里补填起止时间**，整批一次提交；不允许先单独补报再重提整批（会导致补报的人 status=1、整批又要 status=0 的死锁）；**不允许零工资兜底**
- **当**工资单生成 **且** price_type=0（历史行或未匹配工价）→ 不归入任何分类合计，单价不显示单位
- **当**工资单生成 **且** price_type=2（新计时行）→ duration_minutes 固化，"计时合计（元）"= 该类 amount 之和（扣款前）
- **当**工人撤回报工 → 关联 session UPDATE status=3（已取消），不删记录（留痕）
- **当**管理员修改报工时长（未结算）→ 同一事务内同步 UPDATE 关联 session 的 duration_minutes 为新值；session 的 start_time/end_time 原始记录不变；已结算（settled_flag=1）的报工禁止修改，沿用现有冻结规则

### 并发与重复提交

- 报工提交沿用现有 `client_request_id` 去重机制
