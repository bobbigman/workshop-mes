# 150-优化指令：工资报表"工资单列表"加分页、姓名搜索、表头吸顶

> 状态：已做（dotnet/npm build 通过；现场 100 人联调待验）
> 性质：内部试用（车间真用，**涉及工资钱数**；本次只动查询展示，不改工资计算/确认/重算口径）
> 目标：让厂长/会计在工资报表页，面对 100+ 员工生成的工资单时，能一眼定位人、不被长列表顶飞底下明细表。
> 依据/拍板：
> - 2026-10-09 黑帽大人转发老沈反馈"员工过 100 个怕这界面看不完整"；
> - 同日 Cursor 对照代码核实：前端 `salary/index.vue` 无分页器无搜索无 sticky，静默传 `page:1, pageSize:50` 不读 total；后端 `SalaryQueryDto` 已有 `Page/PageSize`（默认 20）与 `Skip/Take + total`，但**无 Keyword**，只有精确 UserId；系统无独立"工号"字段，对人是 `Name/Account`；工具栏已有草稿/已确认状态筛选。
> - 拍板选 **A：后端加 Keyword（Name/Account Contains），继续用后端分页**（理由：工资页搜人漏一行就是对账事故，总数必须由后端 where count 给出，不能前端本地 filter 截断当前页）。

## 本次范围与落点

- 交付：
  - **后端**：`SalaryQueryDto` 加 `Keyword`；`QueryAsync` 追加姓名/账号 Contains；`total` 同步走过滤后的 count。
  - **前端** `frontend/src/views/salary/index.vue`：
    1. 工具栏加姓名/账号搜索框，输入防抖 300ms 后带 `keyword` 重新拉列表（`page` 重置为 1）；
    2. 表格底部接 `el-pagination`（sizes 10/20/50，默认 20，显示 total 与跳转），`page/pageSize` 双向绑定；
    3. 表头吸顶，表格区 `max-height: calc(100vh - 360px)` 左右，超出出纵向滚动条；
    4. 顶部切换周期类型/周期值 → `keyword` 清空、`page` 回 1、重新拉。
- 已有 / 缺口：下方"工资明细（报表层）"本次不动；**现有草稿/已确认状态筛选保留不动，不新增**。
- 数据与契约：`GET /api/Salary` query 新增可选 `keyword`，不传 = 不过滤。
- 文档：不动 docs/02、不动 PRD。

## 行为与口径（分叉写成显式条件）

- 当工资单总数 ≤ 20 → 分页器显示但禁用下一页，表格不强行出现纵向滚动条。
- 当工资单总数 > 20 → 表格按后端返回的当前页数据渲染，底部分页器 total 与后端一致。
- 当用户在搜索框输入"李"（防抖 300ms）→ 带 `keyword=李` 重新请求后端，page 回 1；列表与分页器 total 都是后端按 `Name.Contains||Account.Contains` 过滤后的结果；**跨页搜得到，不会只滤当前 20 条**。
- 当用户清空搜索框 → 不带 `keyword` 重新请求，恢复全量分页。
- 当用户切换月份/周期 → `keyword` 清空、page 回 1、重新请求。
- 当用户在第 3 页点了某行"明细"→ 明细区正常切到该人数据，**不重新拉列表、不跳页、不重置分页**。
- 任何分页/搜索都**不改动"应发合计"数字本身**——纯查询条件变化，不重算工资、不改确认状态。
