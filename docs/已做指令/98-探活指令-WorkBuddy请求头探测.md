# 98-探活指令-WorkBuddy请求头是否透传用户身份

> **结案（2026-09-30）：不需要实现，已归档到「已做指令」。**  
> 原因：MCP Server 在客户端注册时已用 `Authorization: Bearer <钥匙>` 标明身份/厂；WorkBuddy 专用钥匙走 docs/99，认人走 docs/97 手机号直绑。无需再临时打请求头探活日志。

> （以下为原文，仅作归档备查，勿再开工。）

---

## 一、为什么探活（原文）

多租户系统认人靠"平台透传的用户 ID"。微信给 openid、豆包给账号标识、扣子给 Coze 用户标识，都能认人。但 **WorkBuddy（腾讯 AI 办公台）调用 MCP 时，到底带了哪些请求头、有没有用户身份字段，得实测**。本指令让后端临时打印一次 WorkBuddy 发来的完整请求头，据此判断能不能靠它认人。

---

## 二、要执行的指令（原文，已作废）

```
# 探活任务：检查 WorkBuddy 调 MCP 时带了哪些请求头（是否含用户身份）
…（已结案，不执行）
```

详见历史：曾要求在 `McpTokenMiddleware` 临时打全量请求头日志，验完删除。现已明确不做。

---

## 三、原判断表（备查）

| 日志里出现的头 | 结论 |
|---|---|
| 有 `user` / `openid` / `userid` / `x-user-*` | WorkBuddy 透传用户身份 → 可加 `chan_type=workbuddy` 认人免报 |
| 只有 `authorization` + 通用头 | 不透传用户 → 须靠手机号绑定（docs/97） |
| 有企微类 `userid` | 可能免绑定直接认人 |

> 现行方案：注册 MCP 时 Bearer 定厂（96/99）；会话侧用手机号直绑认人（97）。
