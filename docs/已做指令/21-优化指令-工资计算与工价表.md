# 优化指令：工资计算与工价表（固定字段 + 对照表，不做公式引擎）

> 状态：已实现  
> 依据：`docs/02-数据字典.md`（已同步 DDL）；`docs/01` PRD「工资报表」P1；`docs/04` M4 暂缓项（绩效口径砍掉）；前期分析结论「事实×规则分离、先字段后引擎」；`docs/22` §8  
> 目标：用**报工事实 + 工价对照表 + 结算快照**跑通计件/计时/固定三种工资，PC 可维护工价、可生成/确认工资单、可导出；**不做**公式引擎、阶梯、班组分成、绩效、H5  
> 原则：瘦身版。一张工价对照表吃下多数工厂；结算结果必须可追溯、可重算；已结算报工冻结；**只结算 `review_status=1` 的报工**。

## 0. 复核纪要（相对初稿改了什么）

| 问题 | 初稿 | 复核后决定 |
|---|---|---|
| `prod_report` 加 `status`（待审/确认/作废） | 提过 | **不做**。现网报工提交即生效、无审核流；`RecalcStatusAsync` 直接 `SUM(good_qty)`。加状态会凭空引入未消费语义，与 docs/16 第二期「复核双轨」抢活 |
| `settled_flag` | 有 | **保留**。只解决「发工资后禁改」这一个点 |
| `salary_statement_item` 唯一键 | `(statement_id, report_id)` | 改为 **`UNIQUE(report_id)`**：一条报工全局只能进一张工资单 |
| `unit_price` / `wage_amount` 何时写 | 口径含糊 | **提交时报工尽力匹配回填**（预览）；**结算时以明细表固化为准** |
| `department_id` 多人多部门 | 未定 | **取「用户所属部门 ∩ 工序报工权限部门」中 id 最小者**；交集空（管理员代报）→ NULL |
| `base_product.price` | 易混 | **明确不是工价**；工价一律 `base_price_rule` |
| 无匹配规则怎么结算 | 未定 | 草稿可生成（amount=0，标「未匹配」）；**确认时若仍有未匹配 → 阻断** |
| 与 docs/16「计件工资范围外」 | 冲突 | 本期落地的是 **M4 砍掉绩效后的简单工资报表**；须在 **docs/22 复核之后** 做，结算只取已通过 |
| 复核后才进工资 | 曾写本期不做复核 | **改**：依赖 docs/22；`generate` 过滤 `review_status=1 AND settled_flag=0` |

## 1. 功能定位

| 项 | 内容 |
|---|---|
| 名称 | 工资计算（工价表 + 工资单） |
| 入口 | PC：基础数据「工价表」+ 报表「工资报表」；**仅管理员** |
| 做什么 | 维护工价规则；按人/月（或周）从 `prod_report` 生成草稿工资单；确认后冻结报工；列表查询 + 导出 |
| 不做什么 | 公式引擎、阶梯、班组内部分成、绩效系数、H5 查看工资、自动发薪；**不在本期实现复核**（复核见 docs/22） |

**数据流一句话：**

```
prod_report（事实） × base_price_rule（规则） → salary_statement_item（快照明细） → salary_statement（汇总）
```

## 2. 自主拍板（实现前定死）

| 项 | 决定 | 理由 |
|---|---|---|
| 角色 | 仅 `role=1` 可维护工价 / 生成 / 确认 / 删除草稿；`role=2` 无入口无接口 | 与现 PC 管理动作一致；工人看工资属后期 |
| 终端 | **仅 PC**；H5 不做 | 交付节奏：先管理后现场 |
| 计价类型 | 仅 1 计件 / 2 计时 / 3 固定 | 覆盖 90% 小厂；阶梯另议 |
| 公式（写死，禁止配置） | 计件 `amount = good_qty × unit_price`；计时 `amount = (duration_minutes / 60m) × unit_price`（四舍五入到分）；固定 `amount = unit_price`。扣款 `deduct = defect_qty × COALESCE(deduct_price,0)`。应发贡献 `amount − deduct`（可为负，表示扣光仍记） | 避免公式引擎 |
| 规则匹配 | 同工厂 + 生效期内 + 四维通配匹配；**命中维度数最多**优先；同具体度取 `priority` 升序、再取 `id` 升序 | 一张表吃多颗粒度 |
| 生效期 | `effective_from ≤ report_time` 且 (`effective_to` IS NULL OR `report_time < effective_to`) | 按报工时刻取价 |
| 报工写入 | `SubmitAsync` / `BatchReportAsync` / `UpdateAsync`：写 `product_id`；写 `department_id`（口径见上）；尽力匹配写 `unit_price`/`wage_amount`（无规则则两字段 NULL） | 实时预览 + 旧数据兼容 |
| 已结算冻结 | `settled_flag=1` 时 `UpdateAsync` 拒绝；本期无物理删除报工接口则不必加删拦截 | 防发完工资再改数 |
| 结算范围 | 某工厂、某周期、可选某人；只取 `review_status=1 AND settled_flag=0` 且 `report_time` 落在周期内的报工 | 依赖 docs/22；未通过/退回不进工资 |
| 周期 | `period_type`：1=月（`period_value='yyyy-MM'`，自然月）；2=周（`period_value='yyyy-Www'`，ISO 周，周一为一周开始） | 月够用；周预留 |
| 草稿 / 确认 / 发放 | `status`：0 草稿可删可重算；1 已确认（置报工 `settled_flag=1`，不可改明细）；2 已发放（仅状态标记，本期无支付对接） | 可审计 |
| 重算 | 仅草稿：删工资单 → 明细删光 → 相关报工 `settled_flag` 回 0 → 再生成。已确认不可直接重算，须先「反确认」（本期**不做反确认**，做错就人工联系改库或下期加） | 降低状态机复杂度 |
| 无规则 | 生成草稿允许 `rule_id=NULL, amount=0`；列表标红；**确认时若存在未匹配则 403/业务异常阻断** | 避免漏配还发薪 |
| 计时时长为 0 | 小计 0，不阻断；允许事后改报工时长再删草稿重算 | 与现「时长可空填 0」一致 |
| 并发 | 生成工资单事务内：筛选报工后插入明细；确认时 `UPDLOCK` 相关报工行再置 `settled_flag` | 防两人同时结算同一批 |
| 唯一约束 | `(factory_id, user_id, period_type, period_value)` 一张人期工资单；`report_id` 全局唯一进明细 | 防重复结算 |
| 删除依赖 | `DeleteGuard`：删产品/工序/部门/用户前检查 `base_price_rule` 引用；有工资明细引用用户时禁删用户（已有报工禁删已够，再补工资单检查） | 三条硬规则 |
| 库兼容 | 项目用 `EnsureCreated` + `DbCompat` 幂等补表/加列，**不走 EF Migration** | 与现网一致 |
| 与 `base_product.price` | 互不理睬 | 避免误用产品扩展单价当工价 |

## 4. 后端改动

### 4.1 工价匹配（抽公共方法，报工与结算共用）

位置建议：`backend/Services/PriceRuleMatcher.cs`（静态或注入均可）。

输入：`factoryId, productId?, operationId, departmentId?, userId, atTime`  
输出：命中的 `BasePriceRule?`

伪逻辑：

```
candidates = rules where factory_id match
  and effective_from <= atTime
  and (effective_to is null or atTime < effective_to)
  and (product_id is null or product_id == productId)
  and (operation_id is null or operation_id == operationId)
  and (department_id is null or department_id == departmentId)
  and (user_id is null or user_id == userId)
score = (product_id!=null?1:0) + (operation_id!=null?1:0) + (department_id!=null?1:0) + (user_id!=null?1:0)
order by score desc, priority asc, id asc
take first
```

计算小计：

```
deduct = defectQty * (rule.DeductPrice ?? 0)
switch price_type:
  1: amount = goodQty * unitPrice; calcQty = goodQty
  2: amount = Round(durationMinutes / 60m * unitPrice, 2); calcQty = 0
  3: amount = unitPrice; calcQty = 1
wage = amount - deduct
```

### 4.2 改报工写入（`ReportService`）

- `SubmitAsync` / `BatchReportAsync`：插入前填 `ProductId = order.ProductId`；`DepartmentId = ResolveDeptSnapshot(userId, operationId)`；调用匹配器填 `UnitPrice`/`WageAmount`（可空）。
- `UpdateAsync`：若 `SettledFlag` → `ThrowHelper.Biz(..., "已结算报工不可修改")`；改数后重新匹配回填单价/工资额。
- `ResolveDeptSnapshot`：用户部门 ∩ 工序 `base_operation_department`，`OrderBy(id).FirstOrDefault()`；无则 null。

### 4.3 工价 CRUD

`PriceRuleController` + `PriceRuleService`：

| 方法 | 路由 | 说明 |
|---|---|---|
| 列表 | `GET /api/PriceRule?page&pageSize&operationId&productId` | 分页；管理员 |
| 新增 | `POST /api/PriceRule` | 校验 factory；`unit_price >= 0`；`price_type ∈ {1,2,3}`；`effective_from` 必填 |
| 修改 | `PUT /api/PriceRule/{id}` | 已有结算明细引用时**允许改**（历史靠 item 快照）；或本期简化为允许改并提示「只影响未结算」 |
| 删除 | `DELETE /api/PriceRule/{id}` | 无硬外键；直接删。已结算明细 `rule_id` 可悬空（仅追溯展示「规则已删」） |

返回统一 `{ code, msg, data }`。

### 4.4 工资单

`SalaryController` + `SalaryService`：

| 方法 | 路由 | 说明 |
|---|---|---|
| 生成草稿 | `POST /api/Salary/generate` | body: `{ periodType, periodValue, userId? }`。已存在同人同期 → 业务异常「请先删除草稿」。事务内插入 statement + items，回填报工 `unit_price`/`wage_amount`（不置 settled） |
| 列表 | `GET /api/Salary?periodType&periodValue&userId&status&page&pageSize` | |
| 明细 | `GET /api/Salary/{id}` | 含 items（带工单号/工序名/数量/金额/是否匹配） |
| 确认 | `POST /api/Salary/{id}/confirm` | status 必须 0；存在 `rule_id==null` → 阻断；事务内 UPDLOCK 报工置 `settled_flag=1`，statement.status=1，confirmed_at=now |
| 标记发放 | `POST /api/Salary/{id}/pay` | status 必须 1 → 2（可选，可与确认合并；若想更瘦：**本期不做 pay，确认即完结**） |
| 删除草稿 | `DELETE /api/Salary/{id}` | 仅 status=0；删 items；本单涉及报工若无其它明细则保持 settled=0（本来就是 0） |

**拍板细化：本期不做「已发放」状态流转**，`status` 只用 0/1；字段保留 2 以兼容 02 字典，接口不暴露 pay。确认后即不可删。

导出：`GET /api/Salary/export?periodType&periodValue` 返回 CSV/Excel（与现有导入导出风格一致；若项目无现成 Excel 写出，**首版 CSV 即可**）。

### 4.5 DeleteGuard 补强

- `Product`：若 `base_price_rule` 引用该 product_id → 阻断「请先删除相关工价规则」
- `Operation`：同上
- `Department`：同上
- `User`：若存在 `salary_statement` → 阻断（报工已有检查可保留）

### 4.6 生产人员 403

`RoleGuardMiddleware`：确保 `/api/PriceRule`、`/api/Salary` 对 role=2 返回 403（若中间件按白名单放行报工，则新控制器默认仅管理员，对齐现有管理接口写法）。
