# 142｜开发复盘：轻量指令与验收避坑

> 2026-10-02。耗时由用户反馈：129 企微事件推送约 38 分钟，MP-UN-002 固定缺料样板约 6 分钟。本文整理开发经验，不增加新功能或验收任务。
> 案例：[129 企微事件推送](已做指令/129-优化指令-企微消息推送事件驱动对标黑湖.md)、[MP-UN-002 固定缺料样板](已做指令/MP-UN-002_预置工序缺料演示样板轻量化开发指令.md)。

## 1. 为什么这次快

这次在约 6 分钟内完成了一条可见流程：查看缺口 → 模拟补齐 → 再次校验 → 重置。速度改善来自目标收敛、落点独立、固定数据和集中验收；不只是少写了几行代码。

两次任务复杂度不同，不能据此认定所有开发都能提速六倍。129 是生产消息功能，涉及事务、持久待发、失败处理、规则配置、租户隔离等；MP-UN-002 是不接生产的售前样板。生产可靠性成本不能照搬样板方式省掉。上次也存在执行节奏分散的问题，不能把慢全部归因于开发指令。

| 对比 | 129 企微事件推送 | MP-UN-002 固定缺料样板 |
|---|---|---|
| 交付性质 | 生产能力，真实外部通道 | 售前模拟演示 |
| 改动范围 | 前后端、业务事务、数据与文档 | 同目录 3 个前端文件 |
| 数据与状态 | 持久化事件、投递与失败状态 | 固定 3 行数据，页面内存 |
| 环境依赖 | 企微配置及现场联调 | 现有前端开发环境 |
| 验证范围 | 多项自动验证，现场联调另验 | 一轮页面操作、一次默认生产构建 |
| 验收边界 | 代码完成不等于真实投递已联调 | 固定样板流程通过即交付 |

## 2. 指令与执行容易踩的坑

| 坑 | 为什么拖慢或出错 | 如何解决 |
|---|---|---|
| 把产品愿景全部写进首版 | 演示变正式模块，带出台账、统计、配置、权限、集成 | 用一句话定义本次成果，列明止步线；后置项不要求预留接口或隐藏按钮 |
| 把商业分析当开发清单 | 调研、报价、竞品结论、客户资料变成开发前置条件 | 分开商业资料与执行指令；只从分析中提取本次明确要交付的行为 |
| 用“轻量”标题包装大量需求 | 字数少，实际依赖和验收仍然多 | 看要改几个系统、接几种数据、增几类状态，而不是看标题与篇幅 |
| 一上来接正式菜单和鉴权 | 纯演示也要跨路由、权限、服务配置 | 售前样板采用独立入口；确需生产入口时另定范围 |
| 为将来扩展提前搭框架 | 固定样板也做通用计算、版本管理、导入导出 | 直接固定字段与数据；真实复用需求出现后再抽象 |
| 全库搜索、边写边反复检查 | 上下文和工具往返增加，进展难判断 | 先读相关规则、目标指令与直接落点；完整流程实现后集中验收，失败才定点复验 |
| 验收捆绑未开发能力 | 首版永远无法结束 | 每项验收都对应本次可观察的行为；不验后续 ERP、H5 或生产能力 |
| 用简化省掉正确性 | 消息可能丢失、业务回滚却发通知，或样板数字误导客户 | 三条业务硬规则、异常上下文、生产事务与涉及钱的追溯仍保留；缩范围不缩正确性 |

## 3. 本次落地的具体避坑

| 问题 | 本次处理 | 下次照做的条件 |
|---|---|---|
| 在途 100 被误当现货 | 只展示在途；裁切仍缺 50，并明确说明不能用于当前开工 | 到货未确认时，不抵扣当前可用量 |
| 需求量浮点计算可能出现尾数 | 固定整数样板用 `100 × 单件用量 × (100 + 损耗百分数) ÷ 100`，验证 210/100/100 | 仅适用于本样板；真实小数业务另定精度与舍入口径 |
| 连点补齐造成数量累加 | 每次只补当前缺口；齐套时禁用按钮，函数内也检查缺口为零 | 同类一键补足操作 |
| 只测重置，没测刷新 | 补齐后刷新，确认回到初始数据；实现不写本地存储 | 明确要求刷新恢复的临时演示 |
| 演示不小心进入生产包 | 独立 HTML 和入口脚本不接正式应用；默认构建后确认没有演示入口与 DEMO-M01 | 沿用当前 Vite 构建配置时；配置变化后重查 |
| 新开一个演示服务或打包模式 | 复用现有 Vite 与 Vue/Element Plus 依赖 | 同项目的本地售前样板 |
| 启动端口与 HTTPS 假设不一致 | 记录实际启动地址；端口以启动输出为准，本次使用 HTTPS 5188 | 不把临时预览地址当部署地址 |
| 小窗口表格显示不全 | 当前 PC 表格可横向查看，操作区仍显示当前缺口 | 首版仅 PC；若客户实际需要窄屏，再调整关键列或单独立项 |
| 现有大文件分包警告带出优化任务 | 构建成功，记录警告；本次不附加全站分包优化 | 警告未阻断当前交付且与本次新增页无关 |

上述项目包含实际采用的防护与验证，不表示每一项都曾发生故障。此次没有业务接口联调、数据库或真实库存问题，因为它们明确不在范围内。

## 4. 下次开工的最短流程

1. **先定性质**：演示、内部试用、正式生产三者选清楚，不能混写。
2. **审指令**：目标、固定落点、数据口径、止步线和验收是否一致；已有指令不靠谱，先修正文档再编码。
3. **实现一条完整流程**：用户从哪里进来、看什么、点什么、看到什么结果；只读相关落点，不顺带改周边模块。
4. **集中验收**：低影响独立演示按页面流程与构建验证；生产功能按实际风险验证事务、隔离、失败与持久化。发现问题再定点修复复验。
5. **达到验收即交付**：记录入口、实际结果与未完成边界，归档指令；不追加通用化、配图、全库回归或额外功能作为交付条件。

执行期间若出现必须改数据库、跨端、接外部接口或修改生产契约的新要求，先判断是否仍属于用户授权目标。能移出首版的直接移出；确属必要且改变产品取舍的，再明确取舍，避免悄悄扩大任务。

## 5. 可复用的短指令骨架

```text
目标：本次让谁完成什么动作，看到什么结果。
性质：演示 / 内部试用 / 正式生产。
落点：复用哪个页面、目录或服务；必要依赖是什么。
口径：数据来源、计算规则、关键业务约束。
动作：最少的完整操作流程。
止步线：明确后置项；不预建接口、配置或框架。
验收：少量、可观察、与本次行为对应的结果。
验证：根据改动风险列必要检查，失败才扩大检查。
交付：入口、实际证据、剩余限制；通过后停止扩范围。
```

不用每次新建指令。遵循现有约定：有取舍或改契约，先短指令与验收清单；其余直接开工。短指令也不能代替生产业务规则和权威数据字典。

## 6. 以后怎样判断有没有改善

分别记录指令澄清、实现、验证和环境阻塞的耗时；没有分段记录时，不事后编造各阶段分钟数。比较同类任务，关注是否出现范围返工、无关修改、重复验证，以及是否一次通过核心验收。

这次 6 分钟值得保留的做法是：首版边界明确，复用现有环境，固定数据支撑完整演示，验证集中且有终点。6 分钟是本次结果，不是以后每个需求的交付承诺。
