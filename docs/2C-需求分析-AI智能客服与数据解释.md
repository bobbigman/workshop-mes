# 需求分析 · AI 智能客服与数据解释

> 日期：2026-09-20｜状态：已开发实现并通过自动测试/构建与真实模型联调（S01–S12）。
> 执行：[25 Cursor 开发指令](已做指令/25-开发指令-AI智能客服与数据解释.md)；逐项记录：[51 执行清单](51-AI智能客服-逐项执行与验收清单.md)。

## 1. 要解决什么问题

在现有“AI 助手”菜单中，让用户直接问“怎么操作”“为什么数字是这样”。助手读取服务器上的操作说明，必要时查询当前工厂的业务数据，用有依据、可核对的语言回答。

这件事可行。文件夹负责保存说明，后端负责检索与受控查询，模型负责理解问题和组织答案。文件放入服务器并不会自动被模型读取，需要接通检索服务；无需训练模型。

| 场景 | 示例问题 | 回答依据 |
|---|---|---|
| 操作帮助 | 怎么补报？为什么产品删不掉？ | 已核对的操作手册、常见问题 |
| 数据查询 | 工单 A 做到哪了？ | 当前工厂的工单及工序数据 |
| 数字解释 | 两道工序报了 100 和 80，为什么完成数是 80？ | 实际明细＋完成数计算规则 |
| 复核解释 | 已经报工，为什么报表还没算进去？ | 待复核/通过/退回明细＋入账口径 |

## 2. 当前基础与缺口

2026-09-20 阅读本地代码确认；这是静态核查，不代表运行环境或真实模型已验收。

- `AiAssistantController`、`AiAssistantService`、`AiToolDispatcher`、`AiSessionStore` 已存在；仅 PC 管理员 role=1，工厂与用户取自 JWT。
- 当前模式为 progress（查进度）、guide（问工艺）；工具含工单查询、进度查询、产品定位、工艺资料读取。
- 工艺资料关联产品/工序，不等于系统操作手册检索。不能把通用操作说明硬绑到某个产品。
- `KnowledgeFileParser` 支持 docx/pdf/xlsx，当前不支持 Markdown/TXT；不能假定放入两本 Markdown 手册即可直接问答。
- 当前工具拒绝 sql/path/factoryId 等参数；没有自由 SQL 执行能力。
- `docs/30`、`docs/31` 可作为首批素材，需按当前页面核对。整个 docs 含开发指令、旧方案等，不能全部当客服知识。

## 3. 首版取舍

1. 在现有 AI 助手内新增 support“智能客服”模式，同一客服对话可查说明、查工单和解释报工；保留 progress/guide 原行为。
2. 先服务 PC 管理员；工人/H5/PDA 客服以后另立需求。
3. 首批知识仅为 UTF-8 `.md`、`.txt`；按模块和章节检索，支持服务器替换文件。复杂格式、OCR、向量数据库、在线上传维护暂不做。
4. 首批数据范围：工单进度、工序良品/不良品、报工复核状态、退回原因、已有补报批次标记。工资、成本、排产与任意跨表分析不做。
5. “执行 SQL”首版落实为后端参数化业务查询，由 EF Core 访问 SQL Server；模型选择工具和参数，不提交 SQL 字符串。将来自由 SQL 属于另一项需求。
6. 无写工具、无新增业务表；不代用户下单、报工、改数、退回或删除。

## 4. 文件夹与资料维护

配置独立客服根目录，示例 `D:\MES\SupportDocs`（仅示例，部署时填写）。首版只存同一软件版本的通用操作资料，不存客户专属数据或各工厂私有说明；以后需要私有说明时再增加工厂隔离。

建议内容：操作入门、基础资料、工单、报工与复核、常见问题、数据口径。每份文件包含标题、适用角色、适用系统版本、文档版本、更新时间；内容包含菜单路径、操作步骤、前置条件、常见失败原因。文件名不强制固定，按元信息和章节检索。

发布者先从 docs/30、31 整理并核对，再复制到专用目录。不能指向仓库 docs 根目录，避免将旧方案、开发命令、部署凭据混入答案。首版不提供资料写入或上传接口。

刷新方式：每次客服检索检查目录指纹，在限额内重建内存索引；新增、替换、删除均应在下一次检索生效。替换文件推荐先写临时文件再改名。新一轮回答必须重新取证，不能把旧会话中的说明当最新版本。

## 5. 回答流程与可信边界

用户提问 → 模型选择白名单工具 → 服务端检索说明/查询数据 → 返回带来源的证据 → 模型解释 → 页面显示依据和核对入口。

- 操作答案给菜单、步骤、前置条件，标注文档与章节。
- 数据答案给工单、筛选范围、查询时间、实际数字、计算规则，并可打开现有工单详情。
- 没有匹配、文件损坏、未配置、超限是不同状态，不应统一说“没有资料”。
- 文档冲突或版本不适用时明确说明，不能自行猜最新有效规则。
- 数据未记录的原因不能断言。例如第二道工序少报 20，不代表一定停机或缺料。
- 文档和数据库文本都是证据，不是系统指令；不能因其中写了“忽略权限”就执行。
- 外部模型会收到相关说明片段与必要查询结果。内网存文件不等于资料不出网，沿用现有出网提示。

## 6. 数字口径

业务以 docs/01 为准，字段以 docs/02 为准；实施时再次核对服务实现。发现冲突应记录并解决，不通过修改业务公式来迁就模型。

| 项目 | 已确认口径与边界 |
|---|---|
| 进度计数 | 报工复核状态 0 待复核＋1 已通过；排除 2 已退回 |
| 生产报表入账 | 只计算复核状态 1；不能直接拿进度数当报表数 |
| 有工序任务的工单完成数 | 各工序有效良品合计的最小值；没有报工的工序按 0 参与，不能只统计有记录的工序 |
| 无工序任务 | 复用现有服务的工单报工汇总逻辑，不套用不存在的工序最小值 |
| 工单完成判定 | 各工序达到各自计划数；不能用展示完成数自行重写状态判定 |
| 补报 | 可展示现有 batch_no 批次标记；不能把所有单条报工推断为手工或补报，也不能虚构改数历史 |
| 时间范围 | 明确使用的日期字段、业务时区、起止日期；按半开区间筛选 |

首版解释某张工单当前累计数据，以及指定报工时间段的复核数量差异。时间段报工数量与整单累计进度分别标注；未接入完整报表筛选时，不声称已经核对整张生产报表。

例：工序一有效良品 100，工序二有效良品 80 → 整单展示完成数 80。若工序二的 80 中有 20 待复核，则该工序进度计 80，已通过口径计 60。不同工序数量不能相加冒充最终产品产量。
