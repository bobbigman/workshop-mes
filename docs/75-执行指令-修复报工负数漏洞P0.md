## 一、背景（已实测，非推测）

在报工接口 `POST /Report` 上，`goodQty=-1` 和 `defectQty=-1` 均返回 **code=0 且真实写入数据库**（把 GD20260914003 切菜工序「已报良品」从 100 改成了 99）。

连锁后果（已实测）：负数写入后，工单列表接口 `GET /WorkOrder` 报错：
```
code=1  msg=报工汇总数量非法：operationId=1
```
**整个工单列表功能瘫痪**。因此这是 P0 严重缺陷，须立即修复。

## 二、根因（已读源码定位）

文件：`backend/Services/ReportService.cs`

- **`SubmitAsync`（新增报工，第 87 行起）**：校验块在 122–128 行，只有——
  - `dto.DefectQty > 0 && dto.DefectId == null` → 「有不良品时必须选择不良品原因」
  - `dto.DurationMinutes < 0` → 「报工时长不能为负」
  - `dto.DurationMinutes > 1440` → 「单次报工时长不能超过24小时」
  
  **漏了良品/不良品数本身的非负校验**。「超出计划数」防线（137 行 `alreadyGood + dto.GoodQty > planQty`）拦不住负数——`99 + (-1) = 98 < 100` 不超计划，负数直接溜过。
  
- **`UpdateAsync`（修改报工，第 193 行）已有同款校验**：
  ```
  if (dto.GoodQty < 0 || dto.DefectQty < 0) throw ... "良品/不良品数不能为负"
  ```
  → 说明这是**疏漏**：新增路径没补，修改路径有。修复目标就是对齐 `UpdateAsync` 的文案与逻辑。

## 三、修复动作（一处改动）

在 `SubmitAsync` 校验块开头（第 122 行 `if (dto.DefectQty > 0 ...)` **之前**）插入：

```csharp
// P0 修复：良品/不良品数不能为负（对齐 UpdateAsync 文案，防负数报工污染汇总）
if (dto.GoodQty < 0 || dto.DefectQty < 0)
    throw ThrowHelper.Biz(nameof(SubmitAsync), "良品/不良品数不能为负");
```

不改其他逻辑。`BatchReportAsync` 第 300 行已有「补报良品数必须大于 0」，无需动。
