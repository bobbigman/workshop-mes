## 0. 一句话定位

把小工单从"报工系统"升级成"会答工艺的制造知识库"：**文件放硬盘，数据库只存路径，微信那头只吐答案，绝不吐路径。**

---

## 1. 文件怎么存（问题 1）

**结论：物理一个根文件夹，逻辑靠数据库关联。不要"每个工序一个文件夹"。**

| 方案 | 做法 | 判定 |
|---|---|---|
| A. 一个根文件夹堆所有文件 | 文件全丢一个目录，归属靠数据库记 | ✅ 采纳（物理层） |
| B. 每个工序记「文件夹+文件名」 | 用目录层级表达归属 | ❌ 不采纳 |

理由：

1. **一个文件会被多个产品/工序共用**（同一份工艺适用于多个产品）。文件夹层级表达不了"一文件挂多处"，数据库关联表能。
2. **绝对路径是死路**。`D:\工艺\产品A.docx` 一搬电脑、一换服务器就断链。要存**相对根目录 + 文件名**，系统里配一个可改的"文件根目录"。
3. **文件归属靠数据库表记录**，不是靠文件夹位置。文件夹只是文件睡觉的地方，归属关系是账本。

所以最终形态：

- 物理：一个"知识库根文件夹"，所有文件都放里面（也可按需再分一两个子目录，但不靠目录表达归属）。
- 数据库：一张附件表，存 `相对路径 + 挂在哪个产品/工序 + 版本号 + 上传人/时间`。**不存文件二进制、不存抽取出的全文**（保持数据库瘦）。

## 2. RAG 怎么实现、要不要索引（问题 2）

RAG = 检索 + 增强 + 生成。对应到我们这套：**先定位该读哪些文件 → 读出来 → 交给大模型组织成大白话答案。**

"要不要索引"要分两层看，别一上来就上向量库：

### 2.1 文件级索引（必须有，而且极便宜）

就是数据库那张关联表：**问"产品 A 怎么生产" → 按产品查工艺路线 → 顺出挂在它下面的所有文件**。这一步是 SQL 查询，不是什么高级东西，但它是"精准定位"的关键——没有它，AI 只能在一堆文件里瞎翻。

### 2.2 内容级索引（向量检索，demo 不做）

把文件切成小块、转成向量、按语义相似度检索。这是网上"知识库问答"那套重家伙（向量库、embedding、切片）。

**结论：demo 阶段不需要。** 因为一个产品顶天几个文件，直接把全文塞进大模型上下文问就行。什么时候才需要？文件多到几百上千、单个文件又大，塞不进上下文时，再上向量检索。**现在上等于杀鸡用牛刀。**

### 2.3 大模型放哪（这是本稿最关键的架构拍板）

用户设想"小工单系统内含大模型、有读文件能力（像 Cursor）"。这里要纠正一个误解并定方向：

- **大模型不会读二进制文件**。docx / pdf / excel 不是纯文本，模型一口吞不下。所以系统内部必须有个"翻译官"小组件：把 docx / pdf / excel 解析成文字。
- **demo 期：大模型借用扣子的，不内嵌。** 系统只做"翻译官 + 按产品工序捞文件"，把捞到的**文字内容**吐给扣子，扣子用它的模型组织成大白话。这样系统侧零大模型成本，最轻。
- **正式期：台子不变，仍是微信连扣子 → MCP → 小工单系统。** 变的只有两处：① 发动机换 DeepSeek（扣子支持接第三方模型）；② 部署从"个人电脑 + cpolar"挪到"客户内网固定 IP 服务器"常驻。**不需要、也不要**脱离扣子去自建微信入口。
- **「系统内嵌大模型」是可选分支，不是默认路径。** 只有当客户要求「彻底不用扣子 / 数据不出厂 / 完全私有化」时，才走内嵌。默认不碰。

一句话：**系统负责"找得到、读得出"，扣子负责"说得好"；路径只活在系统内部，扣子只拿到文字和答案。**

## 3. demo 轻交付方案（问题 3）

最小闭环，目标只有一条：**微信问"产品 A 怎么生产" → 得到一句大白话、带工艺要点的答案。**

要做（就 3 件）：

1. **一张附件表**：存相对路径 + 挂产品/工序 + 版本号。（瘦表，不塞内容）
2. **一个"翻译官"组件**：docx / pdf / excel → 文字。用现成开源库，不自己造（扫描型 pdf 需 OCR，demo 不做）。
3. **第 6 个 MCP 工具 `query_production_guide`**：只读不写；内部按产品工序找文件 → 解析成文字 → 返回给扣子。

明确不做（边界）：

- 不做向量库 / embedding / 切片。
- 不做文件版本历史管理（只留版本号字段，够用就行）。
- 不做公网常驻服务器（demo 继续个人电脑 + cpolar）。
- 不做文件上传/管理页面（demo 先手工把文件放进根文件夹、手工登记到表里；管理动作等验证通了再上 PC 页面）。

## 4. 已拍板 & 待拍板

### 已拍板（2026-09-18）

1. **文件根文件夹 → 做成参数**。`appsettings.json` 配一个 `KnowledgeBase:RootPath`，附件表里只存**相对该根目录**的路径。换电脑、换服务器，只改这一个参数，所有路径不断链。
2. **文件格式 → docx / pdf / excel 都支持**。翻译官三种全接，用现成开源库。注意：pdf 分两种——**文字型**能直接抽文字；**扫描/图片型**要 OCR（重活）。demo 先只支持文字型 pdf，遇到扫描件提示"请提供电子版"。
3. **附件挂法 → 产品、工序都能挂（多态关联）**。附件表加 `ref_type`（`product` / `operation`）+ `ref_id`。一个文件可以挂产品、也可以挂工序，**一个文件挂多处 = 插多条记录**（同一个相对路径多行）。查询"产品 A 怎么生产" = 直接挂 A 的文件 + 挂 A 所有工序的文件，一起捞。

### 已拍板（2026-09-18 续）

4. **大模型：全程用扣子搭台，发动机 demo 用默认、正式换 DeepSeek**。这俩不是二选一，是"台子"和"发动机"两个东西——
   - 扣子 = 平台（搭台子：智能体编排 + MCP + 微信入口，`docs/47` 已跑通）；**demo 和正式都不换**。
   - DeepSeek = 模型（发动机：只负责"给句话还句人话"，不管接微信/挂 MCP）。

   分两段定：

## 5. 一句话总结

**方向：一个根文件夹存文件，数据库存相对路径+归属（瘦表），系统当翻译官把文件读成文字，扣子当嘴把答案说出去（正式期换 DeepSeek 当发动机）。demo 只做"找得到、读得出、说得好"这一个闭环，向量库和内嵌大模型都往后放。**

## 6. 分析层草稿（字段 / 接口 / 选库，仍非开发指令）

> 本节把方向落到"附件表长什么样、第 6 个 MCP 工具怎么对扣子、翻译官选哪个库"。只定形状，不写代码。

### 6.1 附件表 `base_knowledge_file`

命名沿数据字典前缀：挂产品和工序，属基础数据范畴，用 `base_` 前缀（与 `base_product`、`base_operation` 同族）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT IDENTITY(1,1) PK | 主键 |
| factory_id | BIGINT NOT NULL | 工厂（多租户，同现有表） |
| file_name | NVARCHAR(256) NOT NULL | 显示名（给人看，可与磁盘文件名不同） |
| relative_path | NVARCHAR(512) NOT NULL | 相对 `KnowledgeBase:RootPath` 的路径，**不存绝对路径** |
| file_type | NVARCHAR(16) NOT NULL | `docx` / `pdf` / `excel`，决定翻译官用哪个解析器 |
| ref_type | NVARCHAR(32) NOT NULL | `product` / `operation`（口径同 `sys_custom_field.target`） |
| ref_id | BIGINT NOT NULL | 挂的产品 ID 或工序 ID |
| version | NVARCHAR(32) NULL | 版本号（如 `V1.2`），够用即可，不做历史管理 |
| created_by | BIGINT NULL | 登记人 |
| created_at | DATETIME2 DEFAULT SYSDATETIME() | 登记时间 |

关键口径（草稿，非最终）：

1. **一个文件挂多处 = 插多条记录**：同一个 `relative_path` 可以多行，`ref_type`+`ref_id` 不同。所以 `relative_path` **不加唯一约束**。
2. 唯一约束（可选）：`(ref_type, ref_id, file_name, version)` 唯一，防同一对象下重复登记同名同版本。
3. **不存文件二进制、不存抽取全文**——保持数据库瘦，读时现翻译（+内存缓存）。
4. 删除顺序：本表挂在 `base_product` / `base_operation` 之上，**先删本表记录，才能删产品或工序**；插入到 `docs/02-数据字典.md` 的删除倒序链最顶层。

### 6.2 第 6 个 MCP 工具 `query_production_guide`

写法对齐现有工具（`[McpServerToolType]` + `[McpServerTool]`，返回 JSON 字符串给扣子直读）。

**入参：**

| 参数 | 类型 | 说明 |
|---|---|---|
| authToken | string? | 授权码，同现有工具；演示模式可空 |
| productCode | string? | 产品编号（精确，推荐）；或 productName 模糊 |
| productName | string? | 产品名称 |
| operationName | string? | 可选，定位到某道工序；不传=整条路线 |

**内部流程：**

```
按 productCode/Name 找到 base_product
  → 顺 base_routing → base_routing_step → 各 base_operation
  → 捞 base_knowledge_file：
       直接挂该产品的（ref_type=product）+ 挂路线各工序的（ref_type=operation）
  → 按 relative_path + KnowledgeBase:RootPath 拼磁盘路径
  → 翻译官按 file_type 解析成文字
  → 组装返回
```

**出参（JSON，只吐内容、绝不吐路径）：**

```json
{
  "code": 0,
  "product": { "code": "A-1001", "name": "法兰盘" },
  "routing": ["下料", "车削", "钻孔", "检验"],
  "files": [
    { "file_name": "车削作业指导书.docx", "version": "V1.2", "content": "……车削工序要点文字……" }
  ]
}
```

- 扣子拿到 `content`（文字）后，用自己的模型组织成大白话回微信。
- **`relative_path` 只活在后端内部**，永不进出参——这正是"扣子读不到文件路径"的落地保证。
- 只读不写，跟现有 5 个工具一致；管理/上传动作先走 PC 端（符合"先 PC 管理动作"节奏），demo 阶段手工放文件 + 手工登记表。

### 6.3 翻译官选库（.NET 开源，不自己造）

| 格式 | 推荐库 | 备注 |
|---|---|---|
| docx | `DocumentFormat.OpenXml`（微软官方） | docx 本质是 zip+XML，官方 SDK 最稳 |
| pdf | `UglyToad.PdfPig` | 纯托管、免费无授权坑；只抽文字型 pdf，扫描件需 OCR（demo 不做） |
| excel | `ClosedXML` | xlsx 好上手；xls 旧格式另议，demo 可只认 xlsx |

- 缓存：翻译结果按"相对路径 + 文件最后修改时间"做内存缓存，文件没变不重翻。
- 扫描型 pdf：解析不出文字时，返回明确提示"该文件是扫描件，请提供电子版"，**不静默造假**（对齐异常处理规约）。

> **落地踩坑（2026-09-18 实测）**：
> 1. `DocumentFormat.OpenXml` 必须用 **2.20.0**（`<3.0.0`），因为 `ClosedXML 0.102.3` 依赖约束是 `>=2.16.0 && <3.0.0`，用 3.x 会 NU1608 冲突。
> 2. `UglyToad.PdfPig` 在本机 nuget 镜像（api.nuget.org 被重定向到 nuget.azure.cn）上只有 `0.1.9-alpha001-patch1` 和 `1.7.0-custom-5` 两个版本；用 `0.1.9-alpha001-patch1` 会因子包（Core/Fonts/Tokenization/Tokens）对不上版本而 NU1603 警告。最终用 **`1.7.0-custom-5`**（主包+子包同版本），API 与标准一致（`PdfDocument.Open` / `GetPages()` / `Page.Text`），0 警告 0 错误通过。
