# Codex复盘：开发技巧总结

> 日期：2026-11-12。
> 来源：微聚小工单项目文档及本次与用户的复盘讨论。
> 用途：作为下个项目使用 AI 开发的学习素材，不是本项目的新开发指令，不据此启动功能或修改现行业务规则。

## 一、本次复盘的判断

本项目一部分返工，来自业务方向还在讨论时，方案已经推进成完整功能；后续调整就连页面、接口、表结构和数据一起改。

另一类反复出现的问题，是提示和限制不符合实际操作：文案有技术味或说明书味、提示指错地方、尚未填写完成就报错、可以继续的状态却显示得像失败。用户需要事后逐处纠正，使用时也容易感觉“卡住了”。

AI 容易把“解释充分、检查严格、功能完整”当成完善，却没有充分判断：功能是否真有用、此刻是否需要提醒、操作是否确实不能继续、用户看完究竟该改哪里。

这些判断有文档案例支持，但不能把所有改版都算作错误，也不能仅凭指令断言每项设计都是 AI 首先提出。客户需求演进、正常视觉打磨、必要的正确性校验应分别看待。

## 二、下个项目重点执行的五条建议

### 1. 新功能先验证有用，再做完整实现

**本项目案例：**“学操作”先做工序闪卡，又做改名和管理页直接学习，最后整套拆除，涉及两端页面、后端、三张表和种子数据。84 明确记录用户确认“学操作”不是想要的东西。

**下次做法：**

- 新概念先用草图或简单可点击样例，说明“谁在什么情况下用、解决什么问题”。
- 方向未定时，不急着接正式菜单、接口和数据库。
- 已经做出页面，不是继续扩建的理由；发现方向不对，先停下来核对目标。
- 明确且低影响的小修改直接完成，不把每项改动都变成原型和审批流程。

### 2. 含糊需求先用操作实例说清楚

**本项目案例：**2L 记录了报工预填方向回滚，实际目标是根据历史报工推荐“派给谁”。报工预填、推荐执行人、排产排序、无人自动派工是不同功能，不能用“智能”一词替代定义。

**下次做法：**

- 开工前让 AI 复述具体操作，例如：“主管打开工单，选一道工序，看到推荐人员，点选后完成派工。”
- 明确操作者、入口、输入、动作和结果，避免只讨论功能名称。
- AI 先查现有代码和有效文档；只有无法确定且会改变产品行为的歧义，才集中提问。
- 常规实现由 AI 自行完成，不把事实核对和技术选择反复交还用户。

### 3. 核心规则用真实案例算通，外部能力用真实环境试通

**本项目案例：**400/401 记录工价从工序内手选转为属性驱动、集中价目表自动取价；411 对齐字段归属和产品绑定口径；413 又要求统一价格来源。Pushplus 的回滚记录则说明，接口集成后发现消息提醒效果不符合车间诉求。

**下次做法：**

- 涉及金额，先拿客户真实资料选出正常、缺失、冲突和特殊案例，核对计算结果。
- 先确定属性归属、取价时机、锁价依据、调价对旧单的影响，再确定表结构和完整页面。
- 涉及推送、扫码、第三方接入，先用目标设备和实际账号验证效果及开通条件。
- 现场条件成立、核心案例算通后，再建设配置、自动流程和完整集成。
- 演示与生产分清：固定样例可简化范围，真实业务的权限、事务、金额追溯不能省略。

### 4. 提示和拦截必须有依据，正常操作要顺畅

**本项目案例及反复程度：**

| 记录 | 具体问题或调整 |
|---|---|
| 55 提示文案去机器味 | 清理追踪号、内部参数、运维话术；避免用户点到无权限入口后再收到 403 |
| 432 建单取价提示文案可读性 | 清理裸 ID、eq 等技术表达，说明问题和处理位置 |
| 433 建单工艺属性取价提示不误导 | 工序工艺未填不能说成产品资料缺失；选产品后不自动取价冒红字 |
| 434 → 445 | 从整段错误提示，继续调整为字段级定位、输入旁感叹号，减少长文重复 |
| 452 缺价与单价提示一体化整改 | 区分可保存的待办和审核时真正阻断，避免红字被误读为整单作废 |
| 240 AI 助手页拿掉严肃使用说明（待做记录） | 记录橙色警告条太严肃、“我知道了”确认门槛影响直接提问的诉求；不能据此认定已实施 |
| 262 AI 应答口径全链路落地 | 真实模型把能力咨询误答成“本期只读、不能修改”，后续整改检索编排 |
| 16 未来待办及 132A 对标记录 | 记录按无报工时长猜“工序停滞”的预警方向被纠偏；不据此断言当时已全部上线 |

仅建单取价提示就有 432 → 433 → 434 → 445 → 452 多份连续相关指令，涉及措辞、触发时机、定位和严重程度。它们不能当成五次独立故障，但足以说明这类体验问题持续出现，需要在首次实现时约束。

**下次做法：**

- 没操作、没填完时，不提前显示失败；必要说明可以就近展示。
- 普通说明用中性色，待办用黄色；只有确实阻断本次操作才用红色，严重程度与行为一致。
- 每条提示只说“哪里有问题、怎么处理”，使用真实名称和按钮名，不暴露内部 ID、技术词，不加口号和长篇解释。
- 能定位到字段，就在字段附近提示；修正后及时清除，避免弹窗、字段、整行同时重复同一段话。
- 新增预警要有可核实的触发依据和处理动作，不能靠“可能有风险”猜异常。
- AI 不自行增加确认弹窗或强制前置步骤。确需拦截时，说明所依据的业务规则。
- 权限、金额、数据一致性等必要校验继续保留；减少打扰不能以隐藏真实失败为代价。

验收必须包含“正常操作不被打扰”：不仅验证错误能提示，还要验证正常流程没有多余弹窗、提前警告、重复提醒和误导性红字。

### 5. 每个模块明确现行方案，避免历史指令反复影响开发

**本项目案例：**405 讨论记录包含方向演进；411 专门对齐新旧口径，并提醒原型和部分权威文档当时仍有旧内容；413 又覆盖前面的部分兼容方案。一些“已做指令”正文也明确标着尚未现场验收，目录不能独自代表完成状态。

**下次做法：**

- 每个模块保留一个明确的当前入口，列出现行规则、替代关系、实现状态和未验证事项。
- 改规则时同步更新权威文档，历史材料开头标明已被什么替代。
- 不依赖不断新增补充指令，让执行者自行拼出最终方案。
- 区分文档定稿、代码完成、本地验证、现场验收和部署，不把它们统称为“已完成”。
- 每次只交付明确范围，完成适当验证后提交；达到验收就停止顺手扩展。

## 三、下个项目可以直接使用的 AI 开工约定

> 先读当前有效文档，用具体操作说明本次目标。方向未定的新功能先做样例；金额规则先用真实案例核对，外部能力先验证现场效果。不能从现有依据确定且会改变产品行为的歧义，一次集中确认；常规实现自行完成。
>
> 不自行新增预警、确认步骤或操作限制。新增提示必须说明触发时机、严重程度、是否允许继续及处理办法。普通待办不能表现成失败，填写过程中不提前报错。提示用用户熟悉的名称，不暴露内部技术词；真实错误必须保留并可排查。
>
> 验收同时检查正确性与正常操作是否顺畅。交付说明实际验证结果和剩余限制，同步现行规则及替代关系；达到本次验收后，不顺手扩展功能。
