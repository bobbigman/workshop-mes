# AI提效分析方案——以小工单为原型（Codex V2）

> 日期：2026-11-12。
> 性质：分析方法与后续执行方案，不是项目统计报告或业务开发指令。
> 本次交付：综合本文件夹六份方案、总结与双方点评，形成可执行的V2；尚未开展全量分类统计。
> 核心顺序：资料盘点 → 全文提取 → 事项归并 → 分类统计 → 证据复核 → 原因分析 → 提效试验。

## 一、要回答什么

用户关心的是：项目改了哪些、为什么反复改、花了多少时间，以及下次怎样减少无效工作。不能只检索几个案例后给通用建议，也不能把一批文件数量换成百分比就称为原因分析。

本轮后续分析要检验：

1. 哪些模块的修改最多？其中多少是首次开发、正常完善、缺陷修复或方向性重做？
2. 提示、预警、确认步骤和操作限制的问题是否高频？是文案不顺、指引错误，还是实际阻断？
3. 需求理解、业务决定变化、契约遗漏、实现错误、环境故障分别造成了什么影响？
4. 有可靠记录的时间花在哪里？没有时间记录时，哪些比较仍然成立？
5. 原型、真实案例试算、现场试通、集中修改等做法，是否与更少重复修改相关？有什么反例？

以上均为问题，不预定“AI味多”“原型一定有效”“工单改得多很正常”等答案。

## 三、范围、快照与主键

### 3.1 分层读取，公开覆盖情况

- **盘点范围：**递归盘点整个docs，按目录、类型及用途列清单；同时登记与分析相关的规则和外移资料。
- **核心事件来源：**已做、未做、处理中、已作废、归档中的指令和执行记录，以及下一步清单、测试反馈、验证记录。
- **辅助核对来源：**权威文档、原型、真实业务资料、讨论稿、Git历史；只在有助于判断事件时读取，不把每份资料当任务。
- **方法资料：**本“经验复盘”目录及本轮生成物单列，不进入业务改动次数与耗时统计，避免循环计数。
- **排除内容：**密钥、密码、连接配置等无关敏感内容；不可读附件或外移未取得资料登记缺口，不能算已读。手机画面核验遵守项目ADB规则，不用OCR。

读取MD、TXT、HTML以及相关Word、表格和附件的实际内容。关键词只用于发现候选，不能代替全文归类。无法确认覆盖全部时，报告必须称“已覆盖样本”，不能称整个项目。

### 3.2 固定输入，才能复算

记录运行日期、纳入/排除规则、递归方式、文件相对路径和内容哈希。新增、搬移、替换或修改的文件作为增量，记录统计版本。

- 文件分配稳定的`file_id`，路径用于定位，哈希识别内容版本；移动后保留映射，不能因此新增一个开发事件。
- 事项、事件、时间记录分别使用独立ID。文档编号仅展示，重号不要求修改原业务文件。
- 同内容文件保留来源映射；同名、同编号不自动合并。事项拆分/合并也记录旧ID去向。

## 四、建账单位和最小字段

| 单位 | 含义 | 不代表什么 |
|---|---|---|
| 文件 | 一份资料及其快照 | 不等于一次开发 |
| 事项 | 相对独立的用户目标，例如建单缺价提示 | 不等于一个目录或页面 |
| 事件 | 事项中一次可辨认的决定、实现、修复或撤回 | 不等于每一份执行或验收文档 |
| 时间记录 | 有对象、范围、口径和来源的时间证据 | 不等于文件日期或提交间隔 |

后续使用UTF-8 CSV保存明细、Markdown保存说明；需要筛选时另做工作簿。先用最小字段开工，不为建账搭数据库或通用框架。

| 台账 | 必填信息 |
|---|---|
| 资料清单 | file_id、路径、哈希、资料用途、已读/未读/不可读、纳入或排除理由 |
| 事项/事件 | 事项ID、事件ID、标题、主模块、辅助标签、改前→改后、性质、实施状态、日期及来源、前后关联、证据ID |
| 分类与原因 | 事件ID、问题表现、原因主类、原因证据等级、提出来源、存在争议或未知之处 |
| 时间 | 时间ID、关联对象、原文、类型、时长或范围、执行者、来源、重叠组、是否纳入汇总及理由 |
| 证据与缺口 | 证据ID、路径和章节/短摘录、支持什么、矛盾或缺失、核对结果 |

保留“原文说法”和“分析者判断”两列，不把推断写成原始事实。没有耗时的事件仍然有分析价值，不因此丢弃。

## 五、先校准，再全量整理

1. 从不同目录、模块和性质中选一批校准材料，至少包含重号、跨模块、仅讨论、实现后撤回、文档日期冲突、时间记录和多阶段验证样例。
2. 用全文生成事件明细，实际检验分类能否落地。例：A方案、B执行单、C验收记录如描述同次实现，合为一个事件；D后来撤销已实现行为，另建事件。
3. 对无法一致判断的分类修改定义，保留版本与重分类记录；不要为保持旧数字强行套类。
4. 分类规则稳定后逐份处理剩余核心来源，分批保存检查点。试点结果不能外推为全项目比例。
5. 普通事件按模块、性质、来源分层抽检，公布抽检数、误分类数、修正项；用于核心结论的返工链、耗时、争议和金额事件全部复核。不固定“抽20份就可靠”。

脚本负责清点、候选定位、汇总和一致性检查；语义判断依据全文和关联证据。重复运行数字相同只能证明计算稳定，不能证明归类正确。

## 六、分类口径

### 6.1 主模块与辅助标签

主模块按本次主要改变的用户行为确定：工单、报工/复核、工序价目表/取价、工资、工作台/看板、基础资料、登录/权限、企微/通知、AI助手、环境/交付、跨模块或未知。

主模块只选一个，确实无法合理拆分的共同改动归跨模块；其它受影响模块用辅助标签。主模块表可加总，多标签表不可直接加总。不能依关键词先后决定归属。

### 6.2 改动性质

| 主类 | 判定标准 |
|---|---|
| 首次开发 | 首次实现该用户目标 |
| 正常完善 | 新增或细化合理能力，无证据表明之前违反当时要求 |
| 缺陷修复 | 已实现行为违反当时明确要求或正确性约束 |
| 方向性重做 | 已实现成果因理解、产品决定或核心模型变化被替换/撤销 |
| 仅方案/文档变化 | 有修改记录但无对应代码实现变化证据 |
| 环境/交付处理 | 网络、依赖、构建、打包等处理 |
| 未知 | 无法据证据判定 |

实施情况另外记录：仅讨论、已定待做、实施中、已实现、已撤回、未知。验证按构建/单测/接口/页面/真机/现场分别记录通过、失败、未验证或未知。历史描述与当前状态冲突时保留时间线，不用目录覆盖正文。

验收记录关联对应事件，不自动计一次产品改动。缺陷修复与方向性重做分别统计；不能把“优化”标题全部算返工，也不能把未实施方案作废算代码重做。

### 6.3 原因与责任分开

原因主类：需求理解偏差、需求/产品决定变化、模型/契约遗漏、实现缺陷、提示交互问题、文档/版本不同步、外部环境、其他/未知。优先记录可证明的直接原因；多因素无法选主因时保留多因或未知，不强编唯一根因。

每条归因标记：原文明确、交叉核实、分析推断、未知。“用户提出修改”不代表用户造成错误；“AI写代码”不代表AI造成返工。责任判断需要当时要求、建议和实现证据。

### 6.4 提示体验专项

标签包括：技术词/内部ID、空泛口号或说明书腔、内容不准、处理方向错、触发过早、重复提醒、颜色与实际阻断不符、无必要确认、无依据预警、错误定位不清。

每条核对四件事：用户做了什么、提示何时出现、是否真被阻断、改后能否正确继续。区分只改文字、调整展示/触发、改变放行规则。统计专项问题在全部已实现事件及纠错事件中的占比，另列无问题/正常完善案例，不能只搜问题词。

## 七、时间与节奏怎么统计

| 证据 | 允许表达 | 禁止表达 |
|---|---|---|
| 正文明确实际投入 | 对应任务的有记录投入 | 未知范围下推全项目总工时 |
| 起止时间 | 经过时长，注明可能含等待 | 净工时或人时 |
| 回忆的约数 | 回忆估计，单列范围 | 与精确记录混成精确合计 |
| 开发前估时 | 计划时间 | 实际耗时 |
| 业务日期/修改日期 | 有证据的事件日/资料更新日 | 真动手日 |
| 两个记录日间隔 | 记录跨度、无记录间隔 | 闲置、拖延、不敢决定 |

时间核对要求：

- 同任务总时间和子步骤只选一种汇总方式；重复转述去重，多人并行区分经过时间与人时。
- 时间仅能归属整项任务时，不全部记为返工成本；无法拆分的保持整项口径。
- 无记录留未知，不记0，不用文件数、动手日、提交间隔或少量案例折算。
- 日期取正文明确的相关业务日期，并以Git/记录交叉核对；文件名和mtime另存，不混用。跨度注明起止是否含当日。
- 时间覆盖率按相应目标事件数计算；若只有部分事件有时间，展示其样本量、合计/中位数/范围和偏差，不能外推整体。

耗时不足时，仍可分析已确认事件数量、修改链、影响范围和验证缺口；明确“不能按耗时排序”，不因缺时间退回主观判断。

## 八、先交什么统计

| 表 | 必须展示 |
|---|---|
| 资料覆盖 | 纳入、已读、未读、不可读、排除数量，按目录与类型分布 |
| 主模块×改动性质 | 去重事件数、事项数、实现状态、未知数 |
| 原因分布 | 已实现纠错/重做事件的原因、证据等级、未知及多因 |
| 提示体验专项 | 各标签事件数、涉及事项数、仅文案/展示/放行变化、实际阻断情况 |
| 验证覆盖 | 各验证层级的通过/失败/未验/未知，按适用范围计算，不把未现场验一概叫无人验收 |
| 时间分布 | 口径一致的时间记录、覆盖率、重叠排除、已知时间及无法归属的部分 |
| 时间节奏 | 事件日期分布及资料更新日期分布分开；不将其换算工作投入 |
| 重点修改链 | 每次改前改后、已实施与否、原因、规则依据、时间证据 |

分母规则：

- N为首次开发、正常完善、缺陷修复、方向性重做中确认已实现的事件总数。修复占比、重做占比分别除以N，称“事件占比”。
- 原因分析以已实现修复/重做事件为目标集，展示全体分母及未知，不能只报已知原因样本占比。
- 标签是多选；总数以事件ID去重。事项数和事件数分开，不把文件占比写成返工率。
- 任何百分比同时列分子/分母；小样本给原始数，避免只报百分比制造强结论。

## 九、如何形成结论和优先级

每条结论使用：**观察结果 → 台账ID和证据 → 可支持的解释 → 其他可能解释/缺口 → 建议 → 如何验证建议**。

具体事件有直接证据即可报告，不要求每条事实都有占比；“主要、高频、最多、最耗时”等总体判断必须有覆盖范围与可比统计。

优先级分别看：正确性风险、有记录的耗时、重复事件数、用户操作影响。不得用未经授权的权重合成一个看似精确的总分。钱、权限和数据错误即使次数少也要独立突出。

从排名靠前的事项选择深入分析对象，同时选择相近且顺利完成的事项对照。原型出现后少修改只说明相关，未使用或记录缺失也可能解释；除非证据充分，不写成原型导致成功。不能因关键词没出现就断言规则未执行。

## 十、将建议变成下一批任务的试验

| 待检验做法 | 适用条件 | 记录与比较 |
|---|---|---|
| 同页多项调整集中展示改前/改后 | 布局、按钮和文案需要一起看 | 记录准备成本、被取消/改写需求、实施后固定观察窗口内纠错与新增需求，二者分开 |
| 业务案例表/操作实例 | 状态、权限、取价、锁价等规则 | 核对正常、缺失、冲突和边界输入输出，记录实施后遗漏；操作实例可以检验规则，静态图不能独自证明正确 |
| 提示可读性与不打扰检查 | 用户提示、确认和预警变化 | 检查10秒内能否理解问题和处理动作，同时验证正常流程；AI自检与用户/真实角色实测分开记录 |
| 外部通道小规模试通 | 推送、扫码、设备接入 | 记录目标环境下是否达到实际目的，再决定完整集成 |
| 单一现行裁决入口 | 多指令相互覆盖 | 记录生效规则和被替代条目，检查后续是否仍按旧契约实现 |
| 定期清理想法池 | 已被替代、依赖失效或无当前需求 | 记录保留/搁置/作废理由及恢复成本；年龄只作复查信号，不自动作废 |

没有客户时，用用户本人或明确角色场景评审样例、业务案例与最小试用，标“内部验证”，不冒充市场验证。AI核对既有事实及常规实现自行完成，未定且影响业务的规则集中请用户决定，不把每个技术细节都升级为确认。

不强制花半小时出图、不强制否掉一项、不宣称必省三条指令。试验前固定观察窗口，例如14天；按同类任务、复杂度及实际使用情况比较，记录样本量与干扰因素。没有可靠前后对照，不报提效百分比。
