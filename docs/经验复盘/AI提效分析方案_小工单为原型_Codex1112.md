# AI 提效分析方案——以微聚小工单为原型

> 日期：2026-11-12；整理：Codex。
> 状态：分析方案，尚未完成全量分类统计。
> 本次交付：规定资料整理、分类统计、证据核对和结论形成的方法；不启动业务开发、数据修改或部署。
> 核心要求：先整理数据，再分类统计，最后解释原因并提出建议。不能检索几个案例后，直接当成全项目结论。

## 一、分析目标与待检验问题

利用本项目已有开发资料，回答哪些工作消耗了时间、哪些修改反复发生、哪些返工可以避免，以及下个项目怎样改善。

以下是待检验问题，不是预设结论：

1. 提示文案、预警、确认弹窗和操作限制，是否构成较多重复修改？
2. 需求理解错误、方向变化、设计遗漏、实现缺陷、环境故障，各占多少有记录的改动？
3. 哪些模块修改次数最多，哪些实际耗时最高？两者是否一致？
4. 哪些是正常完善，哪些是推翻已有成果的返工？
5. 哪些改善措施有案例支持，哪些仍只是推测？

旧的《开发技巧总结》作为初步观察和待检验假设，不能用来给原始任务预先定性，更不能作为证明自身结论的统计来源。

## 二、资料范围与整理顺序

### 2.1 先建立资料清单

先盘点整个 docs，按文件类型、目录和内容用途统计数量；之后逐份登记有效内容。不局限于标题含“返工”“提示”的文件，否则会遗漏反例并放大目标问题。

| 资料 | 主要用途 | 注意事项 |
|---|---|---|
| 已做、未做、处理中、已作废、归档指令 | 提取需求、改动、替代关系、实施与验证状态 | 目录不等于完成状态，编号不一定唯一或代表时间顺序 |
| 开发手册、PRD、数据字典、接口说明 | 了解当时规则与最终契约 | 当前规则不能倒推早期设计必然错误 |
| 测试反馈、验证记录、下一步清单 | 识别实际故障、复验、待办 | 区分计划验收与实际执行结果 |
| 讨论稿、原型、推广及竞品分析 | 识别方向来源与取舍过程 | 讨论不等于决定，决定不等于实施 |
| Markdown、文本、Word、表格、HTML及图片附件 | 补充正文与人工反馈 | 无法读取的列入缺口，不能默认没有信息；真机画面遵守项目 ADB 规则，不用 OCR |
| Git 历史（第二阶段按需只读核对） | 核对实现、回滚和时间顺序 | 提交次数不等于任务数，提交间隔不等于工时 |

不读取或输出与分析无关的密码、密钥及连接配置。若关键分析对标资料已移出 docs，登记外部依赖及可访问情况，不能把未读资料算入已覆盖范围。

### 2.2 记录覆盖范围

资料清单至少包括：路径、类型、用途、是否已读、提取状态、疑似重复或替代关系、不可读原因、是否包含时间证据。

分析开始时固定资料快照或记录文件哈希；后续文件变化列为增量，不让同一轮统计分母悄悄变化。文件修改时间只用于识别版本变化，不当作业务发生日期。

## 三、统计单位：文件、事项、改动事件分开

| 单位 | 定义 | 用途 |
|---|---|---|
| 文件 | 一份资料或一个版本 | 衡量资料覆盖，不代表开发工作量 |
| 事项 | 一个相对独立的用户目标，例如“建单缺价提示” | 把相关指令、讨论、测试和提交串起来 |
| 改动事件 | 某事项中一次有证据的需求/方案/实现调整 | 统计首次开发、正常完善、纠错与返工 |
| 耗时记录 | 一条有明确对象、口径和来源的时间记录 | 单独去重、核对可加总性 |

同一事件可能对应多份文件，一份文件也可能包含多个事件。不能按文档数计算返工率，不能把一次集中修改拆成数次重复返工。

合并示例：若 A 指令、B 执行单、C 验收记录均描述同一次实现，归为一个事件、三条证据；后续 D 明确要求撤销已实现交互，另建改动事件。仅有同义改写或文档整理，不新增代码改动次数。

## 四、先建立四份基础台账

### 4.1 资料清单

字段：文件 ID、相对路径、类型、目录、哈希/快照依据、已读状态、内容用途、提取备注。

### 4.2 事项与改动事件台账

每条事件至少记录：

| 字段 | 要求 |
|---|---|
| 事项 ID / 事件 ID | 分别唯一，不使用可能重号的文档编号作唯一键 |
| 标题、模块、端、角色 | 按实际内容登记，跨模块可有辅助标签 |
| 日期和顺序 | 正文明确日期优先；不确定标未知，保留冲突来源 |
| 改前 → 改后 | 简明描述实际行为，不能只抄“体验优化” |
| 改动性质 | 按第五节归类 |
| 原因主类和辅助标签 | 主类仅一个，证据不足归未知 |
| 提出来源 | 用户明确要求 / AI 建议 / 实测反馈 / 不明；与原因分开 |
| 实施状态 | 仅讨论、已定待做、实施中、已实现待验证、已验证、已撤回或未知 |
| 验证状态 | 构建、单测、接口、页面、真机、现场分别记录，不能互相替代 |
| 前后关联 | 替代、修复、补充、回滚的事件 ID |
| 证据 | 文件路径、标题/章节、必要短摘录、提交或测试依据 |
| 判断等级 | 原文明确 / 交叉核实 / 分析推断 / 未知，并写明推断理由 |

### 4.3 耗时台账

字段：时间记录 ID、对应事项/事件、原始表述、记录类型、分钟值或区间、人员/执行者、起止或统计范围、来源、是否与其他记录重叠、是否可加入汇总及排除理由。

### 4.4 证据缺口与争议表

登记：缺什么、影响哪个指标、目前能说什么、不能说什么、能否通过已有资料或 Git 核对。矛盾不能静默选一方；不能要求用户凭记忆补齐所有空白。

## 五、分类口径

### 5.1 改动性质（每个事件一个主类）

| 类别 | 判定标准 |
|---|---|
| 首次开发 | 首次实现该用户目标 |
| 正常完善 | 既有目标下补充合理能力，无证据表明此前违反已定要求 |
| 缺陷修复 | 已实现行为与当时明确要求或正确性规则不符 |
| 方向性返工 | 已实现成果因需求理解、产品方向或核心模型调整被撤销或替换 |
| 仅文档/方案调整 | 未能确认对应实现变化，不计代码返工 |
| 环境/交付处理 | 构建、依赖、连接、打包、部署等非产品行为处理 |
| 未知 | 证据不足，无法确定 |

不能把所有第二次修改算返工。后续新决定改变前次行为，不自动证明前次开发错误。缺陷修复和方向性返工分别展示；如合称“纠错与重做”，必须明确包含范围。

### 5.2 原因主类（证据不足不归因）

- 需求理解偏差：当时已有要求，但被理解成另一种操作或目标。
- 需求/产品方向变化：后来新增或改变决定。
- 业务模型或契约遗漏：属性归属、金额、状态、权限、接口等设计不完整或冲突。
- 实现缺陷：方案明确，实现不符合方案。
- 交互与提示设计问题：触发时机、措辞、严重程度、定位或额外步骤不合适。
- 文档/版本不同步：执行依据过时、替代关系不清或线上版本落后。
- 外部条件或环境问题：设备、第三方限制、网络、运行环境等。
- 无法判断/其他：保留原文，不强行塞入预设原因。

“AI 写的代码”不等于“AI 导致返工”。只有证据明确或交叉核实，才归因于 AI 理解、建议或实现；其他情况分析事件原因，不评价模型责任。

### 5.3 提示体验专项标签（可多选，不直接相加）

技术词/内部 ID、空泛口号或说明书腔、提示内容错误、处理方向错误、触发过早、重复提示、颜色与阻断程度不符、无必要确认、无依据预警、错误未定位到字段、成功后状态不清。

区别三种结果：只改文字；改变提示展示或触发；改变实际放行规则。不能把“看起来被卡住”和“后端确实拒绝”混为一谈。必要的权限、金额和数据校验不因产生提示就定为问题。

## 六、耗时统计：只算有依据的时间

| 时间类型 | 统计方式 |
|---|---|
| 明确记录的实际投入 | 保留原口径和执行者，可加总前先检查重叠 |
| 起止时间计算的经过时长 | 标为经过时长，可能包含等待，不叫净工时 |
| 用户或执行者回忆的约数 | 标为回忆估计，单独展示或给范围 |
| 开发前预计耗时 | 仅用于计划与实际比较，不计实际耗时 |
| 等待、环境阻塞 | 有证据才单列，不从总时长中任意拆分 |
| 未记录 | 留空或未知，不记 0，不按平均数补齐 |

- 同一任务总耗时与子步骤耗时不能重复累加；多处转述同一条时间只计一次。
- 多人同时工作时，经过时间与人时分别统计；口径混杂时不算全项目总工时。
- 只有实际时间能明确对应返工事件，才能统计已记录返工耗时。整项开发总时间不能全部记为返工成本。
- 文件时间、提交间隔、版本号差值、行数均不能代替耗时。
- 不用不同复杂度任务的时间差证明提效倍数。项目142记录的约38分钟和约6分钟，任务性质不同，不能据此宣称提升六倍。

## 七、先交统计，再交原因分析

第一轮必须先形成下表，并公布分母、未知数和覆盖率。未完成的写“暂缺”，不为了填满表格编数字。

| 输出 | 内容和口径 |
|---|---|
| 资料覆盖表 | 已盘点/已读/不可读/未读文件数，按目录及类型展示 |
| 改动性质分布 | 去重事件数及各性质数量；讨论记录与已实现事件分列 |
| 模块分布 | 每模块事项数、已实现改动数、修复数、方向性返工数 |
| 原因分布 | 原因数量、未知数量、归因证据等级 |
| 提示体验专项 | 涉及事项数、事件数、标签分布、是否实际阻断 |
| 时间覆盖表 | 可比实际时间记录覆盖的事项/事件数及缺失数 |
| 时间分布 | 按一致口径分别列实际投入、经过时长、估计和等待；必要时给样本量、中位数、范围 |
| 重复修改链 | 同一事项每次改前改后、原因、状态和可确认时间 |

指标约定：

- 已实现改动事件总数 N：首次开发、正常完善、缺陷修复、方向性返工四类中确认已实现的事件；状态未知单列。
- 缺陷修复占比 = 已实现缺陷修复事件数 / N；方向性返工占比 = 已实现方向性返工事件数 / N。它们是事件占比，不是代码量占比或成本占比。
- 原因百分比同时给出全部目标事件数和可归因数，展示未知，不能只对已知样本计算后称全项目占比。
- 专项标签可重叠，列明多选；跨模块总计按事件 ID 去重。
- 耗时覆盖率按所用时间口径分别计算；总投入时间覆盖率和可归属返工耗时覆盖率分开。
- 时间只代表有记录且可比的样本，不外推为整个项目总成本。覆盖率高也不自动排除记录偏差。

## 八、从统计到结论的程序

1. 完成盘点和内容提取，先不写“主要问题是……”之类结论。
2. 合并重复证据，串联事项时间线，复查同名重号及相互替代文件。
3. 对全部方向性返工、金额相关事件、耗时记录和争议事件逐条复核；普通事件按模块和类型抽样核对，并记录抽样数量及纠错结果。
4. 输出分类统计及未知项；检查“文档多”是否误当“改动多”，“次数多”是否误当“耗时高”。
5. 从真实排序中选择重点事项，解释其变化过程，兼顾顺利完成的同类案例，不只挑支持原假设的材料。
6. 每条结论按“统计结果 → 代表事件与来源 → 解释 → 其他可能原因 → 建议 → 可信范围”书写。
7. 修订先前初步总结：保留得到支持的判断，降低或撤回证据不足的判断；保留版本说明。

不能凭重复次数直接估算节省时间。提效效果应在下一批同类任务中记录澄清、实现、验证、等待及重做情况，再与相近复杂度任务比较。

## 九、后续执行阶段与交付物

| 阶段 | 交付物 | 完成条件 |
|---|---|---|
| A 盘点 | 资料清单、读取范围、缺口表 | 每份范围内文件都有处理状态，未读不冒充已读 |
| B 提取归并 | 事项/事件台账、耗时台账、证据索引 | 核心字段可追溯，重复与冲突有处理记录 |
| C 分类统计 | 分类统计表及口径说明 | 数字可从基础台账重新计算，分母和覆盖率明确 |
| D 深入分析 | 重点事项修改链、原因分析 | 结论有统计和直接证据支持，推断标注清楚 |
| E 学习应用 | 修订后的技巧总结、下个项目约定 | 建议对应已发现问题，验证方法可执行 |

后续台账建议使用 UTF-8 CSV 保存明细，Markdown 保存说明与分析；需要筛选和阅读时可另外制作工作簿。全部放在本目录，原始业务文件保持原样。表格中路径统一以项目根目录为基准。

每阶段完成后交付数据和覆盖情况；无需逐份资料向用户确认。只有确实无法从证据判断、且会显著改变统计口径的选择，才集中说明并询问。
