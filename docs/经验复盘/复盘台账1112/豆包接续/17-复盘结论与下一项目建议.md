# 微聚小工单：AI开发的经验与教训

2026-11-13 · 最终经验总结版

本次复盘已按用户调整后的目标完成：从已有记录中提炼下次开发能直接采用的做法，不追求全项目精确修改次数、返工率和耗时排名。以下是典型案例能支持的经验，不代表全项目问题频率排序。历史记录中的“通过”是当时的记载，本轮未重新运行业务验收。

## 1. 先把用户目标说成一个具体动作

**发生了什么：**“学操作”先做了工序文字卡片和续学，又扩展电脑端和管理页入口，后来整套撤除。拆除指令说明，真正想要的是教新人使用系统，而不是教工人学习工序。

**学到什么：**名称相似，不代表要解决的问题相同。功能已经实现，也不能作为继续扩建的理由。现有资料不足以认定最初是谁理解错，但足以说明目标值得尽早核对。

**下次怎么做：**新概念开工前，用一句话描述“谁在什么场景，从哪里进入，完成什么动作，看到什么结果”。容易歧义时先用小样例说明；方向未定，先不接正式菜单、数据库和权限。普通小改动不强制先做原型。

来源：已作废78、82、83；已做84《移除学操作功能》。

## 2. 界面要看完整效果，别只逐句改文案

**发生了什么：**143登录页先精简主区，后续又补底部链接和版权弹窗；253回答排版首轮后，用户仍觉得平淡，第二轮使用实际长度回答继续调整阅读区域、字号、间距和来源展示。

**学到什么：**文字单独看没问题，放进整页仍可能拥挤、重复或缺重点。多轮修改也不全是缺陷，有些是看到效果后产生的新决定。

**下次怎么做：**同页相关改动尽量一起展示，使用真实长度的内容，查看常用屏幕和窄容器。集中看一轮完整效果，发现问题再定点修改；不要每改一处就重复全站验证。

来源：已做143《登录页参照金蝶精简》；253《PC助手回答排版优化》。

## 3. 提示好不好，取决于出现时机和下一步动作

**发生了什么：**432先把取价提示里的裸ID、运算符和长句改成人话，再区分产品属性和工序工艺属性的处理位置；433进一步把工艺缺失指向本页，并取消选产品时自动取价。452又区分可继续操作的提示与审核失败等错误。

**学到什么：**“AI味”不只是语气问题。提示位置不对、时机过早、处理方向错误，或颜色让人误以为流程被卡住，都需要检查。只润色句子可能解决不了问题。

**下次怎么做：**按正常、缺值、冲突几种操作核对：用户刚做了什么？现在必须提醒吗？究竟能否继续？去哪里处理？能在当前页补齐就说清位置；需要拦截时保留必要校验，不能为了“不打扰”放过错误。

来源：已做432、433、452。这里只提取提示设计经验，不裁定432中其它规则变化的范围。

## 4. 改接口契约时，顺手检查直接调用者

**发生了什么：**登录改成按账号归属选厂后，建账套脚本仍按旧的一步登录取Token，还把需要登录接口返回的401误判成“后端连不上”。故障说明记录了脚本修复及只检查连通性和登录的DryRun验证。

**学到什么：**网页完成改造，不代表配套脚本也已适配。先判断错误发生在哪一层，能减少对正常后端的无效修改。

**下次怎么做：**改变登录流程、返回字段或错误约定时，查直接使用这些契约的页面、脚本和集成入口，做必要回归。遇到连接问题，分清无响应、HTTP拒绝、业务失败和解析失败，不见到异常就重写业务服务。

来源：已做151《登录选厂按账号归属》；测试反馈《一键新建账套-故障定位与修复》。不将DryRun成功写成真正新建账套已验证。

## 5. 测试判据要正确，完成状态要说具体

**发生了什么：**自测曾只看HTTP 200，把业务返回“对象不存在”误判成软删除；76确认删除本身无需修复。另一个负数报工问题则真实写入了非法数据，75记录了修复与回归。228代码已落地但真实企微群@未验，63也存在已完成部分与后置部分。

**学到什么：**测试结果需要正确解释，文件放在哪个目录也不能替代事实。“代码完成”“构建通过”“页面可用”“现场通道可用”是不同结论。

**下次怎么做：**校验要同时检查接口约定的业务结果和实际效果。验证按风险选择：文案样式看展示，业务规则查边界，外部通道查实际目标环境；交付用短句写清已做、实际验证、未验证三件事。小改动不因此增加整套部署演练。

来源：已做74自测登记、75负数修复、76 P1清单；处理中228、63。

## 6. 值得保留的做法：缩小范围，但做通一条流程

**发生了什么：**142复盘记录，固定缺料样板用固定数据完成“查看缺口→模拟补齐→再校验→重置”，复用现有前端环境，达到范围后交付。253则用真实回答组件和固定长文、表格样例预览，明确不把它当成真实模型查询验收。

**学到什么：**小范围也可以形成完整、可观察的成果。固定样例适合验证交互和展示；它不能证明生产数据、真实模型或外部通道正确。

**下次怎么做：**先明确演示、内部试用还是正式生产。演示先做最小完整流程，不为将来提前搭通用框架；生产功能按风险保留事务、权限、数据和金额正确性验证。验证达到既定终点就交付，不顺带扩建。

来源：归档142《轻量指令与验收避坑》；已做253。142中的约38分钟和约6分钟属于不同复杂度任务的用户回顾约数，不能据此承诺提速倍数。

## 7. 本次复盘自身的教训：整理精度要服务于用途

**发生了什么：**整理一度偏向逐份阅读、精确事件拆分和时间关联，形成了大批待核资料。用户随后明确，目的只是吸取经验教训，不值得为次要精度消耗过多Token。

**学到什么：**台账越来越完整，不等于复盘越来越有用。AI自主执行时也要判断：下一步核查是否会改变实际建议。

**下次怎么做：**先使用已核实案例形成可用结论。只有疑点会改变重要建议时才补查；查不清就降低表述强度、保留未知或不用于主结论。不把小清单不断拆成新清单代替交付。

来源：本次会话的范围调整及11执行清单。

## 下次开发直接照着做

| 时机 | 采用的动作 | 做到什么程度就继续 |
|---|---|---|
| 开工前 | 用一个具体用户动作复述目标，确定本次范围 | 新概念歧义已澄清；普通小改动直接做 |
| 有业务取舍时 | 写关键分支与少量输入输出例子 | 正常、缺失、冲突和必要失败路径讲清；权限、金额等不变量有依据 |
| 做界面时 | 用完整页面和真实长度内容看效果 | 主路径和重点清楚，典型窄屏可读 |
| 做提示时 | 核对时机、能否继续、处理位置 | 正常操作不被误导，必要错误仍被拦截 |
| 改契约时 | 检查直接调用者 | 页面、脚本和集成入口没有明显沿用旧约定 |
| 执行中 | 拆成能落地的小清单，完成一项再推进 | 关键证据和下一步足以接续，不为记账制造工作 |
| 验证时 | 按影响范围和风险验证，失败才扩大 | 实际证据足以支持本次交付范围 |
| 交付时 | 说明改了什么、验证了什么、还缺什么 | 达到授权目标即结束，不附加无关优化 |

这些做法适用于本项目和相近开发任务。正确性、异常可追查、权限以及涉及钱的可追溯与可重算要求始终保留。后续可以观察是否减少方向撤回、遗漏调用者和重复验证，但本报告不声称已经证明节省多少时间或Token。

## 阅读和使用边界
