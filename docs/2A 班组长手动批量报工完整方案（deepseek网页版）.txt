# 末道补报前道（批量补报）——修正稿

> **来源：** DeepSeek 网页版「班组长手动批量报工完整方案」  
> **本文定位：** 对照本项目（PRD / 数据字典 / docs/10·14 / docs/16）纠偏后的**可交付方案**。  
> **一句话：** 保留「人工点一下、多道工序一次补数量」的核心；砍掉班组长角色、计件分摊体系、冲销、日志表、设备追踪、行业开关等过度设计。

---

## 〇、原方案哪里不对（对照本项目）

| # | DeepSeek 原文 | 问题 | 改正方向 |
|---|---|---|---|
| 1 | 权限写「班组长 / 车间主管 / 系统管理员」 | 本项目只有 `role=1` 管理员、`role=2` 生产人员；班组长是 **docs/16 第二期** 才做，现在引入会拖垮交付 | 本期入口仅 **role=1 管理员**；工人无入口 |
| 2 | 独立「计件分摊明细表」+ 冲销 + 按工时比例 + 工资挂起 | 工资报表仍是简单版；新建分摊体系 ≈ 半套薪资模块，明显变复杂、不好交付 | **不做分摊表**。「谁做的」在提交时直接选人写进 `prod_report.user_id`（可一道工序拆多人 → 多条报工） |
| 3 | `prod_report` 加 `report_type / batch_id / operator_id / device_type / device_id` | 字段过多；看板/报表现按 `SUM(good_qty)` 聚合，不需要设备维度 | 最多加可选 `batch_no`（同一次操作同一号，便于追查）；其余不改 |
| 4 | 新建「批量操作日志表」 | 审计可用现有报工记录 + `batch_no` 查出；单独日志表本期多余 | **不做**日志表 |
| 5 | 「返工工单禁止」「质检追溯客户强提示」「已结案」 | 数据字典无返工工单、无质检开关；状态只有 未开始/执行中/已结束/已取消 | 删掉这些概念；状态按现有 4 态校验 |
| 6 | 「修改不良后良品相应减少」「良品+不良≤计划」 | 与 docs/14 **冲突**：上限只约束良品，不良不占上限；良品/不良各自独立 | 补不良走现有改报工；**不自动减良品**；不良不参与上限 |
| 7 | 「冲销 = 生成反向报工记录」 | 现约定「只改数不删」；负数记录会搞乱 `SUM` 与防超额 | **不做冲销**；错了用现有 `PUT /Report/{id}` 改数 |
| 8 | 「更新工序累计报工数」 | `prod_work_order_operation` **无累计字段**，累计靠 `SUM(prod_report)` | 只插报工行，完工回算走现有 `RecalcStatusAsync` |
| 9 | PDA 独立能力、扫工序码、device_id | 本项目是 H5 + PDA 键盘枪（当扫码枪），无独立 PDA App、无工序码 | 手机/PC 够用；扫码仍是**工单号** |
| 10 | 行业默认开关、补录不良期限锁定、分摊必须挂起工资 | 配置项堆叠，交付和测试成本高 | **不做后台开关矩阵**；功能默认给管理员用；不良随时可改（沿用现规则） |
| 11 | 批量报工不校验部门权限、班组长代报全工序 | 硬规则「工序报工权限=部门」；生产人员批量会与部门模型冲突 | 仅管理员可批量（管理员本就可豁免部门限制，与现 PC 报工一致） |
| 12 | 入口挂「末道报工页底部」+ 多端齐全首版 | 首版铺 PC+H5+PDA+分摊，范围过大 | **首版仅 PC**；H5 有明确现场需求再补 |

**保留的正确点（原方案里值得留的）：**

- 纯人工触发，不做「末道一报自动倒冲」（避免无痕、难追责）。
- 一次填一个数量，给多道待报工序各生成正规 `prod_report` 行。
- 事务提交；数量 ≤ 各待报工序剩余可报的最小值。
- 不良默认 0，需要时事后逐条补。

---

## 1. 功能定位（修正后）

**名称：** 批量补报前道（界面文案可用「一键补报未完工序」）。

**解决什么：** 流水线小厂经常只在末道认真报数；前道漏报导致看板进度假低。管理员一次性把「尚未报满的工序」按同一良品数补齐。

**不是什么：**

- 不是自动倒冲。
- 不是班组长角色体系（等 docs/16 第二期）。
- 不是计件分摊/冲销/审计日志子系统。

**谁用：** 仅轻量管理员（role=1）。生产人员继续只走单工序报工。

---

## 2. 权限与终端（修正后）

| 功能 | PC | 手机 H5 | 权限 |
|---|---|---|---|
| 批量补报 | **首版做** | 不做（有需求再开） | 仅 role=1 |
| 查看待报工序 / 剩余可报 | 随弹窗展示 | — | 同上 |
| 「谁做的」分配 | 弹窗内按工序选人拆数量 | — | 同上 |

- 不做独立 PDA 端；PDA 即浏览器 + 扫工单号。
- 不做「普通工人看分摊结果」页（无分摊表）。

---

## 3. 操作入口（修正后）

**首版只保留一个入口：**

- PC 工单详情 / 报工页：按钮【一键补报未完工序】（仅管理员可见）。

**明确不做（首版）：**

- 末道报工页再挂第二个入口（避免工人误点；管理员已有工单入口）。
- 扫工序码、设备标识。

---

## 4. 前置校验（修正后）

后端统一校验：

1. 当前用户 `role = 1`，否则 403 / 业务拒绝。
2. 工单存在且 `status ∈ {0未开始, 1执行中}`（已结束/已取消不可补报）。未开始允许补报：提交后走现有逻辑变为执行中。
3. 存在至少一道「剩余可报 > 0」的工序。  
   - 剩余可报 = `plan_qty - SUM(good_qty)`（无任务行则 plan 兜底工单 `qty`，与 docs/14 一致）。
4. 本次良品数 `N > 0`。
5. `N ≤ min(各待报工序剩余可报)`；超了明确提示「超过工序 X 剩余可报 Y」。
6. **不做：** 返工工单、质检开关、单次最大数量后台配置、行业开关。

---

## 5. 操作流程（修正后）

1. 管理员打开工单，点【一键补报未完工序】。
2. 弹窗展示待报工序列表（序号、名称、计划、已报良品、剩余可报）。
3. 录入**本次统一良品数 N**（默认建议可填 `min(剩余)`，可改小不可改大过 min）。
4. **「谁做的」——本期就在这里做完（替代原分摊模块）：**
   - 默认：每道待报工序生成 **1 条**报工，`user_id = 当前管理员`（和现 PC 代报一致）。
   - 可选展开：某道工序可拆成多人，每人填数量，合计必须 = N；每人一条 `prod_report`。
   - 人员下拉：本厂用户即可（不强制校验该工人是否属于该工序报工部门——因为这是管理员代录；若要坚持部门一致性，可只提示不拦截，拍板见 §自主拍板）。
5. 确认提交 → 事务内插入多条 `prod_report`（良品=分摊到该人的数，不良=0，时长=0）。
6. 调用现有完工回算；成功提示「已为 X 道工序生成 Y 条报工」。
7. 需要补不良：到报工查询改对应记录（现有 `PUT`），**不**自动改良品。

---

## 6. 数据模型（修正后）

### 6.1 尽量不改表；若要可追查「同一次点击」

可选加一列（非必须；没有也能上线）：

```sql
-- prod_report 可选
batch_no NVARCHAR(32) NULL   -- 同一次批量补报共用；单条报工为空
```

**不做：**

- `report_type / operator_id / device_type / device_id`
- 批量操作日志表
- 计件分摊明细表 / 冲销表

### 6.2 统计口径

批量补报的行与工人扫码报工**同表同字段**。看板、防超额、`RecalcStatusAsync`、工资若按 `user_id` 汇总——**直接复用**，无需新聚合。

---

## 7. 生成逻辑（修正后）

```
事务开始
  加悲观/乐观锁：按工单 id（防两人同时补报超数）
  重新计算各工序剩余可报
  校验 N ≤ 每道剩余
  对每个「待报工序 × 分配人」：
      INSERT prod_report(order_id, operation_id, user_id, good_qty, defect_qty=0, ...)
  RecalcStatusAsync(工单)
事务提交
```

- 已报满的工序跳过。
- 某工序已报一部分：只允许补不超过其剩余；本次对该工序写入的合计 = N（不是「自动只补差额」——由校验保证 N 不超过剩余，写入就是 N）。
- **不做反向冲销记录**；改错用现有修改接口。
- **不**维护工序表上的累计字段。

---

## 8. 不良（修正后）

- 批量行默认不良 = 0。
- 事后用现有报工修改：可改 `defect_qty / defect_id / good_qty`（改良品仍受 docs/14 防超额约束）。
- **禁止**「改不良自动减良品」。
- **禁止**「良品+不良≤计划」校验。
- 不做「补录期限锁定」。

---

## 9. 「谁做的 / 计件」怎么交代（修正后）

| 原方案 | 修正 |
|---|---|
| 先挂班组长，再 PC 分摊冲销 | 提交时就把数量拆到具体工人（或暂挂管理员） |
| 工资读分摊明细，未分摊挂起 | 工资仍按 `prod_report.user_id` 汇总（现有思路）；挂管理员名下的需管理员自己再改 `user_id`——**若现改报工不支持改人，本期允许改 `user_id`（仅管理员）** 或要求提交时必须选人 |

**建议拍板（推荐）：** 弹窗里每道工序至少选一个报工人，默认当前管理员，避免大量产量挂管理员名下事后扯皮。

---

## 10. 配置（修正后）

**首版零配置。** 有管理员账号就能用。

明确不做：总开关、移动端开关、行业默认、补不良期限、单次最大数量、分摊是否必须。

---

## 11. 异常与边界（修正后）

| 场景 | 处理 |
|---|---|
| 无待报工序 | 「所有工序已报满」 |
| N 超某工序剩余 | 「超过工序【名称】剩余可报 Y」 |
| 已结束/已取消 | 禁止 |
| 并发 | 工单锁；后者提示冲突重试 |
| 重复点击 | 前端禁用 + 后端事务；不引入复杂 batch 幂等协议（可选：前端生成一次 `batch_no` 传后端，相同 `batch_no` 已存在则直接返回成功） |
| 撤销 | 管理员改数或把良品改 0（现规则）；不做冲销单 |

---

## 12. 风险（如实保留、范围收窄后）

- 批量补报仍是「事后认账」，不能证明前道真实加工过——小厂可接受；强追溯客户别用（口头约定即可，不做开关）。
- 产量归谁完全依赖管理员选人是否认真。
- 与「工人逐道扫码」并存时，可能出现前道已有部分工人自报 + 管理员再补——靠剩余可报校验兜住，不超计划即可。

---

## 13. 测试要点（瘦身后）

- [ ] 工人账号看不到按钮；管理员可见。
- [ ] 6 道工序，前 5 未报、第 6 已报满：补 N=1000 → 前 5 各增良品 1000（或按拆分多人多条）。
- [ ] 某前道已报 200、计划 1000：N=900 被拒；N=800 通过后该道合计 1000。
- [ ] 超计划被拦；不良不占上限（与 docs/14 一致）。
- [ ] 提交后看板/工单进度正确；工单该结束时能结束。
- [ ] 事后改某条批量报工的不良，良品不变。
- [ ] 并发两人同工单补报，不超数。

---

## 14. 自主拍板（实现前定死）

| 项 | 决定 |
|---|---|
| 角色 | 仅管理员；不引入班组长 |
| 终端 | 首版仅 PC |
| 分摊 | 不建表；提交时选人拆数量写入 `prod_report` |
| 字段 | 可选 `batch_no`；不加设备/类型/操作人冗余列 |
| 日志/冲销/配置开关 | 不做 |
| 不良与上限 | 完全遵循 docs/14 |
| 部门权限 | 批量补报走管理员豁免（与现 PC 报工一致） |
| 自动倒冲 | 永不做；必须点按钮 |

---

## 15. 工作量粗估（修正后）

| 块 | 人天（约） |
|---|---|
| 后端批量接口 + 事务 + 防超额复用 | 1 |
| PC 弹窗（待报列表 + 数量 + 按工序选人） | 1 |
| 可选 batch_no + 联调验收 | 0.5 |
| **合计** | **约 2.5 人天** |

原 DeepSeek 全量（角色+分摊+冲销+日志+多端+配置）：估 **2 周+**，且与第二期班组长模型缠在一起，**不适合当前交付**。

---

## 16. 最终结论

伙伴要的「末道认 1000、前面也算 1000、谁做的自己分」——用 **管理员一键补报 + 提交时选人拆数量** 就能落地。  

DeepSeek 原文里「班组长 / 计件分摊冲销 / 设备审计 / 行业开关」对当前双角色、轻量表结构的小工单来说过重，已全部砍掉或改写为上表方案。
