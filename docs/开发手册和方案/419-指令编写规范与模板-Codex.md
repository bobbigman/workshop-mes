# 419 指令编写规范与模板（Codex）

> 状态：当前有效；2026-10-25启用。
> 用户依据：新建Codex使用的开发指令模板，将豆包指令起草规范及102系列模板标为作废。
> 适用：本项目后续开发/执行指令的编写、审核与修正。不是一份待执行的业务开发任务，不因此启动其它功能。
> 替代：原《指令起草规范（给豆包/千问）》、102精简版、V2、V3。旧文件保留作历史资料，不再作为起草或审核标准。

## 一、使用原则

**主线简明，业务分支充分，契约可实现，验证可对应。** 不限制半页、一页或40～80行；篇幅由风险和必要信息决定。复杂度不能靠删掉条件掩盖，也不能靠堆技术细节制造。

- 明确、低影响、无契约变化的小修改按AGENTS直接开工，不强制先填模板。
- 有业务取舍、改表/改接口、多状态或资金风险时，写指令并补必要决策表；不适用章节删掉，不为填满模板新增能力。
- 同一规则只定义一次，用分支ID、状态表和引用关联正文/附录/测试；不要把同一流程换三种说法重复抄写。
- 需要列全的是会改变**用户结果、权限、数据写入、金额或失败恢复**的分支。循环写法、局部变量、工具函数等常规实现不提前写死。
- 保留正确性约束，让执行方选择最小正确实现。指定技术栈和真实契约，不在无依据时硬规定表数、类名、缓存/队列/通用框架。
- 未核实的事实标“待核实”，未定的产品选择标“待确认”；正确性红线和已有授权不重复请求批准。
- 本规范不改变AGENTS授权规则。用户只要文档就只交文档；后续明确要求开工时先审后做。替换模板不自动授权实现既有未做指令。

## 二、证据与取舍

| 标记 | 含义 | 执行方式 |
|---|---|---|
| 已核实 | 有代码、权威文档或实际查询依据的现状 | 给文件/符号/接口/证据日期，不绑容易过时的行号 |
| 已定 | 用户明确决定或现有项目约定覆盖 | 写依据，不把起草者建议冒充用户决定 |
| 待核实 | 现状、字段、复用点、数据能力尚未确认 | 执行方针对性核实，不让用户代查代码 |
| 待确认 | 无现有依据且会改变操作、业务结果或数据契约的取舍 | 给推荐及影响，一次集中确认；独立且已授权部分继续 |

接口、按钮、字段、工资发放/关账等能力，没有证据不写“已有”。竞品只采信带出处的结论，区分产品明确功能、一般建议与本项目推断。

## 三、分支如何列全

按实际涉及的维度检查，不要求每个任务都有全部维度：

| 维度 | 必须核对的真实分叉举例 |
|---|---|
| 身份与范围 | 未登录/越权/本厂/跨厂，授权有效/失效；身份由服务端取得 |
| 输入与对象 | 空/非法/不存在，边界值；对象已删除/版本变化；不能以默认值掩盖错误 |
| 业务状态 | 每个实际合法状态、允许的动作、未知或不支持状态；预留状态不冒充已有能力 |
| 时间 | 生效前/当日/之后，补录业务时间/提交时间，跨日/月、时区；只列涉及的边界 |
| 依据与匹配 | 唯一命中/缺失/多命中/来源冲突；事实、快照、当前资料分别使用什么 |
| 历史与金额 | 是否已有报工/工资/结算，原值/新值/差额；精度、换算、系数、扣款和舍入 |
| 并发与重复 | 预览后变化、新增目标、相同请求重试、同键异内容、重复点击 |
| 失败与恢复 | 写前失败/中途失败/提交后响应丢失；回滚范围、部分成功边界和查询结果方式 |
| 界面与入口 | 入口是否可见、跳转/卸载时机、无数据/加载/失败/重复提交；共享规则的其它已有入口 |

每个关键分支至少写：**条件 → 提示/返回 → 写哪些数据 → 不得改变什么 → 后续状态 → 验证项**。多个条件可能同时成立时，写检查顺序或优先级；互斥条件要明确，未覆盖或未知情况要有明确处理。

既要覆盖各维度，也要覆盖会相互影响的组合，例如“已确认工资＋预览后新增报工”。不用枚举所有无意义的笛卡尔积；不能因为单项覆盖就宣称关键组合全部覆盖。

## 四、可直接使用的指令模板

下面是内容骨架，不要求保留无关空表。复杂数据/算法细节可放同文附录或已指定方案文件，但关键业务分叉与交付范围必须在主指令可见。

````markdown
# NNN-开发/执行指令：目标标题

> 状态：待做 / 待确认 / 实施中 / 已实现待现场验证（按事实）
> 日期、性质：售前演示 / 内部试用 / 正式生产；数据为固定模拟还是真实业务
> 本次交付：文档 / 代码与必要验证 / 本地验收 / 增量包 / 部署；按用户授权写终点
> 目标：让【谁】在【入口/触发条件】完成【动作】，得到【可观察结果】
> 依据：用户决定、权威文档及现状证据；起草规范为419

## 1. 已核实现状与取舍

| 项 | 现状/方案 | 证据或决定依据 | 已核实/已定/待核实/待确认 |
|---|---|---|---|
| 已有与缺口 | 只写直接相关能力，不重复开发已有功能 | 文件/符号/记录 | … |
| 做与不做 | 本次完整用户流程、明确后置项 | 用户决定/项目约定 | … |
| 入口与影响面 | PC/H5、角色、数据范围、现有入口复用 | … | … |

只列影响主流程的待确认业务项；常规实现和事实核对由执行方负责。未定项依赖部分不编码，独立已授权部分可继续。

## 2. 完整流程与范围

【入口 → 查看/输入 → 预览或操作 → 结果/下一步】。
说明界面挂载/跳转时机；直接落点文件/服务；本次影响的数据和已有入口；真实数据操作须列准确目标范围。

## 3. 业务决策表

| 分支ID | 条件及优先级 | 提示/返回或用户看到什么 | 写入范围 | 保持不变/后续状态 | 验证ID |
|---|---|---|---|---|---|
| B01 | 当… | 则… | 无 / 明确对象字段 | … | V01 |
| B02 | 当…且… | 则… | … | … | V02 |
| B03 | 未知/不支持状态 | 明确拒绝或已定处理，不吞错 | … | … | V03 |

无关维度不加入；条件重叠时明确优先级，增加必要组合分支。多状态流程再加下表：

| 当前状态 | 操作与前置条件 | 成功状态 | 拒绝/失败后的状态 |
|---|---|---|---|
| … | … | … | … |

## 4. 数据与接口契约

| 对象/关联 | 读取来源 | 本次新增/修改/删除/继续引用 | 历史记录与审计 | 不变量 |
|---|---|---|---|---|
| … | 原事实/快照/有效配置，不能混用 | 明确原对象还是复制对象 | … | I01… |

涉及接口时写：方法/路径、调用角色、服务端身份与厂别来源、请求字段/校验、响应、业务失败与兼容性；预览和提交如何保证内容一致。
涉及改表时先同步docs/开发手册和方案/02-数据字典.md的SQL Server DDL、约束/索引和迁移，再落代码；改业务同步01、改接口同步33。
涉及金额时写：单位、数量/时长、系数、扣价、精度/舍入、旧新金额、重算来源与审计，不能只写“调用重算”。

## 5. 事务、并发与恢复

- 哪些写入必须同时成功；事务起止与回滚范围；已有方法是否自行提交，不能假装多个独立事务原子完成。
- 预览后哪些变化使计划失效，如何重扫新增目标；锁/版本检查与现有写入是否协调。
- 是否需要幂等及唯一约束；同键同内容、异内容、并发提交分别怎样处理。
- 失败是否允许部分成功；若允许，准确说明成功/失败范围与重试边界。提交后响应丢失先查询结果，不盲目重复破坏性操作。
- 没有外部副作用就不加消息/队列框架；若确实涉及外部动作，说明授权、提交时机和失败恢复。

## 6. 核心伪代码（需要时）

只写容易误解的业务算法或状态分派，引用B/I/V编号；不是必须照抄的源码，不重复整张决策表。

```text
校验身份、授权、厂别
按已确定优先级处理输入、对象、状态与版本
执行分支Bxx（写入、事务和不变量以第3～5节为准）
返回明确结果；未知状态和失败不能静默落入成功
```

## 7. 验收与分支映射

| 验证ID | 对应分支/不变量 | 给定输入与状态 → 操作 → 可观察结果 | 合适的验证方式 |
|---|---|---|---|
| V01 | B01 / I01 | … | 针对性测试/接口/页面/数据对比 |
| V02 | B02 | … | … |

- [ ] 关键正常流程通过。
- [ ] 真实错误/状态/权限分支逐项可判定，不把资金风险藏在一句“异常处理正常”里。
- [ ] 结果/数据边界及必要的并发、回滚、重复操作验证通过。

条数服从风险，无固定3～5条上限；不要为凑数量合并独立风险，也不要测试未交付能力。简单可逆改动可用必要检查，不强制堆自动化测试。
开发中针对性验证，完整流程后集中验收；失败定点复验，没新依据不反复全量回归。

## 8. 止步线与交付终点

列本次不做及触发即停止/回滚的条件。后置功能不预建接口、表、开关、隐藏按钮或框架。
文档交付只标文档完成；代码/构建/本地/真实库/现场验证分别报告，未验证不勾通过。
是否打包、部署、真实数据写入按本次授权，不擅自扩大也不重复询问已有授权。实施完成后按AGENTS归档，旧未做指令不因模板替换自动作废。
````

## 五、if / else / switch的写法要求

适合写伪代码：取价优先级、草稿/已确认等状态转换、幂等提交、事务失败恢复、多条件冲突处理。业务结果说不清时，不用一段貌似完整的代码掩盖未定规则。

示例仅演示“已有工资状态下执行已授权重算”的分派，不是新增调价功能的实施授权，也不代表已实现发放管理：

```text
验证当前用户身份、操作权限、厂别及本次授权
if 本厂RequestId已有成功结果:
    if 请求内容一致且当前用户有权查看: 返回已保存结果
    else: 拒绝同键异内容或越权读取

验证输入、对象及确认凭据
重新核对目标集合、版本与完整计划；若变化则要求重新预览

switch 工资单实际状态:
    case 草稿: 在共同事务内重算受影响明细
    case 已确认: 在共同事务内撤回，再重算；完成后仍为草稿
    case 已发放预留状态或其它实际关闭限制: 拒绝整次操作
    default: 明确拒绝未知状态，不按草稿兜底

全部约束满足后，共同提交业务数据、审计和幂等结果
任一步失败则按指令定义的原子边界回滚
若提交响应丢失，先查询RequestId结果，不直接重复执行
```

完整指令还需覆盖无工资单、多张单或其它实际分叉，不能把这个局部示例称为“所有条件已列全”。分支优先级、可观察行为和验证映射必须与最终代码一致。

## 六、发出前检查

- [ ] 授权和交付终点明确，已定有依据，未定业务与待核实事实分开。
- [ ] 实际影响用户结果/权限/写入/资金的分支及关键组合有去向，未知状态有明确处理。
- [ ] 状态转换、原始事实与快照来源、历史影响、事务边界和必须保持的不变量一致。
- [ ] 并发、重复请求、提交结果不明等风险按需要说明；没有凭空新增通用框架。
- [ ] 每个关键分支和不变量可映射到验证；未执行验证没有写“通过”。
- [ ] 保留三条业务硬规则、异常上下文及钱可追溯可重算；没有用“演示”标签忽略真实资金/权限风险。
- [ ] 没有重复主线、过时行号、编造能力、强行限制篇幅或扩展后置功能。

本规范只替代开发/执行指令的旧起草模板，不一并废止说明书/帮助知识库等其它文种的独立约定。
