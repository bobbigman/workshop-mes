# 设计说明：工资底座与计价外挂口子

> 状态：定稿（只记账，不写代码）
> 一句话：**小工单不做"万能工资引擎"，只做"底座 + 一条算钱的口子"；哪个客户要特殊算法，就单独写一个"计价函数"塞进口子，不动主系统。**
> 依据：`docs/21`（工资计算与工价表，已实现）、`docs/02`（数据字典）、`docs/22`（复核双轨，已实现）

---

## 1. 定位（为什么这么设计）

工资计算是各厂差别最大的功能，硬塞进主系统，最后一定是又大又乱又没人敢改。所以策略是：

| 层 | 内容 | 归属 |
|---|---|---|
| **底座** | 记事实、算一个"标准版"、留口子 | 主系统，永远只有一套 |
| **外挂** | 某客户的特殊计价 | 每个客户单独一个"计价函数"，独立项目/脚本/小程序皆可 |

原则一句话：**事实记全、记死；钱的口子留小、留固定；定制只换"计价函数"，不碰主系统。**

---

## 2. 底座已经做了什么（这部分永远不动）

三件事，`docs/21` 已落地：

**① 事实记全、记死。** 报工那一刻就落快照，谁、哪天、哪道工序、良品/不良多少、干了多久、当时单价多少，都存在 `prod_report`，复核通过（`review_status=1`）才入账，之后冻结（`settled_flag=1` 禁改）。

**② 内置一个"标准版"算法。** 计件 / 计时 / 固定三种 + 不良扣款，够 80% 的小厂直接开箱用。规则走 `base_price_rule`，后台匹配（有优先级、有生效期），不是前台乱填。

**③ 结果单独存。** 算出来的钱进 `salary_statement` / `salary_statement_item`，金额固化，和"事实"分开。算错了重算，不动历史事实。

> 关键点：**事实（`prod_report`）是定死的公共底座，任何客户、任何算法，都算这一份事实。** 这一条是"可扩展"的根。

---

## 3. 那条"口子"是什么（核心契约）

**口子 = 一个固定不变的接口，输入是事实，输出是钱。**

```
输入：某个工厂、某周期、某（批）人的报工事实
      └ prod_report（已复核、含快照）+ 工厂自己的规则参数
输出：每个人应发多少钱（分项）
      └ 写进 salary_statement_item 的金额，或定制项目自己的结果表
```

**契约要钉死的三条（以后做定制都照这个来）：**

| # | 约定 | 为什么 |
|---|---|---|
| 1 | **读事实，不改事实。** 定制只能读 `prod_report`，绝不允许改、删、补造事实 | 事实是账本，动了就全乱 |
| 2 | **算钱的结果，单独落。** 不覆盖 `prod_report.unit_price/wage_amount` 的原始快照 | 结果可重算、可对账 |
| 3 | **一个客户 = 一个计价函数。** 输入/输出形状固定，内部逻辑随便 | 定制压到最小，不复制整个系统 |

**默认实现就是主系统内置的 `PriceRuleMatcher` + `SalaryService`（`docs/21`）。** 某客户要特殊算法，就写**另一个函数**替换这一步，主系统其余全部复用。

## 4. 定制怎么落地（动手时的接缝）

```
             ┌──────────── 主系统（底座，唯一一套）────────────┐
报工/复核 ──▶ prod_report（事实，冻结）                       │
                       │                                      │
                       ▼                                      │
              ┌────────────────────┐                          │
              │  计价口子（接口）   │  ◀── 就这一个接缝        │
              └────────────────────┘                          │
                 │                │                           │
         默认实现 │                │ 定制实现（外挂）          │
     PriceRuleMatcher       某个客户的计价函数/脚本           │
     + SalaryService         只做"算钱"这一步                 │
                 │                │                           │
                 ▼                ▼                           │
        salary_statement（结果固化）                           │
             └──────────── 主系统 ────────────────────────────┘
```

落地要点：

1. **默认客户**：直接用内置标准版，零开发。
2. **特殊客户**：新建一个独立项目/脚本，从底座读 `prod_report` 事实，按该客户规则算出金额，把结果写回（或导到该客户自己的工资表）。主系统一行不改。
3. **"写回还是外置"二选一，别纠结**：
   - 简单：结果直接写回 `salary_statement`（复用主系统的确认/导出/冻结流程）。
   - 复杂：结果放客户自己项目里，主系统只当"事实供应商"，不管钱。

### 4.1 外挂的两种形态（关键分水岭）

外挂长什么样不重要，重要的是**事实经不经过用户的手**。这决定了两条路：

| | 形态 A：离线文件型（默认） | 形态 B：直连库型 |
|---|---|---|
| 典型做法 | 系统导出事实到 Excel → 用户算 → 点按钮上传结果 | 存储过程 / VBA 直连库 / Python，直接读 `prod_report` 算 |
| 用户能不能碰事实 | **能**（文件在他手里） | **不能**（只读库） |
| 交付给客户 | **看得见、改得动、心里踏实** | 黑盒子，客户看不到逻辑，只能回头找你 |
| 失控怎么防 | 系统最后**对一遍总行数 + 每人总数**，对不上就报"报工有变动，请重新导出再算" | 天然可追溯，事实和算法都在库里 |

**两条路不冲突，是给两种人用的：**

- 客户要"自己看得懂、自己改得动、钱得自己算一遍才踏实" → **形态 A（Excel + VBA）**；
- 客户要"系统自动算、我别碰" → 形态 B（存储过程 / 系统内置）。

### 4.2 特殊客户默认 Excel + VBA

**默认走形态 A（Excel + VBA）**，存储过程只留给"客户明确要全自动"的极少数情况。理由：

1. **中小客户（如老沈这类）要的是"透明、可控"**，不信黑盒子；把存储过程给他，他看不到逻辑，反而不踏实。
2. **"失控"是伪命题**：Excel 里算的只是**草稿**，事实永远在 `prod_report` 锁着；结果上传回系统时对一遍总数，改没改、漏没漏立刻现形。**灵活在前台，兜底在后台。**
3. **交付快、好维护**：你熟 VBA，客户还觉得"透明又高级"。

落地一句话：

> 系统导出事实 → 客户在 Excel 里用公式/VBA 算 → 点按钮上传 → **系统对"总行数 + 每人总数"**，对不上就报"报工有变动，请重新导出再算" → 对上了才写回 `salary_statement`。

语言选型一句话：

| 语言 | 什么时候用 |
|---|---|
| **Excel + VBA** | **默认**。客户要自己算；你熟、交付快。注意 **WPS 免费版无 VBA**，须用 Excel |
| **存储过程** | 客户明确要"全自动、我别碰"时 |
| **Python** | 客户规则特别绕、跨数据源（一般不推荐） |

> 提醒：能纯公式搞定的（计件/计时/VLOOKUP/SUMPRODUCT）就别上宏，Excel 和 WPS 通用；只有公式搞不动的才上 VBA，此时让客户用 Excel。

---

## 5. 红线（做定制前先过一遍）

1. **不复制整个系统。** 定制永远只有"一个计价函数"那么小，其余全复用底座。
2. **不动事实。** 定制改了事实 = 废掉整个可追溯性。
3. **不做半吊子。** 底座的标准版要么做干净（计件/计时/固定+扣款，真发货），要么底座干脆不算钱只记事实——最忌"又像标准又不标准"。
4. **结果与事实分离。** 金额另存，别混进 `prod_report`。

---

## 6. 一句话总结

> 底座记死事实 + 留一条算钱的口子 + 定制只写一个计价函数。

这套你**现在已经能扩展了**：事实（`prod_report` 快照）和口子（`PriceRuleMatcher` 的输入/输出）都打好了，差的只是把这条口子的契约（§3）钉成文档、并在第一个定制客户来时按 §4 走一遍。
