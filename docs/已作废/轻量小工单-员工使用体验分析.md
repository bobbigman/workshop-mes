# 轻量小工单：员工使用体验分析

日期：2026-09-30  
状态：现状评估，未实施。配套见《轻量小工单-报工可靠性与员工查账优化指令.md》。

## 结论

不用被 MES 的吐槽吓着，也不需要因此大改。评论用于检查“有没有给工人添麻烦”，不能直接变成开发清单。小工单先把“报得快、记得准、查得到”做好。

建议顺序：先修普通报工提交可靠性，微调提交反馈，再补手机“我的报工”；个人工资查询等有实际使用需求再做。本轮只保存分析和指令，不改业务代码、不改数据库、不部署。

## 已经做好的部分：保留，不重建

- 派工用于提示任务，不代替部门报工权限，也不是报工前置条件。
- 报工时长非必填，已有连续报工与 PDA 扫码入口。
- PC 已有改数、退回复核、补报能力；并非完全没有纠错路径。
- 工资已有明细、导出、确认冻结和纠错能力，不需要重建工资系统。
- 异常已有上报与 PC 标记恢复；先约定现场谁处理，不必增加复杂流转。
- 手机已有作业指导书/图纸入口，不应列为新功能。

## 建议修改

### 1. 优先补普通报工提交可靠性

现状：手机提交期间禁用按钮；普通 ReportDto 没有请求去重标识，SubmitAsync 未见普通报工去重。批量补报已有 batch_no 机制，不代表普通报工已有同等保护。

普通路径先保存报工，再保存扩展字段、重算工单状态。后续失败可能出现“页面报错，主记录已经保存”。网络响应丢失也可能诱发重复提交。

建议：同一次提交重试只记一笔；主记录、扩展字段、相关状态更新作为完整业务提交处理。不能靠“数量一样就拒绝”去重，因为同工序连续两批相同数量是正常生产。

### 2. 小改报工页

“报工时长”目前一直显示，先标注“选填”；折叠到更多信息可作为后续体验调整，不要误伤计时场景。成功提示从一句“报工成功”变为包含工序、良品、不良和复核状态的回执。无须加一道强制确认弹窗。

### 3. 增加只读的“我的报工”

手机当前缺少自己的历史报工入口。不确定是否提交成功时，手册要求找管理员查。

增加日期、工单、工序、数量、提交时间、复核状态、退回原因即可；只看本人、本厂数据。改数仍留 PC，不顺带建设手机审批、申诉和补报中心。

### 4. 工资查询后置

当前工资页面是管理员入口。“工资透明可对账”应解释为管理员可查明细、导出交工人核对，不能宣传成工人随时用手机查工资。

先用现有导出功能跑通完整工资周期。确有每天查钱的需求，再做“本人已确认工资”只读页，另立指令。现有报工工资字段属于预览，结算明细才是固化依据，不宜直接当最终工资展示。

不良扣款目前可配置。试点未明确责任和规则时，建议现场先配为零；这是交付建议，不是本次自动修改客户工价数据的指令。

## 不增加的东西

不因评论新增厕所/停工计时、个人效率排名、自动绩效、复杂申诉、更多审批、设备联网或整套移动工资中心。不强制开启派工、AI、企微推送，也不取消部门权限、复核、结算冻结等正确性约束。

## 落地顺序

1. 班组长与财务先核准资料、单价、权限和纠错路径。
2. 一个班组试用，包含不熟手机的工人，使用真实工单；管理员每天处理退回和异常。
3. 跑通完整工资周期，对清差异后逐班扩面，撤掉重复登记。
4. 有真实需求再扩展员工工资查询。验收看是否少填、少错、能查，不只看登录次数。
