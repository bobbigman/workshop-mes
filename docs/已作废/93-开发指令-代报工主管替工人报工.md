## 一、目标（说人话）

有的工人**不会用智能手机、或车间不让带手机**（老工人、招不来年轻人），他自己报不了工。让**管理员/班组长**替他报：主管核对完工作量，在系统上"选谁干了多少"，**记到工人自己名下、进工人自己的工资**。工人不用碰手机，账还是工人的。

## 二、业务行为（设计决策，拿主意如下）

1. **触发**：管理员、班组长在报工页进入"代报工"模式（普通报工的一种入口，不是独立新模块），**为实际干活的工人代报**。
2. **报工人 = 被代报的工人**：每条记录记到**被代报工人名下**（UserId=工人），不是记到操作的管理员名下——工资、进度、复核都归工人。（与现"普通报工报工人=当前登录人"不同，仅代报模式放开。）
3. **可一次代报多人、各人数量不同**：如工序1 选 1号工人 120、2号工人 80；工序2 选 3号工人 200。逐行添加，各自填良品/不良数。**不要求统一数量、不要求平分**（与多人分摊、补报区分）。
4. **权限硬规则（守住"报工权限=部门"）**：
   - 被代报的工人**必须属于该工序报工权限部门**，否则拒绝并提示（不能替无权的人报，也不能借此绕过部门权限）。
   - 代报人权限：管理员不受限；**班组长受部门限制**（沿用 docs/05"管理员不受部门限制，班组长受限制"），代报人无权限则不可代报。
5. **同事务 + 可追溯**：
   - 一次代报多人 = 在**同一数据库事务**内生成多条独立记录（各人 UserId、数量不同），任一步失败整体回滚，**不留"部分人代了、部分人没代"的半笔**。
   - 代报必须记录**操作人**（谁代的），便于追溯、防纠纷；但业务归属（工资/进度/复核）按被代报工人。
6. **工资/进度/复核口径不变**：各条进各工人名下；进度按数量合计、不按条数；复核各自独立。
7. **复用不另起炉灶**：代报的"选人+数量→多条记录"基础**复用现有补报拆分（一键补报→按工序拆分到人）的落库/界面思路**，只是放开场景为"正常报工也可代报、各人数量可不同、不限未报满工序"。不新建一套报工体系。

## 三、本期不做（边界）

- 不做手机端代报入口（先 PC，符合"管理动作先 PC 后 H5/PDA"节奏）；如时间紧可只做 PC。
- 不做手机工资中心、审批、自动绩效；不改工资算法、复核、结算冻结、部门权限口径。
- 不改既有报工数据、工价、客户不良扣款。
- 不与"多人分摊"（92）混淆：多人分摊是"一群人共干一道、自动平分"，代报是"主管替不会报的人报、各自数量"。

## 四、第 0 步：先审真（开工前必做）

背景：本指令让普通报工的"报工人"在代报场景改为**被代报工人**，并在同一事务内为多人生成多条记录。

- **当**：确认普通报工 `ReportDto` 目前无"被代报人"入参、`SubmitAsync` 报工人固定=当前登录人 → 按本指令实施。
- **当**：代码已具备"主管替工人报、记到工人名下"能力 → 停止，回报"已实现，复用"，只补缺的验收。
- **当**：第 91 指令（去重 + 事务完整）未落地 → 先完成 91 再动代报；否则代报多人可能留半笔。
- **当**：与"一键补报拆分到人"（BatchReport.Users）能力可复用 → 明确复用点与差异（本指令放开"正常报工/各人数量不同/不限未报满"），不重复造一套。
- **当**：报工表/EF 映射不符 → 先按 docs/02 真实结构修正，不凭想象建表。

## 五、后端（ReportService 及模型）

### 5.1 入参
- **当**：需要代报入参 → 在 `ReportDto`（或新增代报 DTO）增加"被代报人列表"，如 `List<ReportAssigneeDto>? Assignees`（空 = 现有单人报工原逻辑）；每项含 UserId、GoodQty、DefectQty、DefectId、时长等。
- **当**：Assignees 为空/null → **完全走现有单人报工原逻辑**，零回归。

### 5.2 代报拆条（核心）
- **当**：Assignees 非空 → 逐被代报人生成一条报工记录（UserId=该工人、数量为其填值），同一事务提交。
- 各条独立进各人工资、进度、复核；进度按数量合计、不按条数。
- **当**：任一被代报人不在该工序报工权限部门 → 拒绝整次提交并提示"XX 无该工序报工权限"，不静默剔除、不全报。
- **当**：代报人权限不符（如班组长代报本组外/无权限工序）→ 拒绝。
- 去重标识、防超额、成功回执按 **91 指令**执行；防超额按各被代报人合计一次校验，不得把合计算成 N 份各自超额。
- 记录操作人（代报人）字段，可追溯；业务归属按被代报工人。
- 回执返回各被代报人及其良品/不良、复核状态。

### 5.3 数据与兼容
- 复用补报拆分的基础能力与现有报工表；最小字段方案（如是否需"操作人/代报标记"列）开工时按 docs/02 核对后补入指令与数据字典，不得另造整表。
- 历史数据、旧客户端无 Assignees → 按单人处理，兼容旧行为。
- 权限、账套、身份校验在重放/重试时仍执行，不得泄露他人记录。

## 六、前端（PC 优先，本期可只做 PC）

### 6.1 PC 报工/代报（frontend/src/views/report/index.vue 或就近）
- **当**：需代报入口 → 在报工页提供"代报工"模式（仅管理员/班组长可见；班组长按权限约束）。
- 进入后：选工单 + 工序 → 添加行（选被代报工人、填良品/不良数），可多行；**被代报工人选项限定为工序报权部门人员**。
- 提交前显示各被代报人数量合计与总数是否一致；提交成功回执说明"已为 N 人代报"。
- 不改现有普通报工 UI 默认流程；代报是独立入口，不干扰工人自报。

### 6.2 手机 H5（本期可选，先不做或后置）
- 默认不做；若现场确有主管手机上代报需求再另立指令。

## 七、验收清单（逐项打勾）

### 记账与口径
- [ ] 代报后每条记录记到**被代报工人**名下（UserId、数量正确），进各人工人工资
- [ ] 各被代报人数量可不同（A 120、B 80 各自落账），不要求统一/平分
- [ ] 进度/报表按数量合计、不按条数；代报不改变工单完成数口径
- [ ] 代报有操作人记录，可追溯谁代的

### 权限与硬规则
- [ ] 被代报人不在该工序报权部门 → 拒绝，不静默剔除
- [ ] 管理员可代报；班组长受部门限制，无权限不可代报
- [ ] 代报不能绕过"报工权限=部门"硬规则
- [ ] 换账号/账套看不到他人代报明细

### 可靠性与兼容
- [ ] 一次代报多人同事务；模拟中途失败，无"部分人代了部分人没代"半笔
- [ ] 同请求重试/并发/响应丢失，只生成一套代报记录，不重复
- [ ] 防超额一次校验：剩余 10，多人代报合计不得超 10
- [ ] 单人自报、批量补报、一键补报拆分、多人分摊（92）原流程无回归
- [ ] 复核各自独立，退回一人不影响其余

后端需集成验证（非文案镜像测试）；PC 走查一次完整代报主流程；记录实际测试结果，不把静态阅读当运行验收。
